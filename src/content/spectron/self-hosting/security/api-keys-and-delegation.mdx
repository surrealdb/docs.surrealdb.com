# API keys and delegation

Spectron uses API keys for all authenticated operations. Every key is bound to a **principal** and enforces that principal's grants — `{path, verbs}` pairs naming what it may do and where. A key can never act outside those grants, and a key's own grants can only ever narrow the principal's, never widen them.

## Creating keys

Keys are created via the management API (operator), Cloud-brokered access tokens, or member self-service. Each data-plane key is **bound to a principal** and carries grant regions per verb.

Management mint (requires management key):

```http
POST /api/v1/contexts/{context_id}/principals/{principal_id}/keys/{key_name}
```

See [Management API](/docs/spectron/reference/management-api#api-keys) for the full control-plane surface.

Each key requires:

- **Principal binding** — the principal whose grants the key inherits. Required; there are no unbound keys. An optional body **`grants`** can only attenuate what the principal already has.
- **Name** — a human-readable label unique within the Context, and the handle used to rotate or revoke it.
- **Expiry** (optional) — `?ttl_seconds=` on mint or rotate (`--expires-in` on the CLI). Omitted, the key never expires.

```bash
spectrond keys create ctx_acme planner-agent \
  --principal planner \
  --expires-in 2592000 \
  --url "$SPECTRON_MANAGEMENT_GRPC_URL" \
  --api-key "$SPECTRON_MANAGEMENT_API_KEY"
```

The command prints the key id and plaintext secret once — store the secret immediately. See [Management API](/docs/spectron/reference/management-api#api-keys) for the HTTP equivalent.

> The plaintext key is returned only at creation time. Spectron stores only the hash. If the value is lost, delete the key and create a new one.

### Principal types

A principal's **kind** is one of four values — it is a label describing what the
principal is, not a permission level. Authority comes from its grants.

| Kind | Description |
| --- | --- |
| `human` | A person acting through the API. |
| `agent` | An autonomous agent. The default when minting. |
| `service` | A background service or scheduled job. |
| `unknown` | Kind not recorded. |

Each grant is a **`{path, verbs}`** pair — a scope path plus the verbs allowed on
it. The seven verbs are `memory:read`, `memory:write`, `memory:forget`,
`scope:read`, `scope:create`, `scope:delete`, and `grant:manage`.

```bash
spectrond principals create ctx_acme "Planner bot" \
  --kind agent \
  --grant memory:read=org/acme \
  --grant memory:write=org/acme/agent/planner
```

## Self-service keys and Cloud brokerage

Two flows share the same key substrate on the Spectron data plane:

### SurrealDB Cloud (SurrealDB Studio)

End users call the **SurrealDB Cloud API**, not Spectron's management API directly. Cloud holds the root management key and brokers on your behalf.

| Actor | Cloud API entry | Spectron effect |
| --- | --- | --- |
| Member | `POST /v1/organizations/{org}/spectron_contexts/{ctx}/access_tokens` | Short-lived token for **their own** principal (`external_id = surreal-cloud:<user_id>`) |
| Admin | `POST …/spectron_contexts/{ctx}/api_keys` | Long-lived `sk-ctx-…` key (what SurrealDB Studio **API keys** creates) |
| Admin | `POST …/spectron_contexts/{ctx}/scoped_keys`, `…/principals`, `…/scopes`, … | Proxied management operations |

Members cannot call admin proxy routes (403). **`ttl_seconds`** on access tokens is required; re-broker before expiry — there are no refresh tokens.

For SurrealDB Studio and application integrations, use **API keys** and your context **host**. Members obtain brokered tokens through the Cloud API entry above.

### Self-hosted operator broker

Operators with a Spectron **management key** can broker directly:

```http
POST /api/v1/contexts/{context_id}/access-tokens
Authorization: Bearer <management-key>

{
  "external_id": "surreal-cloud:usr_01HF…",
  "display_name": "Alice",
  "ttl_seconds": 3600,
  "grants": {
    "memory:read": [{ "org": "acme", "user": "alice" }],
    "memory:write": [{ "org": "acme", "user": "alice" }]
  }
}
```

**Self-service** (data-plane API) — once a member holds a brokered or admin-minted key, they manage **their own** key without admin access:

```http
GET  /api/v1/{context_id}/me
POST /api/v1/{context_id}/keys
GET  /api/v1/{context_id}/keys          # own key only, unless context admin
DELETE /api/v1/{context_id}/keys/{name} # own key only, unless context admin
POST /api/v1/{context_id}/keys/{name}/rotate
```

**`GET /me`** returns principal identity, grants, effective grants, and delegation state. **`POST /keys`** mints for the caller's own principal; optional **`grants`** only **attenuate** (narrow) — widening returns `400`. **`GET /keys`**, rotate, and delete are **per-key**: an attenuated key sees and manages only itself unless the caller holds context-wide `grant:manage`. Sibling key operations return **`404`**. Self-service mutating routes reject unbound keys and delegated callers.

Operators can disable self-mint with **`config.allow_self_service_keys: false`** or cap TTLs with **`config.max_token_ttl_seconds`** (see [Configuration](/docs/spectron/reference/configuration#key-policy)).

There is no separate `key:create` grant verb — self-mint is safe by construction because attenuation can only narrow access, and gating it would be circular (you need a key to mint a key).

## Key storage

Spectron stores the HMAC-SHA256 hash of each key in SurrealDB. The plaintext is never persisted. Authentication on each request hashes the presented key and compares it to the stored hash.

Because keys are hashed on storage, you cannot retrieve a key's value after creation. Treat key creation responses like you would treat newly generated secrets: copy the value immediately to a secrets manager or environment variable.

## Key rotation

Spectron supports **in-place rotation** — swap the secret while keeping the same key id, principal binding, and grants:

```http
POST /api/v1/contexts/{context_id}/keys/{key_name}/rotate?ttl_seconds=2592000
Authorization: Bearer <management-key>
```

The response includes the new secret (shown once). The old secret stops validating immediately; there is no grace-period overlap.

| Query param | Behaviour |
| --- | --- |
| `ttl_seconds` omitted | Inherit the key’s current expiry |
| `ttl_seconds=N` | Reset expiry to now + N seconds |

```bash
spectrond keys rotate ctx_acme primary --expires-in 2592000
```

### Manual rotation (create + delete)

To change principal binding or grants, mint a new key and retire the old one:

1. Mint a new key against the same principal.
2. Update all callers to use the new key.
3. Verify the old key is no longer in use — check `lastUsedAt` on the self-service key listing, or traces for activity attributed to that principal.
4. Delete the old key.

```python
# Step 1: Mint the replacement, bound to a principal
POST /api/v1/contexts/ctx_acme/principals/planner/keys/planner-agent-v2
{ "grants": ["memory:write"] }

# Step 3: List the Context's keys (id, name, grants)
GET /api/v1/contexts/ctx_acme/keys

# Step 4: Delete the old key
DELETE /api/v1/contexts/ctx_acme/keys/planner-agent-v1
```

> [!NOTE]
> Keys are minted **against a principal** — the principal id is part of the path.
> There is no per-key detail endpoint and no last-used tracking: `GET /keys`
> returns `id`, `name`, and `grants` only. Attribute activity to a principal
> through traces rather than through the key record.

Deletion is immediate. Any in-flight requests using the deleted key will fail on their next API call.

## Attenuation

There is no key-minting chain: a key cannot mint another key, and there is no
`created_by` link between keys. Minting is a control-plane operation that requires
a management key.

What does exist is **attenuation**. A key is bound to a principal and inherits
that principal's grants; the optional `grants` body on mint can only narrow them.
A key can never hold a grant its principal lacks, and no request can widen its own
authority.

```http
POST /api/v1/contexts/ctx_acme/principals/planner/keys/tool-search?ttl_seconds=2592000
{ "grants": [ { "path": "org/acme/agent/planner/tool/search", "verbs": ["memory:read"] } ] }
```

If the requested grants are not a subset of the principal's, the mint is rejected.

To give a component narrower authority than any existing principal, create a
principal with exactly the grants it needs and mint against that.

### Use cases

- **Least privilege** — a principal per component, granted only the paths it needs.
- **Time-bounded access** — `ttl_seconds` on mint for contractors or short-lived jobs.
- **Per-tool separation** — a principal per tool, so traces attribute activity to the tool.

## Expiry

Expiry is set at mint or rotate time as a **TTL in seconds**, not as an absolute
timestamp: `?ttl_seconds=` on the API, `--expires-in` on the CLI. Omit it and the
key never expires. After the TTL elapses the key stops validating.

```bash
spectrond keys create ctx_acme temp-contractor \
  --principal contractor \
  --expires-in 2592000 \
  --url "$SPECTRON_MANAGEMENT_GRPC_URL" \
  --api-key "$SPECTRON_MANAGEMENT_API_KEY"
```

There is no expiry status on the key record and no automatic cleanup — `GET /keys`
returns `id`, `name`, and `grants` only. Delete keys you no longer need.

## Acting on behalf of another principal

Some deployments need one agent to read or write memory **for** another principal — for example a supervisor orchestrator calling tools on a user’s behalf. Pass the target principal on each request:

```http
X-Spectron-On-Behalf-Of: principal_01hw…
```

Rules:

- **Depth 1 only** — you cannot chain delegation headers.
- **Intersected grants** — effective authority is the intersection of the caller’s key, the caller’s grants, and the target principal’s grants. Delegation **narrows** access; it never widens it.
- **Recorded on traces** — reconciliation traces include both the acting principal and the `on_behalf_of` target when present.

See [REST API](/docs/spectron/reference/rest-api#authentication) for the header on end-user routes.

## Revocation

To immediately invalidate a key, delete it:

```http
DELETE /api/v1/contexts/ctx_acme/keys/planner-agent-v1
```

Deletion is hard and immediate, and it is the only way to withdraw a key — there
is no soft revocation, no `revoked_at`, and no revoked status. To retire a key
while keeping the audit trail, rotate it instead, which issues a new secret
against the same key record:

```http
POST /api/v1/contexts/ctx_acme/keys/planner-agent-v1/rotate
```

## What a key record holds

Two endpoints list keys, and they return different views.

**Management** — `GET /api/v1/contexts/{context_id}/keys`:

| Field | Description |
| --- | --- |
| `id` | Unique key identifier |
| `name` | Human-readable label, unique within the Context |
| `grants` | The `{path, verbs}` pairs this key enforces |

**Self-service** — `GET /api/v1/{context_id}/keys`, for keys a principal manages
for itself:

| Field | Description |
| --- | --- |
| `id`, `name`, `grants` | As above |
| `createdAt` | When the key was minted |
| `lastUsedAt` | Most recent successful validation |
| `validUntil` | Expiry, or null when the key never expires |

`lastUsedAt` is derived from an append-only key-use log rather than written to the
key row, and it is **throttled to at most one entry per key per minute** — treat it
as "recently active", not as a per-request audit trail. Per-call detail lives in
traces and OTel spans.

Neither view carries `created_by`, `revoked_at`, or a `status` field: there is no
minting chain and no soft revocation.
