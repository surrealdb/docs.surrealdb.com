# Principals

A principal is the scope and permission identity inside a Context. Every data-plane
API key binds to exactly one principal and enforces that principal's grants.

Two things describe a principal, and only one of them controls access:

- **`kind`** — what the principal *is*: `human`, `agent`, `service`, or `unknown`.
  This drives trust priors and audit attribution. It never grants or denies
  anything.
- **`grants`** — what the principal *may do, and where*. This is the whole of the
  access decision.

## Principal kinds

| Kind | Description |
| --- | --- |
| `human` | A person acting through the API. |
| `agent` | An autonomous agent. The default when minting. |
| `service` | A background service or scheduled job. |
| `unknown` | Kind not recorded — used for pre-principal legacy keys. |

## Grants

Grants are a **per-verb map**: each key is a verb, each value the list of scope
patterns that verb is allowed on. A pattern is either an exact node
(`org/acme/product/ipad`) or a subtree (`org/acme/*`, or `/*` for everything).

```json
{
  "memory:read": ["org/acme/*"],
  "memory:write": ["org/acme/agent/planner"],
  "scope:read": ["org/acme/*"]
}
```

That principal can read anywhere under `org/acme`, but can only write beneath its
own agent node.

### The seven verbs

| Verb | Authorises |
| --- | --- |
| `memory:read` | Read facts and documents whose scope is in the granted region — recall, query, chat, document reads. |
| `memory:write` | Write knowledge at an existing node in the region: record facts and ingest documents. |
| `memory:forget` | Erase knowledge in the region — facts, derived rows, and document originals. Irreversible. |
| `scope:read` | Browse the scope vocabulary and read node metadata over the region. |
| `scope:create` | Register new scope nodes under the region. |
| `scope:delete` | Tombstone scope nodes in the region. The vocabulary node is retired; facts are kept. |
| `grant:manage` | Administer principals and their grants in the region: list, grant, revoke, and inspect effective access. |

`GET /api/v1/verbs` on the management API returns this catalogue with
descriptions, for rendering grant pickers and validating verb arrays before a
mint.

## Effective authority

A request's authority is the intersection of three things: the key's own grants
(which may attenuate its principal's), the principal's grants, and — when the
`X-Spectron-On-Behalf-Of` header is present — the target principal's grants.
Nothing in that chain can widen access.

To see what a principal actually holds at a given path:

```http
GET /api/v1/{context_id}/principals/{principal_id}/effective?path=org/acme/user/alice
```

This is an end-user route, not a management one. `path` is required; the response
is the resolved verb list at that path. Pass `asOf` for a historical view of the
grants.

### Session write access

When a caller pins an existing **`session_id`** on **`/facts`**, **`/facts/batch`**,
or **`/chat`**, Spectron checks that the session's scope lies within the caller's
`memory:write` region. Guessing another principal's session id does not grant write
access. See [Creating sessions](/docs/spectron/agent-memory/sessions/creating-sessions#session-write-access).

## The management plane

Context provisioning, principal creation, and key minting run on the **management
API**, authenticated with a deployment-level management key rather than a
principal-bound Context key. A management key is not a principal and has no
grants — it sits outside the scope model entirely.

Management keys are for operators and provisioning pipelines. Application agents
must never hold one. A management key for one deployment cannot reach another
deployment (separate binary + SurrealDB).

## Creating principals

Principals are created on the **management API**. A data-plane Context key cannot mint new principals.

**CLI:**

```bash
spectrond principals create demo "Planner bot" \
  --kind agent \
  --grant memory:read=team/eng \
  --grant memory:write=team/eng \
  --url "$SPECTRON_MANAGEMENT_GRPC_URL" \
  --api-key "$SPECTRON_MANAGEMENT_API_KEY"
```

The two binaries read different URL variables: `spectrond` takes the management
gRPC endpoint (`SPECTRON_MANAGEMENT_GRPC_URL`), the `spectron` thin client takes
the management HTTP API (`SPECTRON_MANAGEMENT_URL`).

```bash
# thin client — reads SPECTRON_MANAGEMENT_URL, SPECTRON_MANAGEMENT_API_KEY, SPECTRON_CONTEXT_ID
spectron principals create "Planner bot" --kind agent -c demo \
  --grant memory:read=team/eng --grant memory:write=team/eng
```

Flags: `--kind` (`human` | `agent` | `service` | `unknown`, default `agent`), repeatable `--grant <noun>:<verb>=<scope-pattern>`, optional `--external-id` for idempotent create-or-get. The server returns `{"id": "…"}` — mint a data-plane key for that principal via the management API.

**HTTP:**

```http
POST /api/v1/contexts/{context_id}/principals
Authorization: Bearer <management-key>
Content-Type: application/json

{"display_name": "Planner bot", "kind": "agent"}
```

See [Management API — principals](/docs/spectron/reference/management-api#principals) for grants and key minting.

## Viewing key metadata

You can list a Context's keys and their grants without exposing any secret:

```bash
curl -s https://spectron.example.com/api/v1/contexts/acme-prod/keys \
  -H "Authorization: Bearer $SPECTRON_MANAGEMENT_API_KEY"
```

```json
[
  {
    "id": "key_01hw",
    "name": "planner-agent",
    "grants": {
      "memory:read": ["org/acme/*"],
      "memory:write": ["org/acme/agent/planner"]
    }
  },
  {
    "id": "key_01hx",
    "name": "ops-supervisor",
    "grants": {
      "memory:read": ["org/acme/*"],
      "memory:forget": ["org/acme/*"]
    }
  }
]
```

`grants` is absent on a key that inherits its principal's grants without
attenuation. The management listing carries `id`, `name`, and `grants` only — see
[API keys and delegation](/docs/spectron/self-hosting/security/api-keys-and-delegation#what-a-key-record-holds)
for the self-service view, which adds `createdAt`, `lastUsedAt`, and `validUntil`.
