# RPC protocol

The RPC protocol allows for network protocol agnostic communication with SurrealDB. It is used internally by our client SDKs, and is served over WebSocket, HTTP and, from 3.3.0, [gRPC](#grpc-transport). Combined with the [CBOR protocol](./cbor) specification, the RPC protocol provides a fully type-safe and efficient way to interact with SurrealDB over the network.

## Session variables

SurrealDB's session variables hold session-specific data. They act as temporary storage tied to a user's active connection, for tasks such as maintaining application state, storing user preferences, or holding temporary data relevant only to the current session.

Session variables are strictly confined to the individual connection, so one user's session data remains private and does not interfere with other connections.

You can interact with session variables in the following ways:

1.  **Explicit Session-Wide Management:**
    *   Use the [`let`](#let) method to define a new variable or update an existing one within the current session. This variable will persist for the duration of the connection.
    *   Use the [`unset`](#unset) method to remove a previously defined variable from the session.
    *   The [`reset`](#reset) method, in addition to its other functions, clears *all* currently defined session variables, restoring the session's variable state.

2.  **Implicit Request-Scoped Management:** 
    *   Methods [`query`](#query), [`select`](#select), [`insert`](#insert), [`create`](#create), [`upsert`](#upsert), [`update`](#update), [`relate`](#relate), and [`delete`](#delete), accept an optional `vars` parameter. This parameter is an object containing key-value pairs, where each key represents the variable name (without the leading `$`) and the value is the data to be assigned.
    *   Variables passed via this parameter are defined *only* for the execution context of that specific method call. They temporarily override any session-wide variable with the same name for that request but do not permanently alter the session state. These variables are automatically discarded once the method execution completes.

To use a session variable within a query or method, prefix its name with a dollar sign (`$`), for example, `$user_id`.

## Message size limits

How much a single RPC call may carry depends on the transport it arrives over.

| Transport | Default limit | Environment variable |
| --------- | ------------- | -------------------- |
| WebSocket `/rpc` | 128 MiB per message | `SURREAL_WEBSOCKET_MAX_MESSAGE_SIZE` |
| HTTP `POST /rpc` | 4 MiB per request body | `SURREAL_HTTP_MAX_RPC_BODY_SIZE` |
| gRPC <Since v="v3.3.0" /> | The HTTP `/rpc` limit, so 4 MiB per message unless that is raised, in each direction | `SURREAL_GRPC_MAX_MESSAGE_SIZE` |

The WebSocket ceiling is roughly thirty times the HTTP one, which is why the SDKs default to the WebSocket engine. If a payload is rejected over HTTP, moving the same call onto a WebSocket connection is usually enough.

### Server and client limits

The values above are what the **server** accepts. An SDK may also enforce its own limit on **outgoing** messages, and that limit is applied before anything reaches the network. The effective ceiling is therefore whichever of the two is lower.

The Rust SDK defaults to 64 MiB per message. Sending more than that produces a `Message too long` error from the client itself, not a rejection from the server. The limit is configurable:

```rust
use surrealdb::engine::remote::ws::Ws;
use surrealdb::opt::{Config, WebsocketConfig};
use surrealdb::Surreal;

let websocket = WebsocketConfig::new().max_message_size(128 << 20); // 128 MiB
let config = Config::new().websocket(websocket)?;
let db = Surreal::new::<Ws>(("127.0.0.1:8000", config)).await?;
```

Raising a client limit above the server's ceiling does not help, as the server still rejects the message. Raise both in this case, or keep messages under the lower of the two.

For request bodies on the other HTTP endpoints, see [Request size limits](/docs/reference/rest-api/http-protocol#request-size-limits).

## gRPC transport

<Since v="v3.3.0" />

The server also serves the RPC protocol over gRPC, as the `surrealdb.protocol.rpc.v1.SurrealDBService` service defined in the [surrealdb-protocol](https://github.com/surrealdb/surrealdb-protocol) repository. gRPC shares the listener, port and TLS configuration of the HTTP and WebSocket endpoints: it runs over HTTP/2, which the server negotiates by the connection preface on a plaintext port and by ALPN on a TLS one, so no second port is configured. gRPC calls pass through the same middleware as the other endpoints, including the startup gate and the handling of the `Authorization` header. Denying the `rpc` [HTTP route](/docs/learn/security/authorization/capabilities#http-route-names) closes gRPC along with both `/rpc` endpoints, and the [RPC method names](/docs/learn/security/authorization/capabilities#rpc-method-names) restrict gRPC calls as they do WebSocket ones.

Clients connect with a `grpc://` address, or `grpcs://` for TLS. The [Rust SDK](/docs/reference/rust/methods/connect#connecting-over-grpc) supports both through its `protocol-grpc` feature, and [`surreal sql --endpoint`](/docs/reference/cli/surrealdb-cli/commands/sql#capabilities-and-remote-connections) accepts them too.

A few details:

- `SURREAL_GRPC_MAX_MESSAGE_SIZE` limits every message in both directions. It defaults to the value of `SURREAL_HTTP_MAX_RPC_BODY_SIZE`, and the server reports it to clients as `Limits.max_message_bytes` in the `GetCapabilities` handshake, so a client knows the limit before it sends anything.
- Compression is negotiated per client. The server accepts requests compressed with zstd or gzip, answers in whichever of the two the client lists in `grpc-accept-encoding`, and sends uncompressed messages to a client that lists neither.
- `SURREAL_GRPC_MAX_ATTACHED_SESSIONS` and `SURREAL_GRPC_NOTIFICATION_BUFFER` bound the sessions attached across all gRPC connections and the live query notifications buffered for a slow subscriber. All three variables are listed under [HTTP server config](/docs/reference/cli/surrealdb-cli/environment-variables#http-server-config).

### Example usage

**Inserting a Relation into a Specified Table**

```json title="Request"
{
    "id": 1,
    "method": "insert_relation",
    "params": [
        "likes",                   // (relation table)
        {                          // data
            "in": "user:alice",
            "out": "post:123",
            "since": "2024-09-15T12:34:56Z"
        }
    ]
}
```

```json title="Response"
{
    "id": 1,
    "result": {
        "id": "likes:user:alice:post:123",
        "in": "user:alice",
        "out": "post:123",
        "since": "2024-09-15T12:34:56Z"
    }
}
```

**Inserting a Relation Without Specifying the Table**

If you do not specify the `table` parameter (i.e., set it to `null` or `none`), the relation table is inferred from the `id` field within the `data`.

```json title="Request"
{
    "id": 2,
    "method": "insert_relation",
    "params": [
        null,                      // relation table is null
        {                          // data
            "id": "follows:user:alice:user:bob",
            "in": "user:alice",
            "out": "user:bob",
            "since": "2024-09-15T12:34:56Z"
        }
    ]
}
```

```json title="Response"
{
    "id": 2,
    "result": {
        "id": "follows:user:alice:user:bob",
        "in": "user:alice",
        "out": "user:bob",
        "since": "2024-09-15T12:34:56Z"
    }
}
```

### Notes

- **`table` parameter:**
  - Specifies the relation table into which the new relation record will be inserted.
  - If `table` is `null` or `none`, the method expects the `data` to contain an `id` from which it can infer the relation table.

- **`data` parameter:**
  - Must include at least the `in` and `out` fields, representing the starting and ending points of the relation.
  - Can include additional fields to store more information within the relation.

- **Relation IDs:**
  - If an `id` is provided in the `data`, it will be used as the identifier for the new relation record.
  - If no `id` is provided, the system may generate one based on the `table`, `in`, and `out` fields.

- **Single vs. multiple inserts:**
  - The method primarily handles single relation inserts.
  - The `one` variable in the code determines if the `table` parameter refers to a single item.

### Error handling

- **Invalid parameters:**
  - If you provide fewer than two parameters or incorrect parameter types, you will receive an `InvalidParams` error.
  - The method expects exactly two parameters: `table` and `data`.

**Example of invalid parameters:**

```json title="Request with missing parameters"
{
    "id": 3,
    "method": "insert_relation",
    "params": [
        "likes"  // Missing the data parameter
    ]
}
```

```json title="Response"
{
    "id": 3,
    "error": {
        "cause": null,
        "code": -32603,
        "details": { "kind": "InvalidParams" },
        "kind": "Validation",
        "message": "Expected (what, data)"
    }
}
```

See [Errors](/docs/reference/rest-api/errors) for the full error shape, the list of kinds, and the wire codes.

### Best practices

- **Include `in` and `out` Fields:**
  - Always provide the `in` and `out` fields in your `data` to define the relation endpoints.

- **Specifying the Relation Table:**
  - If possible, specify the `table` parameter to clearly indicate the relation table.
  - If not specified, ensure that the `id` in `data` correctly reflects the desired relation table.

- **Providing an `id` in `data`:**
  - If you want to control the `id` of the relation, include it in the `data`.
  - This is especially important when `table` is `null` or `none`.

### Additional examples

**Inserting a Relation with Auto-Generated ID**

```json title="Request"
{
    "id": 4,
    "method": "insert_relation",
    "params": [
        "friendship",              // table (relation table)
        {                          // data
            "in": "user:alice",
            "out": "user:bob",
            "since": "2024-09-15"
        }
    ]
}
```

```json title="Response"
{
    "id": 4,
    "result": {
        "id": "friendship:user:alice:user:bob",
        "in": "user:alice",
        "out": "user:bob",
        "since": "2024-09-15"
    }
}
```

**Notes:**

- The `id` is generated based on the `table`, `in`, and `out` fields.
- The relation is inserted into the `friendship` table.

## `query_stream` <label label="websocket only" /> {#query_stream}

<Since v="v3.3.0" />

This method runs a query in the same way as [`query`](#query), but answers with a sequence of frames sent while the query runs instead of one response at the end, so the first records reach the client before the last statement has finished. Only the WebSocket `/rpc` endpoint serves it, and HTTP `POST /rpc` reports `Method not found`. Neither the Rust nor the JavaScript SDK calls this method over WebSocket. The Rust SDK's [`.stream_items()`](/docs/reference/rust/methods/query#stream-items) streams incrementally on the embedded engines and over gRPC, and the JavaScript SDK's [streaming query responses](/docs/reference/javascript/concepts/executing-queries#streaming-query-responses) do so on the embedded Node.js and browser engines, which produce the same frames locally.

```json title="Method syntax"
query_stream [ sql, vars ]
```

### Parameters
<table>
    <thead>
        <tr>
            <th colspan="2">Parameter</th>
            <th colspan="2">Description</th>
        </tr>
    </thead>
    <tbody>
        <tr>
            <td colspan="2" scope="row" data-label="Parameter">
                <code>sql</code>
                <label label="required" />
            </td>
            <td colspan="2" scope="row" data-label="Description">
                The query to execute against SurrealDB
            </td>
        </tr>
        <tr>
            <td colspan="2" scope="row" data-label="Parameter">
                <code>vars</code>
               <label label="optional" />
            </td>
            <td colspan="2" scope="row" data-label="Description">
                An object that maps variable names to the values the query uses
            </td>
        </tr>
    </tbody>
</table>

The request needs an `id`, because every frame carries it, and one without an `id` is refused. A second `query_stream` that reuses the `id` of a stream still running on the connection is refused with `A streaming query with this request id is already in progress`. A request that carries a `txn` runs inside that client transaction, and the client waits for the `end` frame before it sends `commit`, because a `commit` that arrives while the stream is running ends the transaction the stream is still using. A failure before execution starts, such as a parse error or a denied capability, is answered with an ordinary error response and no frames.

### Frames

Each frame arrives as an ordinary response carrying the request's `id`, and its `result` is an object whose `stream` field names the frame type:

| `stream` | Fields | Meaning |
| --- | --- | --- |
| `begin` | `statements`, `version` | The stream is open. `statements` is an upper bound, because control flow such as a `RETURN` can skip the rest of a block, so the number of statements is best counted from `finished` frames. `version` is the revision of the frame protocol, currently `1`. |
| `rows` | `index`, `values` | Records produced by statement `index`, with more possibly to follow. A statement's first `rows` frame carries up to 16 records, and each later one up to twice as many as the one before, to a limit of 256. |
| `value` | `index`, `value` | The single value of a statement that does not return a list, such as `RETURN 1 + 2`. A statement sends `rows` frames or one `value` frame, never both. |
| `finished` | `index`, `time`, `type`, `single`, `error` | Statement `index` is final. `single` is `true` when its value is one value rather than a list, `type` is `"live"` or `"kill"` for those statements and `null` for any other, and `error` is present only when the statement failed. |
| `end` | `results`, `time`, `error` | The stream is complete, and nothing follows. `results` is the number of `finished` frames delivered, and `error` is present only when the stream did not complete normally. |

Records are provisional until their statement's `finished` frame arrives:

- A `finished` frame with an `error` retracts every record already sent for that statement.
- An `end` frame with an `error` retracts every statement that has no `finished` frame, while the statements that finished stand. This covers a timeout, a [`query_cancel`](#query_cancel), a transaction that could not commit, and a stream the server stopped because its frames could not be delivered, which reports `The streaming query was stopped before it completed`.
- An `end` error can also name `LIVE SELECT` subscriptions that were discarded because their session ended, since their statements had already finished and cannot be retracted.

New frame types and fields can be added without changing `version`, so a client ignores a `stream` value or a field it does not recognise. Every `finished` frame carries `single`, because a statement that sent no `rows` or `value` frame has no other way to say whether its value is an empty list or a single value.

### Limits

- `SURREAL_WEBSOCKET_MAX_CONCURRENT_STREAMS`, 32 by default, limits how many streams one connection runs at once. A request over the limit is refused with `Too many concurrent streaming queries` rather than queued.
- `SURREAL_WEBSOCKET_STREAM_SEND_TIMEOUT`, 30 seconds by default, stops a stream that has waited that long to send one frame, which is what happens when the client stops reading. It applies whether or not `--query-timeout` is set.
- `--query-timeout`, when set, limits the whole stream, including the time spent waiting to send frames.
- `query_stream` is an [RPC method capability](/docs/learn/security/authorization/capabilities#rpc-method-names) of its own, and the query runs through the `query` method's gate as well, so denying either method denies streaming.

Both environment variables are listed under [WebSocket config](/docs/reference/cli/surrealdb-cli/environment-variables#websocket-config).

### Example usage
```json title="Request"
{
    "id": 1,
    "method": "query_stream",
    "params": [
        "SELECT * FROM person; RETURN 1 + 2;"
    ]
}
```

The server sends these frames in order, one message each:

```json title="Response"
{ "id": 1, "result": { "statements": 2, "stream": "begin", "version": 1 } }
{ "id": 1, "result": { "index": 0, "stream": "rows", "values": [{ "id": "person:jane", "name": "Jane" }, { "id": "person:john", "name": "John" }] } }
{ "id": 1, "result": { "index": 0, "single": false, "stream": "finished", "time": "215.042µs", "type": null } }
{ "id": 1, "result": { "index": 1, "stream": "value", "value": 3 } }
{ "id": 1, "result": { "index": 1, "single": true, "stream": "finished", "time": "18.5µs", "type": null } }
{ "id": 1, "result": { "results": 2, "stream": "end", "time": "402.917µs" } }
```

                <code>DB</code>
                <label label="required" />
            </td>
            <td colspan="2" scope="row" data-label="Description">
                Sets the selected Database for queries
            </td>
        </tr>
    </tbody>
</table>

### Accepted values

For either the namespace or database, a string will change the value, `null` will unset the value, and `none` will cause the value to not be affected.

### Example usage

```json title="Request"
{
    "id": 1,
    "method": "use",
    "params": [ "surrealdb", "docs" ]
}
```

```json title="Response"
{
    "id": 1,
    "result": null
}
```

```surql title="Example Combinations"
[none, none]     -- Won't change ns or db
["test", none]   -- Change ns to test
[none, "test"]   -- Change db to test
["test", "test"] -- Change ns and db to test

[none, null]     -- Will only unset the database
[null, none]     -- Will throw an error, you cannot unset only the database
[null, null]     -- Will unset both ns and db
["test", null]   -- Change ns to test and unset db
```

## `version`

This method returns version information about the database/server.

```json title="Method Syntax"
version
```

### Parameters

This method does not accept any parameters.

### Example usage

```json title="Request"
{
    "id": 1,
    "method": "version"
}
```

```json title="Response"
{
    "id": 1,
    "result": {
        "version": "3.2.0",
        "build": "abc123",
        "timestamp": "2024-09-15T12:34:56Z"
    }
}
```

### Notes

- **Parameters:** Providing any parameters will result in an `InvalidParams` error.
- **Result Fields:**
  - `version`: The version number of the database/server.
  - `build`: The build identifier.
  - `timestamp`: The timestamp when the version was built or released.


> [!NOTE]
> The actual values in the response will depend on your specific database/server instance.
