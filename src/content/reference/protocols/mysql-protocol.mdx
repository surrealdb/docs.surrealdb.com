# MySQL wire protocol

<Since v="v4.0.0" />

The MySQL wire protocol listener lets a MySQL client, such as the `mysql` command-line client, JDBC through Connector/J, or the Python, Go, Node.js and PHP drivers, connect to SurrealDB on a TCP port and run queries. A connection runs the MySQL dialect of SQL against SurrealDB tables, and can switch to ISO GQL. Queries written for MySQL 8.0 run against SurrealDB tables. This page covers how to enable the listener, how to connect, and where the MySQL dialect differs from MySQL. The [Postgres wire protocol](/docs/reference/protocols/postgres-protocol) page covers the equivalent listener for PostgreSQL clients.

## Enable the listener

The listener is included in the official binaries, installers and Docker images, and is off until you give it an address. Pass `--mysql-bind` to [`surreal db start`](/docs/reference/cli/db/commands/start) to start it, on a separate address from the HTTP server:

```bash
surreal db start --user root --pass secret \
  --mysql-bind 127.0.0.1:3306 \
  memory
```

The environment variable equivalent is `SURREAL_MYSQL_BIND`:

<Tabs syncKey="shell">

<TabItem label="Bash">
```bash
export SURREAL_MYSQL_BIND=127.0.0.1:3306
surreal db start --user root --pass secret memory
```
</TabItem>

<TabItem label="PowerShell">
```powershell
$env:SURREAL_MYSQL_BIND = "127.0.0.1:3306"
surreal db start --user root --pass secret memory
```
</TabItem>
</Tabs>

The server logs the address when the listener starts. A server started without `--mysql-bind` or `SURREAL_MYSQL_BIND` does not listen for MySQL connections. The [`mysql` route capability](/docs/learn/security/authorization/capabilities#http-route-names) also controls the listener: with `--deny-http mysql`, the server refuses each connection.

## Connect with `mysql`

```bash
mysql -h 127.0.0.1 -P 3306 -u root -psecret -D main/main \
  --get-server-public-key
```

On a plaintext connection, pass `--get-server-public-key` as above. The client then asks the server for its RSA public key and sends the password encrypted with it, as the default `caching_sha2_password` method requires over plaintext. Without the option, the `mysql` client fails with `ERROR 2061: Couldn't read RSA public key from server`. Over [TLS](#tls), the option is not needed.

The database name selects the namespace and the database as `ns/db`, with a single slash, in the same way as `Surreal-NS` and `Surreal-DB` on HTTP. `USE ns/db` changes both on an open connection.

The server announces itself as MySQL `8.0.35-SurrealDB`, and `SELECT VERSION()` and `SELECT @@version` both return that string.

### Authentication

A client signs in as a system user, such as the root user or a [database user](/docs/reference/query-language/statements/define/user) with a password. The server accepts the `caching_sha2_password`, `mysql_native_password` and `mysql_clear_password` authentication methods:

- `caching_sha2_password` is the default of MySQL 8 clients. It works over TLS, and over a plaintext connection from any address with the server's RSA public key, which the server generates when it first needs it.
- `mysql_native_password` serves older clients and drivers. The server verifies it directly only for a user who signed in earlier since the server started. Otherwise the server asks the client to switch to `mysql_clear_password`, so the client must allow clear-text passwords, as the `mysql` client 8.x does with `--enable-cleartext-plugin`.
- `mysql_clear_password` sends the password as clear text.

A sign-in that sends the password as clear text needs a TLS connection or a loopback address, such as `127.0.0.1`, and is refused with error `1045` `Authentication requires an encrypted (TLS) connection or loopback` otherwise.

### TLS

The listener uses the certificate and key that `--web-crt` and `--web-key` give the HTTP server. Without them, the listener serves plaintext connections and the server logs a warning. TLS is recommended for any connection that does not come from the same host.

### Client tools

`mysqladmin` (`ping`, `version`, `status` and `variables`) and `mysqlslap` run against the listener. `mysqldump` of a table runs to completion when given `--no-tablespaces` and `--skip-lock-tables`, and writes the rows of the table as `INSERT` statements. The structure section of the dump holds the SurrealQL definition that `SHOW CREATE TABLE` returns, so a MySQL server cannot replay it. Pass `--no-create-info` to dump the rows only.

## Query languages

A new connection runs the MySQL dialect. `SET dialect = 'gql'` switches an open connection to [ISO GQL](/docs/learn/querying/gql/overview), and `SET dialect = 'mysql'` (or `'sql'`) switches it back.

```sql
CREATE TABLE person (id INT PRIMARY KEY, name TEXT, age INT);
INSERT INTO person (id, name, age) VALUES (1, 'Ada', 36), (2, 'Bob', 28);
SELECT name, age FROM person WHERE age > 30 ORDER BY name;
```

SurrealQL and the PostgreSQL dialect are not available over this listener: `SET dialect = 'surrealql'` and `SET dialect = 'pgsql'` fail with error `1045`. Send SurrealQL over [HTTP](/docs/reference/protocols/http-protocol), [RPC](/docs/reference/protocols/rpc-protocol) or an SDK, and PostgreSQL queries over the [Postgres wire protocol](/docs/reference/protocols/postgres-protocol).

In the MySQL dialect, every record ID in a result is sent as its key, as a SQL client expects a primary key to be: `person:1` is sent as `1`. The tables are SurrealDB tables, so a SurrealQL query over HTTP or an SDK reads the same records.

## The MySQL dialect

The MySQL dialect parses MySQL 8.0 and 8.4 syntax, and runs `SELECT` with joins, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY` and `LIMIT`, aggregate functions, non-recursive common table expressions (`WITH`), `INSERT` (including `INSERT ... ON DUPLICATE KEY UPDATE`), `UPDATE`, `DELETE`, `CREATE TABLE`, `DROP TABLE`, `TRUNCATE` and the statements that drivers send while they connect. From SurrealDB 4.1, it also runs `ALTER TABLE`, `CREATE INDEX`, `DROP INDEX`, `CREATE VIEW`, `DROP VIEW`, `CREATE DATABASE` and `DROP DATABASE`, as described under [Schema changes](#schema-changes). Prepared statements, statements sent several at a time, window functions, `START TRANSACTION`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` and `SET autocommit` are supported. From SurrealDB 4.1, a statement over a table in another database runs, as described under [Tables in another database](#tables-in-another-database). Before 4.1, it is refused.

User variables and prepared statements in SQL work as in MySQL. `SET @a = expr` keeps the value of the expression for the connection, a later `@a` reads it, and a variable that was never set reads as `NULL`. `PREPARE name FROM 'statement'` (or `FROM @variable`), `EXECUTE name [USING @a, ...]` and `DEALLOCATE PREPARE name` prepare and run a statement, and `EXECUTE` of an unknown name fails with `1243`. `COM_RESET_CONNECTION` clears both.

A column without an alias is named by its expression exactly as it was written, as MySQL names it, so `SELECT COUNT(*), MAX(k) + 1` answers the columns `COUNT(*)` and `MAX(k) + 1`. A name is cut at 255 bytes.

From SurrealDB 4.1, a column name matches the column that the table declares in any letter case, as in MySQL, so `parentid` and `PARENTID` read, write, filter, join, sort and group the column declared as `parentId`. A name that matches no declared column fails with `1054`. Also from 4.1, `BINARY expr` reads as `CAST(expr AS BINARY)`, so it compares and sorts text by its bytes, as the schema reader of Prisma's MySQL connector uses it.

Also from 4.1, a table is read under the name it was created with, as in MySQL where `lower_case_table_names` is `0`, so a table created as `Account` is read by ``SELECT id FROM `Account` `` and by `SELECT id FROM Account`, and `SELECT id FROM account` fails with `1146`. A table that declares no key has no `id` column: `SELECT *` and `information_schema.columns` list only the columns the table declares, and naming `id` fails with `1054`.

`CREATE TABLE` defines a field of a [sized number](/docs/reference/query-language/language-primitives/data-types/numbers#sized-numbers) type for each number column: `TINYINT` is `i8`, `SMALLINT` is `i16`, `MEDIUMINT` and `INT` are `i32`, `BIGINT` is `int`, `INT UNSIGNED` is `u32`, `FLOAT` is `f32` and `DOUBLE` is `float`. A value out of range for the column, such as `300` for a `TINYINT` or `-1` for an `INT UNSIGNED`, is refused with `1366`.

`CREATE TABLE` also records the type of each column as the field's [`SQL TYPE`](/docs/reference/query-language/statements/define/field#declaring-a-sql-type), and every write is checked against it, so a value too long for a `VARCHAR(n)` column is refused with `1406`. A `DECIMAL` column with a precision above 28 defines a [`bigdecimal`](/docs/reference/query-language/language-primitives/data-types/numbers#big-decimal-numbers) field. An `ENUM('s','m','l')` column defines a field of the [inline enum](/docs/reference/query-language/language-primitives/data-types/named-types#inline-enums) `enum<'s', 'm', 'l'>`, which refuses any other value with `1366` and orders its values in the order the column lists them.

From SurrealDB 4.1, a value written to a column is read as the type of the column, as MySQL reads what it assigns. Text such as `'2025-01-01 10:20:30.123'` is a valid value for a `DATETIME(3)` column, the text of a datetime written to a `DATE` column gives its date, `1` and `0` are valid for a `BOOLEAN` column (any other number, such as `2`, is refused with `1366`, where MySQL stores it), `TRUE` is valid for an integer column, and text such as `'12.5'` or `'8'` is valid for a `DECIMAL` or an unsigned integer column. A value written to a `TIME` column, as a literal or as a prepared statement parameter, is read as the time it spells: `'14:37:36'`, a negative time such as `'-838:59:59'`, a day count as in `'1 02:03:04'` (26:03:04), a short form such as `'2:3'` (02:03:00), or a number of `HHMMSS` digits such as `123456` (12:34:56). Text that is no time, and a number that is no time, such as `126000`, are refused with `1366`.

From SurrealDB 4.1, a JSON document is printed as MySQL prints it: `[1, "x"]` and `{"a": 1}`, with a space after each comma and each colon, object keys listed shortest first, and a date, time or datetime inside the document as a string with six fractional digits, such as `"2025-01-01 10:00:00.000000"`. This applies to a `JSON` column and to the result of functions such as `JSON_ARRAY` and `JSON_OBJECT`.

A word that MySQL does not reserve, such as `collation`, `status`, `value`, `offset`, `user`, `mode`, `start` or `work`, names a column without quotes in an expression from SurrealDB 4.1, as in `SELECT collation AS column_order FROM t`. A word that MySQL reserves, such as `select`, is still a syntax error.

The implemented functions are tested against the answers that MySQL 8.4 gives for the same arguments, and include the keyword forms `EXTRACT(YEAR FROM d)`, `POSITION('b' IN s)` and `SUBSTRING(s FROM 2 FOR 3)`, and `INTERVAL` arithmetic such as `DATE_ADD(d, INTERVAL 1 DAY)`. `LENGTH` counts bytes, as in MySQL. `CAST(x AS UNSIGNED)` of a constant follows MySQL as well: a negative integer wraps around to the top of the unsigned range, so `-1` becomes `18446744073709551615`, a number with a fraction is rounded first, and a number above the largest unsigned integer becomes `18446744073709551615`.

Many points behave as they do over the PostgreSQL dialect, which shares the same query planner. The [PostgreSQL dialect](/docs/reference/protocols/postgres-protocol#postgresql-sql) section describes these in more detail: tables that declare their columns, unqualified columns in a join, `t.*`, `LIKE` patterns, subqueries used as a value, window functions, and the limits on how deeply a `FROM` clause can nest. Over this listener, the failures that section describes are reported with the MySQL error numbers listed under [Error codes](#error-codes), and a `FROM` clause that nests too deeply fails with `1064`.

From SurrealDB 4.1, `LEFT JOIN`, `INNER JOIN` and `CROSS JOIN` take a `LATERAL` derived table, as in `LEFT JOIN LATERAL (SELECT COUNT(*) AS n FROM posts p WHERE p.owner_id = u.id) x ON TRUE`. The derived table reads the columns of the tables before it, and can filter, group, aggregate, sort, take a `LIMIT` and hold a `LATERAL` join of its own. This is the form that ORMs such as Drizzle send to read a one-to-many relation as a JSON array.

### Transactions and DDL

`START TRANSACTION` or `BEGIN` opens a transaction, and `SET autocommit = 0` makes each statement run in a transaction until `COMMIT`. As in MySQL, a DDL statement (`CREATE`, `ALTER`, `DROP`, `TRUNCATE` or `RENAME`) first commits the open transaction and then runs on its own, so a `ROLLBACK` does not take back a `CREATE TABLE`.

`CREATE TABLE` and `DROP TABLE` of several tables are each answered with one OK packet. If one part of the statement fails, nothing of the statement is kept, so `DROP TABLE a, missing` fails and keeps `a`.

`TRUNCATE TABLE t` and `TRUNCATE t` answer with an OK packet that reports 0 affected rows, as a plain statement, as a prepared statement and inside a batch of statements.

An `AUTO_INCREMENT` column draws its numbers from a sequence, and is `NOT NULL`. `TRUNCATE` starts the numbering again from 1, as does `CREATE TABLE` of a table that was dropped. Because `TRUNCATE` defines the sequence again, a user who may delete records but not define a sequence, such as an editor, is refused `TRUNCATE` of a table with an `AUTO_INCREMENT` column.

From SurrealDB 4.1, `SET [SESSION] TRANSACTION ISOLATION LEVEL` accepts every level MySQL has, as a plain statement and as a prepared statement, which is how Prisma's driver sends it. Without `SESSION`, the level is the level of the next transaction alone, and the statement fails with `1568` inside a transaction. With `SESSION`, it holds for every transaction of the connection until another `SET` changes it. `SET GLOBAL TRANSACTION ISOLATION LEVEL` is refused, and a level that MySQL does not have, such as `SNAPSHOT`, fails with `1064`. Before 4.1, the statement is refused with `1235`.

| Level | Runs as |
| --- | --- |
| `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ` | Snapshot isolation, which is never weaker than the level named. |
| `SERIALIZABLE` | A [serializable transaction](/docs/learn/querying/concepts-and-guides/transactions#serializable-isolation), on the storage engines that offer one. The statement is refused with `1235` on the others. |

A serializable transaction that read a row which another transaction wrote does not commit. InnoDB reaches serializability with locks instead, so where it makes the second writer wait, SurrealDB makes the first committer fail. `@@transaction_isolation` reads `REPEATABLE-READ` whatever level is set, because the variables are fixed settings, as described under [System variables](#system-variables).

### Tables in another database

<Since v="v4.1.0" />

`CREATE TABLE`, `DROP TABLE`, `SELECT`, `INSERT`, `UPDATE`, `DELETE` and `TRUNCATE` can name a table of another database in the namespace as `database.table`. The statement runs in that database, the connection stays in its own, and `DATABASE()` still returns the name of the connection's database. ORMs such as Drizzle create their test tables this way, as in `CREATE TABLE mySchema.userstest (...)`.

```sql
CREATE TABLE analytics.events (id INT PRIMARY KEY, name VARCHAR(50));
INSERT INTO analytics.events (id, name) VALUES (1, 'signup');
SELECT name FROM analytics.events;
```

These rules keep a statement from reaching a database that `USE` would not:

- The session needs the access that `USE database` needs, which the server checks before it reads the database or its schema. A session without that access gets the same refusal whether the database or the table exists or not.
- The statement runs with the session's own authentication, so the table, field and record permissions of the other database apply as they do on a connection to that database.
- With access, a database that does not exist fails with `1049`, as in MySQL. A table that does not exist fails with `1146`, and `DROP TABLE` of one with `1051`. A statement never creates a database, and `CREATE TABLE` in a missing database creates nothing.
- Every table of the statement is named with its database. A table named alone, a third database, `information_schema` and `DATABASE()` are refused, because each would read the connection's own database instead.
- The statement is the only statement of its request, so a request that holds another statement beside it fails with `1235`, and so does a prepared statement over a table of another database.
- `DROP TABLE` over tables of two databases is refused with `1235`, where MySQL drops both.

A column can be named with its database and table, as in `SELECT shop.item.id FROM item`, where the `FROM` clause names that table. A table given an alias is named by the alias alone, and a database other than the table's is no qualifier, so both fail with `1054`. The same form reads the relations of `information_schema`, as in `INFORMATION_SCHEMA.STATISTICS.TABLE_SCHEMA`.

### Schema changes

<Since v="v4.1.0" />

`ALTER TABLE` runs `ADD COLUMN`, `DROP COLUMN`, `MODIFY COLUMN`, `CHANGE COLUMN` to the same name, `ADD UNIQUE`, `ADD PRIMARY KEY`, `DROP INDEX`, and the foreign key actions described under [Foreign keys](#foreign-keys). A statement with several actions is answered once, and if one action fails, none of them is kept. A table or a column that does not exist is refused. `ALTER TABLE ... RENAME` and `CHANGE COLUMN` to a new name are refused with `1235`, because the records and their values would stay under the old name.

`CREATE TABLE` declares indexes with `INDEX` and `KEY` as well as `UNIQUE` and `PRIMARY KEY`. An index without a name takes the name of its first column, then `_2`, `_3` and so on, as MySQL names it. A `FULLTEXT` index is described under [Full-text search](#full-text-search). Two indexes of one name are refused with `1061`, an index named `PRIMARY` with `1280`, a second primary key with `1068`, a primary key over a column declared `NULL` with `1171`, and a key over a column that the table does not declare with `1072`.

`CREATE INDEX`, `CREATE UNIQUE INDEX` and `DROP INDEX ... ON t` define and remove an index. `CREATE VIEW`, `CREATE OR REPLACE VIEW` and `DROP VIEW` define, replace and remove a view over one table that stays up to date after every write to the table, as over the [PostgreSQL dialect](/docs/reference/protocols/postgres-protocol#not-yet-supported). A view over a query with `GROUP BY` is refused with `1235`. `CREATE OR REPLACE VIEW` and `DROP VIEW` of a table that is not a view are refused with `1347`, and `DROP VIEW IF EXISTS` skips such a table.

`CREATE DATABASE` (or `CREATE SCHEMA`) and `DROP DATABASE` (or `DROP SCHEMA`) define and remove a database in the namespace of the session, with its tables. `IF NOT EXISTS` and `IF EXISTS` work, and character set and collation options are accepted. Both statements need the role that [`DEFINE DATABASE`](/docs/reference/query-language/statements/define/database) needs, so a user of one database is refused them.

### Foreign keys

<Since v="v4.1.0" />

A `FOREIGN KEY` constraint, in `CREATE TABLE` or in `ALTER TABLE ... ADD FOREIGN KEY`, makes the column a [record link](/docs/reference/query-language/statements/define/field#defining-a-reference) to the other table, which a query writes and reads as the key, as over the PostgreSQL dialect. A write whose key names no record in that table fails with `1452`, and so does an `ALTER TABLE ... ADD FOREIGN KEY` over records that already name a missing key.

```sql
CREATE TABLE member (id INT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE post (id INT PRIMARY KEY, author INT NOT NULL, editor INT, FOREIGN KEY (author) REFERENCES member(id) ON DELETE CASCADE, FOREIGN KEY (editor) REFERENCES member(id) ON DELETE SET NULL);
```

`ON DELETE CASCADE` deletes the referencing records with the record they link to, and `ON DELETE SET NULL` sets the column to `NULL`. Without either, deleting a record that another record links to fails with `1451`. `ON DELETE SET DEFAULT` is refused with `1235`. From SurrealDB 4.1, every `ON UPDATE` action is accepted on such a key, because a record's key never changes and no action can run, which is why Prisma's `ON UPDATE CASCADE` on every relation works. `information_schema.referential_constraints` reports `NO ACTION` as the `update_rule` of these keys. Before 4.1, `ON UPDATE CASCADE` and `ON UPDATE SET NULL` are refused with `1235`.

A constraint keeps the name that `CONSTRAINT name` gives it, and a constraint without one is named `table_ibfk_1`, `table_ibfk_2` and so on, as in MySQL. `ALTER TABLE ... DROP FOREIGN KEY name` and `ALTER TABLE ... DROP CONSTRAINT name` remove it. A name that is not a foreign key of the table fails with `1091` in `DROP FOREIGN KEY`, and with `1235` in `DROP CONSTRAINT`. As in MySQL 8.4, `DROP CONSTRAINT IF EXISTS` does not parse.

A column's own `REFERENCES` clause, as in `parent_id INT REFERENCES parent(id)`, is read and ignored, as MySQL ignores it. These foreign keys are refused with `1235`: a key on the `id` column or on an `AUTO_INCREMENT` column, a second key on one column, and a constraint name that holds a double quote.

From SurrealDB 4.1, a key over several columns, or to a column other than `id`, is enforced as well. Its columns keep their values, and two events of the tables enforce it: the event of the child table refuses a write whose key names no row of the parent with `1452`, unless a column of the key is `NULL`, and the event of the parent table carries out `ON DELETE` and `ON UPDATE`, which take `CASCADE`, `SET NULL`, `RESTRICT` and `NO ACTION`, or refuses the change with `1451`. An index over the key columns serves both events. `SET DEFAULT` is refused with `1235` for these keys, on delete and on update.

```sql
CREATE TABLE region_code (id INT PRIMARY KEY, region INT NOT NULL, code VARCHAR(10) NOT NULL, UNIQUE KEY region_code_key (region, code));
CREATE TABLE line (id INT PRIMARY KEY, region INT, code VARCHAR(10), FOREIGN KEY (region, code) REFERENCES region_code (region, code) ON DELETE CASCADE ON UPDATE CASCADE);
```

The parent must have a unique key over exactly the referenced columns, in the order the key lists them, and a key without one is refused with `6125`. The columns of a pair must hold the same family of values, such as two integers or two texts, or the key is refused with `3780`. `information_schema.key_column_usage`, `referential_constraints` and `table_constraints` list the key, and `DROP FOREIGN KEY` and `DROP CONSTRAINT` remove it. While a key exists, these statements are refused: dropping a column it holds (`1828`) or refers to (`1829`), dropping the index it relies on (`1553`), and dropping the parent table (`3730`) unless `foreign_key_checks` is `0` or the child is dropped in the same statement.

### Timestamp columns

<Since v="v4.1.0" />

`CURRENT_TIMESTAMP(N)` and `NOW(N)` return the time cut to `N` digits, from `0` to `6`, in a query and in a column default such as `DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)`. A precision above `6` is refused with `1235`.

A `DATETIME` or `TIMESTAMP` column can declare `ON UPDATE CURRENT_TIMESTAMP` in `CREATE TABLE` and in `ALTER TABLE ... ADD COLUMN`, `MODIFY COLUMN` and `CHANGE COLUMN`, with the spellings MySQL takes. The precision of the attribute must be the precision of the column, as in `DATETIME(6) ... ON UPDATE CURRENT_TIMESTAMP(6)`, and a mismatch, or a column of another type, is refused with `1294`. The attribute is also refused with `1235` on the `id` column and on a column with a foreign key.

```sql
CREATE TABLE note (
  id INT PRIMARY KEY,
  body TEXT,
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);
```

An `UPDATE` that changes another column sets the column to the current time, for the rows it changes and no other. An update that leaves every column as it is leaves the column as it is, as in MySQL. A value the statement assigns to the column wins, whether or not another column changes, and `NULL` for a `NOT NULL` column is refused. An `INSERT` takes the default, `INSERT ... ON DUPLICATE KEY UPDATE` sets the time only when it changes the row it finds, and `REPLACE` writes a new row, which takes the default. `ALTER TABLE ... MODIFY` that does not write `ON UPDATE` removes the attribute. `information_schema.columns.extra`, `SHOW COLUMNS` and `DESCRIBE` read it back as `on update CURRENT_TIMESTAMP(n)`.

### Full-text search

<Since v="v4.1.0" />

A `FULLTEXT` index is declared in `CREATE TABLE` (`FULLTEXT KEY name (columns)`), with `CREATE FULLTEXT INDEX`, or with `ALTER TABLE ... ADD FULLTEXT`, and removed with `DROP INDEX` or `ALTER TABLE ... DROP INDEX`. An index without a name takes the name of its first column. It covers text columns only. `SHOW INDEX` lists it once, under its own name, with a row for each column and `FULLTEXT` as its type, although the engine holds one [full-text index](/docs/reference/query-language/statements/define/indexes#full-text-search-fulltext-index) with BM25 ranking for each column.

`MATCH (columns) AGAINST ('words')` is a condition in `WHERE`, and a relevance in the select list and in `ORDER BY`. The columns can be listed in any order but must be the columns of one `FULLTEXT` index, and the query must read one table. A relevance in the select list or in `ORDER BY` is refused with `1235` in a query that groups, aggregates, removes duplicates or combines queries.

```sql
CREATE TABLE article (id INT PRIMARY KEY, title VARCHAR(100), body TEXT, FULLTEXT KEY article_body (body));
INSERT INTO article (id, title, body) VALUES (1, 'Indexes', 'database index design'), (2, 'Recipes', 'a plain sentence');
SELECT id, MATCH (body) AGAINST ('database') AS score FROM article ORDER BY score DESC;
```

Natural-language mode is the default, and `IN BOOLEAN MODE` takes `+word` for a required word, `-word` for an excluded word and a bare word for an optional one. Words are compared without regard to letter case, a row whose column is `NULL` matches nothing, and words shorter than three characters and common stopwords are left out of the index. The relevance is positive for a row that has a word of the search and zero for one that has none. Its value is the BM25 score of the engine summed over the columns of the index, so its sign agrees with MySQL's and its size does not.

The matcher of the engine cannot express a phrase in double quotes, a trailing `*`, a group in parentheses, `~`, `WITH QUERY EXPANSION` and `NOT MATCH ... AGAINST`, so each is refused with `1235`. Compare the relevance with `0` instead of using `NOT`. The other failures carry MySQL's numbers:

| Number | Reported when |
| --- | --- |
| `1191` | No `FULLTEXT` index covers the columns of `MATCH`. |
| `1210` | The search string of `AGAINST` is not a constant. |
| `1064` | A boolean-mode string cannot be parsed, such as `'+-word'`. |
| `1283` | A `FULLTEXT` index names a column that is not text. |
| `1221` | A `FULLTEXT` index column has an explicit order, such as `DESC`. |

`WITH PARSER`, the ngram and MeCab parsers, and the `innodb_ft_*` tables are not available.

### System variables

A `SELECT` of system variables, such as `SELECT @@version, @@sql_mode, @@autocommit`, answers one column for each variable, in the order asked, named by its alias or by the variable. A number is sent as an integer, and other values as text. `@@name`, `@@session.name`, `@@local.name` and `@@global.name` read the same value, in any letter case. A connection with no database chosen can run a `SELECT` of only system variables, which drivers send before they choose a database.

The values are the fixed settings of the server, so a `SET` does not change what `@@name` reads. A name that MySQL 8.4 or 8.0.35 does not have fails with error `1193` `Unknown system variable`. A variable that MySQL has but this server does not model reads as `NULL`, and so do variables that describe the host, such as `@@datadir`, `@@hostname`, `@@port` and `@@version_compile_os`. From SurrealDB 4.1, `@@socket` reads as an empty text, because the server has no Unix domain socket, so a client that reads it stays on TCP.

### `SHOW` and `DESCRIBE`

`SHOW` and `DESCRIBE` answer with MySQL 8.4's column names, order and types, with one row per table, field, indexed column or database:

| Statement | Answers with |
| --- | --- |
| `SHOW TABLES` | The tables of the current database, in a `Tables_in_<db>` column |
| `SHOW TABLE STATUS` | MySQL's 18 columns, one row per table, with sizes of `0`, times of `NULL`, and `VIEW` as the `Comment` of a view |
| `SHOW COLUMNS FROM t`, `SHOW FIELDS FROM t`, `DESCRIBE t`, `DESC t` | `Field`, `Type`, `Null`, `Key`, `Default` and `Extra`, one row per field |
| `SHOW INDEX FROM t`, `SHOW KEYS FROM t` | MySQL's 15 columns, one row per indexed column |
| `SHOW DATABASES` | The databases of the session's namespace, in a `Database` column |
| `SHOW VARIABLES` | `Variable_name` and `Value`, for the variables this server models |
| `SHOW ENGINES`, `SHOW COLLATION`, `SHOW CHARACTER SET` | MySQL's columns |
| `SHOW STATUS`, `SHOW PROCESSLIST`, `SHOW WARNINGS`, `SHOW ERRORS`, `SHOW TRIGGERS` | MySQL's columns and no rows |

Each `SHOW` reads under the session's own permissions, and needs a database to be chosen. `SHOW DATABASES` needs permission to view the namespace. A table that does not exist fails, and a `LIKE` pattern is limited to 512 characters. Some answers differ from MySQL:

- Columns and indexes are listed by name, not in the order they were defined.
- `SHOW CREATE TABLE` returns the SurrealQL definition, not MySQL DDL.
- With `LIKE`, the first column of `SHOW TABLES` is named `Tables_in_<db>`, where MySQL adds the pattern to the name.
- `Cardinality` in `SHOW INDEX` is `NULL`.
- An instance that denies built-in functions refuses these statements.

## Error codes

A failed statement is answered with the error number and SQLSTATE that MySQL 8.4 gives for the same kind of failure, for plain and for prepared statements. Drivers use the number to decide what to do, so PyMySQL, for example, raises `IntegrityError` for a duplicate key. The message text is SurrealDB's own.

| Number | SQLSTATE | Reported when |
| --- | --- | --- |
| `1062` | `23000` | A write conflicts with a `UNIQUE` index or a primary key. |
| `1048` | `23000` | A write gives `NULL` to a field that requires a value. |
| `1364` | `HY000` | A write leaves out a field that requires a value. |
| `1366` | `HY000` | A write gives a field a value of another type. |
| `1406` | `22001` | A write gives a text column a value longer than its declared type allows, such as `VARCHAR(5)`. |
| `1452` | `23000` | From 4.1, a write names a key that the table of a foreign key does not hold. |
| `1451` | `23000` | From 4.1, a delete removes a record that a foreign key without `ON DELETE CASCADE` or `SET NULL` links to. |
| `1091` | `42000` | From 4.1, `ALTER TABLE ... DROP FOREIGN KEY` names a key that the table does not have. |
| `1061` | `42000` | From 4.1, `CREATE TABLE` declares two indexes of one name. |
| `1068` | `42000` | From 4.1, `CREATE TABLE` declares a second primary key. |
| `1072` | `42000` | From 4.1, a key names a column that the table does not declare. |
| `1171` | `42000` | From 4.1, a primary key covers a column declared `NULL`. |
| `1280` | `42000` | From 4.1, an index is named `PRIMARY`. |
| `1347` | `HY000` | From 4.1, `DROP VIEW` or `CREATE OR REPLACE VIEW` names a table that is not a view. |
| `1049` | `42000` | From 4.1, a statement names a table of a database that does not exist. |
| `1044` | `42000` | From 4.1, a statement names the table `__sql_metadata`. |
| `1294` | `HY000` | From 4.1, `ON UPDATE CURRENT_TIMESTAMP` is declared on a column of another type, or with another precision than the column's. |
| `1568` | `25001` | From 4.1, `SET TRANSACTION ISOLATION LEVEL` is sent inside a transaction. |
| `1191` | `HY000` | From 4.1, `MATCH` names columns that no `FULLTEXT` index covers. |
| `6125` | `HY000` | From 4.1, a foreign key refers to columns that have no unique key in the parent table. |
| `3780` | `HY000` | From 4.1, the two columns of a foreign key hold incompatible values. |
| `1146` | `42S02` | The statement names a table that does not exist. |
| `1054` | `42S22` | The statement names a column that does not exist. |
| `1050` | `42S01` | `CREATE TABLE` names a table that already exists. |
| `1305` | `42000` | The statement calls a function that does not exist. |
| `1142` | `42000` | The user may not run the statement. |
| `1193` | `HY000` | The statement names a system variable that does not exist. |
| `3593` | `HY000` | A window function is used where it is not allowed, such as in `WHERE`. |
| `1213` | `40001` | The transaction conflicts with another transaction. Retry it. |
| `3024` | `HY000` | The statement exceeds its timeout. |
| `1235` | `42000` | The statement uses a feature that SurrealDB does not support. |
| `1644` | `45000` | `THROW` raises an error, or a subquery used as a value returns more than one row. |
| `1064` | `42000` | The statement cannot be parsed. |
| `1105` | `HY000` | Any other failure, where MySQL has no number for it. |

The numbers can differ from MySQL's for the same statement:

- Every refused value apart from a text that is too long is `1366`, where MySQL gives `1292` for a value that is not a valid date.
- SurrealDB refuses some values that MySQL converts, such as a number for a `VARCHAR` column, or `2` for a `BOOLEAN` column.
- `1/0` written into an `INT` column is `1366`, where MySQL gives `1365`.

## Not yet supported

The MySQL dialect refuses or differs from MySQL in these places:

- Recursive common table expressions are refused with `1235`, before the statement changes any data.
- The window function features that the [PostgreSQL dialect refuses](/docs/reference/protocols/postgres-protocol#not-yet-supported), such as `GROUPS` frames and `DISTINCT` inside a window call, are refused with `1235`.
- The forms of `INTERSECT` and `EXCEPT` that the PostgreSQL dialect refuses are refused with `1235`. From SurrealDB 4.1, `INTERSECT ALL` and `EXCEPT ALL` run. Before 4.1, they are refused with `1235`. Text is compared exactly, so `SELECT 'a' INTERSECT SELECT 'A'` answers no rows, where MySQL's default collation ignores letter case.
- From SurrealDB 4.1, `REPLACE` into a table that a foreign key refers to is refused with `1235` while `foreign_key_checks` is on. MySQL deletes the old row first, which a key may refuse (`1451`) or cascade, and `REPLACE` here replaces the row in place and runs neither. A `REPLACE` into any other table runs.
- From SurrealDB 4.1, `INSERT ... ON DUPLICATE KEY UPDATE` that assigns the key column anything but itself, as in `ON DUPLICATE KEY UPDATE id = 7`, is refused with `1235`, because the key of a record cannot change, where MySQL changes the key. `ON DUPLICATE KEY UPDATE id = id` runs. Before 4.1, the statement succeeds and leaves the row as it was.
- `SQL_CALC_FOUND_ROWS` is refused. `SQL_NO_CACHE`, `SQL_CACHE`, `SQL_SMALL_RESULT`, `SQL_BIG_RESULT`, `SQL_BUFFER_RESULT` and `HIGH_PRIORITY` are accepted and ignored.
- From SurrealDB 4.1, `INSERT ... VALUES` and `REPLACE ... VALUES` without a column list are refused with `1235` before they write anything, because a table does not keep the order its columns were declared in. List the columns, as in `INSERT INTO person (id, name) VALUES (1, 'Ada')`.
- `LOAD DATA` is not supported yet. Before SurrealDB 4.1, `ALTER TABLE` is not supported either. An `ORDER BY` inside `GROUP_CONCAT` fails with `1064`, and before SurrealDB 4.1 so does a `LATERAL` subquery.
- From SurrealDB 4.1, `information_schema.tables`, `views`, `schemata`, `columns`, `statistics`, `table_constraints`, `key_column_usage` and `referential_constraints` list the tables, views, columns, indexes and keys of the database in MySQL's form: `table_schema` is the name that `DATABASE()` returns, so `WHERE table_schema = DATABASE()` finds them, `column_type` holds the type as the column declares it, such as `varchar(255)` or `int unsigned`, and `column_key` is `PRI`, `UNI` or `MUL`. `column_default` holds the literal default of a column, a decimal with the scale of its column, or `CURRENT_TIMESTAMP` with the digits of its precision, in which case `extra` is `DEFAULT_GENERATED`. `information_schema.routines` has MySQL's 31 columns and no row, because the server has no stored routines. Before 4.1, `information_schema` lists the tables in PostgreSQL's form, in the schema `public`, with PostgreSQL type names in `data_type` and `NULL` in `column_type`, so `WHERE table_schema = DATABASE()` finds none.
- Before SurrealDB 4.1, `FOREIGN KEY` constraints are not supported, and `CREATE TABLE` with one fails with `1105`. From 4.1, they work as described under [Foreign keys](#foreign-keys).
- `LIKE` is refused with `1235` in an `INSERT`, `UPDATE` or `DELETE`, including in its `WHERE` clause, so `DELETE FROM t WHERE name LIKE 'a%'` fails before it deletes anything. It works in a `SELECT`. Functions, such as `SUBSTRING`, `LTRIM` and `CONCAT`, work in both.
- `CAST(x AS UNSIGNED)` of a value read from a column fails with `1366` when the value is negative, or is a text that is not a number such as `'12abc'`. MySQL wraps the negative value, and reads the number at the start of the text.
- `TIMESTAMPDIFF` with the unit `MONTH`, and compound interval units such as `DAY_HOUR`, are refused with `1235`.
- `TRUNCATE` keeps the records that the table's permissions do not let the user delete, and still answers OK.
- An `INSERT` that gives an `AUTO_INCREMENT` primary key `NULL` is refused, where MySQL numbers the row.
- `@@performance_schema` is `0`. `@@session.name` of a variable that is global only reads a value, where MySQL gives error `1238`.
- `SET GLOBAL timestamp` is error `1235`, where MySQL gives `1228`.
- A batch of several statements that names an unknown system variable fails as a whole before any statement runs.
- In a batch of several statements, only the first statement keeps its column names. Unnamed or repeated columns of later statements are named `?column?1`, `?column?2`, and so on.
- `LIKE ... ESCAPE` is refused, and `e` and `é` are not equal in a comparison.
- A `?` parameter placeholder is accepted only in a prepared statement.

## Capabilities and security

Connections are gated like other query surfaces:

- **The `mysql` route.** [`--deny-http mysql`](/docs/learn/security/authorization/capabilities#http-routes-and-rpc-methods) refuses every connection to the listener with error `1045`. The route also allows the MySQL dialect on the listener.
- **GQL.** `SET dialect = 'gql'` needs the `gql` route. When the server denies the route, the `SET dialect` statement fails, and a GQL query fails with `1045`.
- **Arbitrary queries.** [`--deny-arbitrary-query`](/docs/learn/security/authorization/capabilities#arbitrary-queries) applies to connections on this listener as it does on the other surfaces.
- **The metadata table.** From SurrealDB 4.1, a statement that names the table `__sql_metadata`, which holds what the SQL front ends keep about a table, is refused with `1044`, whether or not the table exists yet, and no listing shows it. The [metadata table](/docs/reference/protocols/sql-compatibility#the-metadata-table) section of the compatibility matrix describes it.

The listener accepts at most 1,024 connections at a time and answers further connections with error `1040` `Too many connections`. A packet is limited to 64 MiB, the value of `@@max_allowed_packet`, and a larger packet is refused with error `1153`.
