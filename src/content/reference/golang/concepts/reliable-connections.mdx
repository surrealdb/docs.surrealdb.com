# Reliable connections

A client can lose its WebSocket connection, for example when the network changes or the server restarts. A Go SDK client that uses WebSocket then reconnects by itself. Before it sends anything else on the new connection, it restores what it held on the old one. This page covers how reconnection works, and what the client restores and loses. It also covers how to watch the state of the connection, and the `contrib/rews` package for custom retry strategies.

## How reconnection works

Reconnection is on by default for WebSocket connections. When the client loses the connection, it connects again, with backoff between attempts. The wait before attempt *n* is the minimum delay times 2 to the power of *n*, counting attempts from 1. Each wait also has up to 10% random jitter in either direction, and no wait is longer than the maximum delay. With the default delays of `1s` and `1m`, the client waits about 2, 4, 8, 16 and 32 seconds before its five attempts. When the last attempt fails, the client gives up and closes.

While the client reconnects:

- A request made in that time waits until the client has reconnected and restored the session. If the request's context ends first, the request fails with `waiting to reconnect: context deadline exceeded`.
- A request that was waiting for its response when the client lost the connection fails with an error that wraps `connection.ErrConnectionClosed`. The server may or may not have run that request.
- After the client gives up, every request fails with an error that wraps `surrealdb.ErrClientClosed`.

Pass options to change the number of attempts and the delays:

```go
db, err := surrealdb.FromEndpointURLStringWithOptions(ctx, "wss://example.surrealdb.cloud",
	surrealdb.WithReconnectAttempts(10),
	surrealdb.WithReconnectDelay(500*time.Millisecond, 30*time.Second),
)
```

`WithReconnectAttempts(0)`, or any number below 1, removes the limit, so the client tries until it reconnects or you close it. `WithReconnect(false)` turns reconnection off: a lost connection then closes the client, and later requests fail.

HTTP connections are stateless, so they have nothing to reconnect. Each HTTP request opens what it needs.

## What gets restored

Before it sends any other request on the new connection, the client restores what it held on the old one:

1. The **sessions** attached with `Attach` or `Fork`, under the same UUIDs.
2. The **authentication** of the default session and of each session, with the last token that the session received. With [token renewal](/docs/reference/golang/concepts/authentication#automatic-token-renewal) on, the client first exchanges an expired pair for a new one.
3. The **namespace and database** of each session.
4. The **variables** that each session set with `.Let()`.
5. The **live queries** started with `Live`, under the same UUIDs, each in the namespace and database where it started. Their channels keep receiving notifications.

The client ends a live query, instead of restoring it, when its session is no longer signed in as the same user. The client also ends a live query when the server refuses to start it again. In both cases, the channel of the live query closes, and the status event reports `surrealdb.ErrLiveQueryEnded`.

## What is lost

The client cannot restore some state on a new connection:

- **Open transactions.** A transaction that was open is gone, and calls on it fail. Run the transaction again from the start.
- **Live queries started with a `LIVE SELECT` statement.** The client does not know their definition, so it cannot start them again. Use `Live` for a live query that must survive a reconnect.
- **Changes made while the client was disconnected.** Live queries that restart do not receive notifications for those changes.
- **A sign-in whose token has expired.** A session that signed in with a username and password can outlive its token. By default, the token lasts one hour. Without token renewal, the client cannot authenticate the session again on the new connection, and the status event reports the error.
- **A sign-in on a server that restarted with a new datastore.** A server that runs in memory starts empty after a restart. It does not accept the tokens that it issued before the restart. The status event reports `authenticate: There was a problem with authentication`. The session is signed out, and its live queries end. A server with a persistent datastore accepts the old token, so the client restores the session.

If the client cannot restore the sign-in, sign the session in again. You can do this in the function that you pass to `.OnStatus()`.

## Watching the connection status

`.Status()` returns the state of the connection, as a `surrealdb.ConnectionStatus`:

| Status | Meaning |
| --- | --- |
| `StatusConnected` | The client sends requests to the server. |
| `StatusDisconnected` | The client lost the connection, or an attempt to reconnect failed. Requests wait. |
| `StatusReconnecting` | The client is trying to reconnect. |
| `StatusClosed` | The client was closed, or gave up reconnecting. Requests fail. |

`.OnStatus()` calls a function with a [`StatusEvent`](/docs/reference/golang/api/types#statusevent) at each change of state, until you call the function that `.OnStatus()` returns:

```go
stop := db.OnStatus(func(ev surrealdb.StatusEvent) {
	switch ev.Status {
	case surrealdb.StatusDisconnected:
		log.Printf("connection lost (attempt %d): %v", ev.Attempt, ev.Err)
	case surrealdb.StatusConnected:
		if ev.Err != nil {
			log.Printf("reconnected, but could not restore: %v", ev.Err)
		}
	case surrealdb.StatusClosed:
		log.Printf("gave up: %v", ev.Err)
	}
})
defer stop()
```

`Attempt` counts the attempts since the client lost the connection, from 1. It is 0 for the event that reports the loss. On a `StatusConnected` event after a reconnect, `Err` holds what the client could not restore, such as an expired token. `Err` is `nil` when the client restored everything.

The client calls the function with one event at a time, in order, on a goroutine of its own. The function can make requests on the client, or close the client. The next events wait until the function returns. Only a client that reconnects reports changes. A client without reconnection reports `StatusConnected` until it is closed.

## Custom connections

A `gorillaws` or `gws` connection that you pass to [`FromConnection`](/docs/reference/golang/api/core/db#fromconnection) reconnects in the same way. Both connection types implement `connection.Redialer` and `connection.CloseNotifier`. A connection of your own reconnects when it implements those two interfaces.

## Using the rews package

> [!WARNING]
> The `contrib/rews` package is outside the backward compatibility guarantee of the SDK. Its API can change in a minor release.

The `rews` package provides a reconnecting WebSocket connection with its own retry strategies. For example, it can use exponential backoff without a limit on attempts, or a strategy that you write yourself. Use it when the built-in reconnection options do not fit.

Create a `rews.Connection` with `rews.New`. It takes these arguments, in this order:

- A function that builds the underlying WebSocket connection
- An interval for checking the connection
- A CBOR unmarshaler
- An optional logger

The example below uses a `gorillaws` connection, checks it every 5 seconds, and passes no logger:

```go
import (
	"context"
	"net/url"
	"time"

	surrealdb "github.com/surrealdb/surrealdb.go/v2"
	"github.com/surrealdb/surrealdb.go/v2/contrib/rews"
	"github.com/surrealdb/surrealdb.go/v2/pkg/connection"
	"github.com/surrealdb/surrealdb.go/v2/pkg/connection/gorillaws"
)

u, err := url.ParseRequestURI("ws://localhost:8000")
if err != nil {
	log.Fatal(err)
}
conf := connection.NewConfig(u)

conn := rews.New(
	func(ctx context.Context) (*gorillaws.Connection, error) {
		return gorillaws.New(conf), nil
	},
	5*time.Second,
	conf.Unmarshaler,
	nil,
)

db, err := surrealdb.FromConnection(ctx, conn)
if err != nil {
	log.Fatal(err)
}
defer db.Close(ctx)
```

A `rews` connection reconnects by itself. The client does not use its built-in reconnection on this connection.

### Configuring retry behaviour

By default, `rews` does not retry a failed attempt to connect. To retry, set the `Retryer` field of the connection. `ExponentialBackoffRetryer` makes the delay between attempts grow exponentially, with jitter:

```go
retryer := rews.NewExponentialBackoffRetryer()
retryer.MaxRetries = 10
retryer.InitialDelay = time.Second
retryer.MaxDelay = 30 * time.Second
conn.Retryer = retryer
```

| Field | Default | Description |
| --- | --- | --- |
| `InitialDelay` | `1s` | The delay before the first retry |
| `MaxDelay` | `30s` | The longest delay between retries |
| `Multiplier` | `2.0` | The factor by which the delay grows |
| `MaxRetries` | `0` | The number of retries, where `0` means no limit |
| `Jitter` | `true` | Adds randomness to each delay |
| `JitterFactor` | `0.3` | The largest jitter, as a fraction of the delay |

`FixedDelayRetryer` waits the same time before each attempt:

```go
conn.Retryer = rews.NewFixedDelayRetryer(2*time.Second, 5)
```

A strategy of your own implements the `Retryer` interface:

```go
type Retryer interface {
	NextDelay(attempt int, lastErr error) (time.Duration, bool)
	Reset()
}
```

### What rews restores

When `rews` reconnects, it restores the namespace and database, the authentication, the variables and the live queries. The figure below shows the states of a `rews` connection and the order in which it restores the session.

<img src="~/assets/img/diagrams/light/conn-reconnect-go-light.webp" darkSrc="~/assets/img/diagrams/conn-reconnect-go.webp" alt="The rews connection of the Go SDK moves from Disconnected to Connecting to Connected, and to Closing and Closed after Close(). At each CheckInterval it checks the socket, and if the socket has closed it reconnects and restores the session; a failed attempt is tried again at the next check. The session is restored in this order: the namespace and database from the last Use(), the authentication with the last token or, if the server refuses it, with the refresh token from SignInWithRefresh, the variables set with Let(), and the live queries from Live() or from a Query() call that starts with LIVE SELECT, whose notifications keep their original IDs. With an expired token and no refresh token the reconnect fails, and a LIVE SELECT that is not at the start of its query is not restored." />

> [!NOTE]
> When the server refuses the last token on a reconnect, and the session signed in with `.SignInWithRefresh()` or `.SignUpWithRefresh()`, `rews` signs in with the refresh token and keeps the new pair. The server revokes a refresh token once it is used, so set `OnTokensRefreshed` to receive the new pair, or read it with `conn.Tokens(ctx)`. Without a refresh token, the sign-in fails and the reconnect is tried again at the next check.

A `rews.Connection` moves through the states `Disconnected`, `Connecting`, `Connected`, `Closing` and `Closed`. After `Closed`, it cannot be used again.
