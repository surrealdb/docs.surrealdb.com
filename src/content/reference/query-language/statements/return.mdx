# `RETURN` statement

The `RETURN` statement can be used to return an implicit value or the result of a query, and to set the return value for a transaction, block, or function.

## Statement syntax

<Tabs syncKey="return-statement">
  <TabItem label="SurrealQL Syntax">

```syntax title="SurrealQL Syntax"
RETURN @value
```

## Example usage
### Basic usage

`RETURN` is always followed by a value. As every data type in SurrealDB is a type of [value](/docs/reference/query-language/language-primitives/data-types/values), the `RETURN` statement can return anything from simple values to the result of queries.

```surql
/**[test]

[[test.results]]
value = "123"

[[test.results]]
value = "'I am a string!'"

[[test.results]]
value = "{ prop: 'value' }"

[[test.results]]
error = "The table 'person' does not exist"

[[test.results]]
value = "[person:l8n06hvjap2dxwchhuzq]"
skip-record-id-key = true

*/

-- Return a simple value
RETURN 123;
RETURN "I am a string!";
RETURN {
	prop: "value"
};

-- Return the result of a query
RETURN SELECT * FROM person;
RETURN (CREATE person).id;
```

Values on their own are treated as if they have an implicit `RETURN` in front. As such, the following queries return the same output as in the previous example.

```surql
/**[test]

[[test.results]]
value = "123"

[[test.results]]
value = "'I am a string!'"

[[test.results]]
value = "{ prop: 'value' }"

[[test.results]]
error = "The table 'person' does not exist"

[[test.results]]
value = "[person:ritmmuf01x433scdjcua]"
skip-record-id-key = true

*/

123;
"I am a string!";
{
	prop: "value"
};
SELECT * FROM person;
(CREATE person).id;
```

## Transaction return value

`RETURN` sets the value that a block or a function returns. Directly inside a transaction started with `BEGIN`, a `RETURN` is a statement like any other: its value is one of the results of the query, and the statements after it still run. This is the case from SurrealDB 4.0. Before 4.0, a `RETURN` ended the transaction early, and the statements after it did not run.

```surql title="Transaction return value"
/**[test]

[[test.results]]
value = "NONE"

[[test.results]]
value = "NONE"

[[test.results]]
value = "NONE"

[[test.results]]
value = "NONE"

[[test.results]]
value = "person:vtuj6es8fkd1gnppfefn"
skip-record-id-key = true

[[test.results]]
value = "NONE"

*/

BEGIN TRANSACTION;

-- We are executing quite a few queries here
LET $firstname = "John";
LET $lastname = "Doe";

LET $person = CREATE ONLY person CONTENT {
	firstname: $firstname,
	lastname: $lastname,
};

-- The person's ID is the result of this statement
RETURN $person.id;

-- One issue with this approach is that query errors are generic.
-- To get around that, use a block, which is executed as a transaction by itself.

COMMIT TRANSACTION;
```

## Return breaks execution

`RETURN` ends the function, block or `IF` that it is in, so the statements after it in that function, block or `IF` do not run.

```surql title="Function return value"
/**[test]

[[test.results]]
value = "NONE"

[[test.results]]
value = "[person:e71cnhnwdb6yuz8is8kq]"
skip-record-id-key = true

[[test.results]]
value = "[{ firstname: 'Thanos', id: person:e71cnhnwdb6yuz8is8kq, lastname: 'Johnson' }]"
skip-record-id-key = true

*/

DEFINE FUNCTION fn::person::create($firstname: string, $lastname: string) {
	LET $person = CREATE person CONTENT {
		firstname: $firstname,
		lastname: $lastname,
	};

	-- The RETURN statement will set the return value of the custom function, and further queries will not be executed.
	RETURN $person.id;

    -- This query will never be executed
    CREATE person SET firstname = "Stephen", lastname = "Strange";
};

fn::person::create("Thanos", "Johnson");
SELECT * FROM person;
```

```surql title="Functions"
DEFINE FUNCTION fn::round::up($num: number) -> number {
    IF $num % 2 == 0 {
        RETURN $num; -- Breaks execution for the function
    };

    -- This is only executed if the RETURN inside the IF statement did not break execution
    RETURN $num + 1;
};
```

A `RETURN` placed directly inside a transaction does not end the transaction. From SurrealDB 4.0, each of the statements below runs, and the two `RETURN` values are among the results. Before 4.0, the transaction ended at `RETURN 1`.

```surql title="Transactions"
BEGIN;
RETURN 1; -- Is executed
CREATE a; -- Is executed
RETURN 2; -- Is executed
COMMIT;
```

To end part of a transaction early, put those statements in a block. The `RETURN` ends the block, and the transaction carries on after it:

```surql title="Ending a block inside a transaction"
BEGIN;
CREATE c:1;
{
    CREATE c:2;
    RETURN "done";
    -- Does not run
    CREATE c:3;
};
-- Runs
CREATE c:4;
COMMIT;
```

Lastly, outside a transaction or function, `RETURN` only ends the statement it is executed in. It does **not** prevent the top-level statements after it from being executed, nor does it adjust their output.

```surql title="Statements"
LET $id = 123;
LET $id = {
    IF $id {
        RETURN type::record('table', $id);
    };

    RETURN table:rand();
};

-- This still executes. The `RETURN` statement only broke until the block in the variable assignment.
$id;
```
