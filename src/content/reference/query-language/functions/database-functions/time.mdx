# Time functions and consts

This page contains built-in functions and constants for working with and manipulating [datetime](/docs/reference/query-language/language-primitives/data-types/datetimes) values. From SurrealDB 4.0, most of them also work with the `date`, `time` and `timestamp` types, as described in [Dates, times and timestamps](#dates-times-and-timestamps).

> [!NOTE]
> Since version 3.0.0-beta, the `::from::` functions (e.g. `time::from::millis()`) now use underscores (e.g. `time::from_millis()`) to better match the intent of the function and method syntax.

Many time functions take an `option<datetime>` in order to return certain values from a datetime such as its hours, minutes, day of the year, and so on. If no argument is present, the current datetime will be extracted and used. As such, all of the following function calls are valid and will not return an error.

```surql
time::hour(d'2024-09-04T00:32:44.107Z');
time::hour();

time::minute(d'2024-09-04T00:32:44.107Z');
time::minute();

time::yday(d'2024-09-04T00:32:44.107Z');
time::yday();
```

## Dates, times and timestamps

From SurrealDB 4.0, most of these functions also take a [`date`, `time` or `timestamp`](/docs/reference/query-language/language-primitives/data-types/dates-and-times). A function that reads a part of the calendar takes a value that has a date, and a function that reads a part of the clock takes a value that has a time of day. A function that changes a value returns the same type that it was given.

| Functions | Accept | Return |
| --- | --- | --- |
| `time::year()`, `time::month()`, `time::day()`, `time::wday()`, `time::yday()`, `time::week()`, `time::is_leap_year()` | `date`, `timestamp`, `datetime` | `int`, or `bool` for `time::is_leap_year()` |
| `time::hour()`, `time::minute()`, `time::second()`, `time::nano()`, `time::micros()`, `time::millis()` | `time`, `timestamp`, `datetime` | `int` |
| `time::format()` | `date`, `timestamp`, `datetime` | `string` |
| `time::ceil()`, `time::floor()`, `time::round()`, `time::group()`, `time::set_*()` | `date`, `timestamp`, `datetime` | the type of the argument |
| `time::trunc()` | `date`, `time`, `timestamp`, `datetime` | the type of the argument |
| `time::extract()` | `date`, `time`, `timestamp`, `datetime` | a number |
| `time::age()` | `date`, `timestamp`, `datetime` | `interval` |
| `time::min()`, `time::max()` | an array of `date`, `time`, `timestamp`, `interval` or `datetime` values, all of one type | the type of the elements |

A function given a `date` must give a whole date back, so a result that is not midnight is an error rather than a value that loses its time. Cast the date to a `timestamp` first to keep the time:

```surql
time::set_year(pd'2026-10-27', 2030);
//- pd'2030-10-27'

time::set_hour(pd'2026-10-27', 3);
//- 'Incorrect arguments for function time::set_hour(). The result is not a whole date, so the argument must be cast to a timestamp first.'

time::set_hour(<timestamp> pd'2026-10-27', 3);
//- ts'2026-10-27T03:00:00'
```

A value of the wrong type is refused with the types the function accepts:

```surql
time::hour(pd'2026-10-27');
//- 'Incorrect arguments for function time::hour(). The argument must be a time, timestamp or datetime, found date.'
```

Called with no argument, a function such as `time::year()` reads the current `datetime`, as before.

## `time::age`

<Since v="v4.0.0" />

The `time::age` function returns the difference between two values as an interval of years, months, days and time, as the PostgreSQL `age` function does. The first argument is the later value, and a result is negative when the first argument is earlier than the second.

```surql title="API DEFINITION"
time::age(date|timestamp|datetime, date|timestamp|datetime) -> interval
```

The following example shows this function, and its output:

```surql
time::age(ts'2026-10-27T12:00:00', ts'2020-02-29T06:30:00');
//- ivl'P6Y7M27DT5H30M'

time::age(ts'2020-02-29T06:30:00', ts'2026-10-27T12:00:00');
//- ivl'P-6Y-7M-27DT-5H-30M'

time::age(pd'2026-03-01', pd'2026-01-31');
//- ivl'P1M1D'
```

The difference is counted in whole calendar units first, so a month is the distance from one day of a month to the same day of the next. When the later value has an earlier day of the month than the earlier value, the function borrows the length of the earlier value's month, as in the last example above. The two arguments can be of different types, and an argument of `infinity` or `-infinity` is refused.

The subtraction operator gives a different result: `timestamp - timestamp` returns days and time but no months, so it is the better choice for a length that should not depend on the calendar.

```surql
ts'2026-10-27T00:00:00' - ts'2026-09-27T00:00:00';
//- ivl'P30D'

time::age(ts'2026-10-27T00:00:00', ts'2026-09-27T00:00:00');
//- ivl'P1M'
```

## `time::ceil`

The `time::ceil` function raises a datetime to the nearest multiple of duration from the Unix epoch (January 1, 1970).

```surql title="API DEFINITION"
time::ceil(datetime, $ceiling: duration) -> datetime
time::ceil(timestamp, $ceiling: duration) -> timestamp
time::ceil(date, $ceiling: duration) -> date
```

The following example shows this function, and its output:

```surql
/**[test]

[[test.results]]
value = "NONE"

[[test.results]]
value = "[d'2024-08-30T03:00:00Z', d'2024-09-05T00:00:00Z']"

*/
LET $now = d'2024-08-30T02:22:50.231631Z';

RETURN [
  time::ceil($now, 1h),
  time::ceil($now, 1w)
];
```

```surql title="Output"
[
	d'2024-08-30T03:00:00Z',
	d'2024-09-05T00:00:00Z'
]
```

### Implementation details

Since this function raises a datetime to the next multiple of duration from the Unix epoch, this means for example that:

* time::ceil(now, 18d) rounds up from the nearest multiple of 18 days since epoch
* time::ceil(now, 17d) rounds up from the nearest multiple of 17 days since epoch

Each call uses a different modular base, so the truncation points land at different offsets that may not be sequential. For example, for October 23, 2023 (day ~19,653 since epoch):

* 19653 / 18 = 1091.83… → 1092 × 18 = day 19,656 → Oct 26
* 19653 / 17 = 1156.05… → 1157 × 17 = day 19,669 → Nov 08
* 19653 / 16 = 1228.31… → 1229 × 16 = day 19,664 → Nov 03
* 19653 / 15 = 1310.20… → 1311 × 15 = day 19,665 → Nov 04


```surql
LET $now = d'2023-10-23T09:12:53Z';

time::ceil($now, 18d); -- d'2023-10-26T00:00:00Z'
time::ceil($now, 17d); -- d'2023-11-08T00:00:00Z'
time::ceil($now, 16d); -- d'2023-11-03T00:00:00Z'
time::ceil($now, 15d); -- d'2023-11-04T00:00:00Z'
```

To use this function to raise to midnight of the next day, the duration values above can be subtracted from the datetime first, followed by `1d` for the ceiling.

```surql
LET $now = d'2023-10-23T09:12:53Z';

time::ceil($now - 18d, 1d); -- d'2023-10-06T00:00:00Z'
time::ceil($now - 17d, 1d); -- d'2023-10-07T00:00:00Z'
time::ceil($now - 16d, 1d); -- d'2023-10-08T00:00:00Z'
time::ceil($now - 15d, 1d); -- d'2023-10-09T00:00:00Z'
```

## `time::day`

The `time::day` function extracts the day as a number from a datetime, or from the current date if no datetime argument is present.

```surql title="API DEFINITION"
time::day(option<date|timestamp|datetime>) -> number
```

The following example shows this function, and its output:

```surql
/**[test]

[[test.results]]
value = "1"

*/

time::day(d"2021-11-01T08:30:17+00:00");
```

```surql title="Output"
1
```

## `time::epoch`

The `time::epoch` constant returns the `datetime` for the UNIX epoch (1 January 1970).

```surql
-- Return the const
RETURN time::epoch;
//- d'1970-01-01T00:00:00Z'

-- Define field using the const
DEFINE FIELD since_epoch ON event COMPUTED time::now().floor(1d) - time::epoch;
CREATE ONLY event:one SET information = "Something happened";
//- { id: event:one, information: 'Something happened', since_epoch: 55y42w6d }
```

## `time::extract`

<Since v="v4.0.0" />

The `time::extract` function returns one field of a `date`, `time`, `timestamp` or `datetime`, named by a string, as the PostgreSQL `extract` function does.

```surql title="API DEFINITION"
time::extract(date|time|timestamp|datetime, $field: string) -> number
```

The field names are not case-sensitive. A field that needs a date cannot be read from a `time`, and a field that needs a time of day cannot be read from a `date`.

| Field | Returns |
| --- | --- |
| `year` | The year. There is no year zero: 1 BC is `-1` |
| `isoyear` | The ISO 8601 week-numbering year |
| `quarter` | The quarter of the year, from `1` to `4` |
| `month` | The month, from `1` to `12` |
| `week` | The ISO 8601 week of the year |
| `day` | The day of the month |
| `doy` | The day of the year, from `1` to `366` |
| `dow` | The day of the week, from `0` for Sunday to `6` for Saturday |
| `isodow` | The day of the week, from `1` for Monday to `7` for Sunday |
| `decade` | The year divided by 10 |
| `century` | The century, so 2026 is in century `21` |
| `millennium` | The millennium, so 2026 is in millennium `3` |
| `julian` | The Julian day number, with a fraction for the time of day |
| `hour` | The hour, from `0` to `24` |
| `minute` | The minute, from `0` to `59` |
| `second` | The seconds, with their fraction |
| `milliseconds` | The seconds, with their fraction, in milliseconds |
| `microseconds` | The seconds, with their fraction, in microseconds |
| `epoch` | The seconds since `1970-01-01T00:00:00`, or since midnight for a `time` |

The following example shows this function, and its output:

```surql
time::extract(ts'2026-10-27T12:30:45.5', 'quarter');
//- 4

time::extract(ts'2026-10-27T12:30:45.5', 'century');
//- 21

time::extract(ts'2026-10-27T12:30:45.5', 'second');
//- 45.5dec

time::extract(ts'2026-10-27T12:30:45.5', 'epoch');
//- 1793104245.5dec

time::extract(pd'2026-10-27', 'julian');
//- 2461341

time::extract(pt'12:30:45', 'year');
//- 'Incorrect arguments for function time::extract(). `year` cannot be read from a time.'
```

For `infinity` and `-infinity`, a field that only grows over time, such as `year`, `century` or `epoch`, returns `Infinity` or `-Infinity`. Every other field returns `NULL`.

```surql
time::extract(ts'infinity', 'year');
//- Infinity

time::extract(ts'infinity', 'month');
//- NULL
```

## `time::floor`

The `time::floor` function truncates a datetime to the nearest lower multiple of duration from the Unix epoch (January 1, 1970).

```surql title="API DEFINITION"
time::floor(datetime, $floor: duration) -> datetime
time::floor(timestamp, $floor: duration) -> timestamp
time::floor(date, $floor: duration) -> date
```

The following example shows this function, and its output:

```surql
/**[test]

[[test.results]]
value = "d'2021-10-28T00:00:00Z'"

*/

time::floor(d"2021-11-01T08:30:17+00:00", 1w);
```

```surql title="Output"
d'2021-10-28T00:00:00Z'
```

### Implementation details

Since this function truncates a datetime to the nearest lower multiple of duration from the Unix epoch, this means for example that:

* time::floor(now, 18d) rounds down to the nearest multiple of 18 days since epoch
* time::floor(now, 17d) rounds down to the nearest multiple of 17 days since epoch

Each call uses a different modular base, so the truncation points land at different offsets that may not be sequential. For example, for October 23, 2023 (day ~19,653 since epoch):

* 19653 / 18 = 1091.83… → 1091 × 18 = day 19,638 → Oct 8
* 19653 / 17 = 1156.05… → 1156 × 17 = day 19,652 → Oct 22
* 19653 / 16 = 1228.31… → 1228 × 16 = day 19,648 → Oct 18
* 19653 / 15 = 1310.20… → 1310 × 15 = day 19,650 → Oct 20


```surql
LET $now = d'2023-10-23T09:12:53Z';

time::floor($now, 18d); -- d'2023-10-08T00:00:00Z'
time::floor($now, 17d); -- d'2023-10-22T00:00:00Z'
time::floor($now, 16d); -- d'2023-10-18T00:00:00Z'
time::floor($now, 15d); -- d'2023-10-20T00:00:00Z'
```

time::floor($now - 16d, 1d); -- d'2023-10-07T00:00:00Z'
time::floor($now - 15d, 1d); -- d'2023-10-08T00:00:00Z'

## `time::max`

The `time::max` function returns the greatest datetime from an array of datetimes.

```surql title="API DEFINITION"
time::max(array<datetime>) -> datetime
time::max(array<date>) -> date
time::max(array<time>) -> time
time::max(array<timestamp>) -> timestamp
time::max(array<interval>) -> interval
```

The following example shows this function, and its output:

```surql
/**[test]

[[test.results]]
value = "d'1988-06-22T08:30:45Z'"

*/

time::max([ d"1987-06-22T08:30:45Z", d"1988-06-22T08:30:45Z" ])
```

```surql title="Output"
d'1988-06-22T08:30:45Z'
```

From SurrealDB 4.0, the array can also hold dates, times, timestamps or intervals, as long as every element has the same type. Intervals compare by their total length, with a month counted as 30 days:

```surql
time::max([ivl'1 mon', ivl'29 days']);
//- ivl'P1M'

time::max([pd'2026-10-28', pt'01:00:00']);
//- 'Incorrect arguments for function time::max(). The elements must all be of one kind.'
```

When `time::max` reads a field over the records of a group, as in `GROUP BY`, `GROUP ALL` or a [pre-computed table view](/docs/reference/query-language/statements/define/table#pre-computed-table-views), keep the values of each group to one temporal kind. A group that mixes kinds does not return an error, and its result depends on the order in which the records are read.

See also:

* [`array::max`](/docs/reference/query-language/functions/database-functions/array#arraymax), which extracts the greatest value from an array of values
* [`math::max`](/docs/reference/query-language/functions/database-functions/math#mathmax), which extracts the greatest number from an array of numbers

## `time::trunc`

<Since v="v4.0.0" />

The `time::trunc` function truncates a value to the start of a unit, as the PostgreSQL `date_trunc` function does, and returns the same type that it was given. It is a wider form of [`time::group`](#timegroup) that also accepts `week`, `quarter`, `decade`, `century` and `millennium`.

```surql title="API DEFINITION"
time::trunc(datetime, $unit: string) -> datetime
time::trunc(timestamp, $unit: string) -> timestamp
time::trunc(date, $unit: string) -> date
time::trunc(time, $unit: string) -> time
```

The units are `microseconds`, `milliseconds`, `second`, `minute`, `hour`, `day`, `week`, `month`, `quarter`, `year`, `decade`, `century` and `millennium`. A week starts on a Monday, and a century or a millennium starts with year 1, as in `2001-01-01`. A `time` can only be truncated to `hour` or a smaller unit.

The following example shows this function, and its output:

```surql
time::trunc(ts'2026-10-27T12:30:45.123456', 'minute');
//- ts'2026-10-27T12:30:00'

time::trunc(ts'2026-10-27T12:30:45.123456', 'week');
//- ts'2026-10-26T00:00:00'

time::trunc(pd'2026-10-27', 'century');
//- pd'2001-01-01'

time::trunc(pt'12:30:45', 'hour');
//- pt'12:00:00'
```

`infinity` and `-infinity` truncate to themselves.

## `time::from_uuid`

The `time::from_uuid` function calculates a datetime based on the UUID.

```surql title="API DEFINITION"
time::from_uuid(uuid) -> datetime
```

The following example shows this function, and its output:

```surql
/**[test]

[[test.results]]
value = "d'2025-01-09T10:57:58.757Z'"

*/

time::from_uuid(u'01944ab6-c1e5-7760-ab6a-127d37eb1b94');
```

```surql title="Output"
d'2025-01-09T10:57:58.757Z'
```

The UUID must be a version 1, 6 or 7 UUID, because only these versions hold a time. Any other version, such as the version 4 UUID that `rand::uuid::v4()` generates, fails with `Incorrect arguments for function time::from_uuid(). The first argument must be a v1, v6 or v7 UUID.` A version 1 or 6 UUID can also hold a date before 1970:

```surql
time::from_uuid(u'3c230000-a32f-1163-8000-000000000000');
```

```surql title="Output"
d'1900-01-01T00:00:00Z'
```

A version 7 UUID, which `rand::uuid()` generates, is only precise to the millisecond, so a conversion from it to a datetime drops anything smaller.

```surql
LET $now = time::now();
[$now, time::from_uuid(rand::uuid($now))];
```

```surql title="Possible output"
[
	d'2026-01-29T02:12:13.848476Z',
	d'2026-01-29T02:12:13.848Z'
]
```

## `time::set_month`

<Since v="v3.0.2" />

The `time::set_month` function sets the month value of a datetime.

```surql title="API DEFINITION"
time::set_month(datetime, $month: integer) -> datetime
time::set_month(timestamp, $month: integer) -> timestamp
time::set_month(date, $month: integer) -> date
```

Example:

```surql
d'1970-01-01T00:00:00.500000005Z'.set_month(9);
-- Output
d'1970-09-01T00:00:00.500000005Z'
```

## `time::set_nanosecond`

<Since v="v3.0.2" />

The `time::set_nanosecond` function sets the nanosecond value of a datetime.

```surql title="API DEFINITION"
time::set_nanosecond(datetime, $nanosecond: integer) -> datetime
time::set_nanosecond(timestamp, $nanosecond: integer) -> timestamp
time::set_nanosecond(date, $nanosecond: integer) -> date
```

Example:

```surql
d'1970-01-01T10:00:00.500000005Z'.set_nanosecond(3535);
-- Output
d'1970-01-01T10:00:00.000003535Z'
```

Since nanoseconds are not needed in a datetime, setting the nanoseconds of a datetime to 0 can be used to make a datetime look cleaner.

```surql
d'1970-01-01T00:00:00.500000000Z'.set_nanosecond(0);
d'1970-01-01T00:00:00Z' -- output
```
