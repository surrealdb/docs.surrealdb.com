# surreal cloud team

`surreal cloud team` manages organisation members: the people who already belong. Invitations that have been sent but not accepted live in [`invite`](/docs/reference/cli/cloud/commands/invite), and `team list` deliberately does not fold them in - a pending invitation is not a member.

<Synopsis>
surreal cloud team <COMMAND> [OPTIONS]
surreal cloud teams <COMMAND> [OPTIONS]
</Synopsis>

| Verb | Purpose | Alias |
| --- | --- | --- |
| [`list`](#team-list) | List the members of an organisation | `ls` |
| [`get`](#team-get) | Show one member | |
| [`invite`](#team-invite) | Invite someone to an organisation | |
| [`update`](#team-update) | Change a member's role | |
| [`remove`](#team-remove) | End someone's membership of an organisation | `rm` |

Two verbs here break the house grammar on purpose. `remove` is not `delete`, because `delete` invites the reading that the *person* is deleted rather than their membership. `invite` exists because sending one is how a team gains a member and no house verb covers it - and it shares [`invite create`](/docs/reference/cli/cloud/commands/invite#invite-create)'s implementation rather than copying it.

The API has no route for a single member, so `get`, `update` and `remove` fetch the member list and match locally, by user id or username, with did-you-mean suggestions when nothing matches. The display name is never a key, because it is neither unique nor stable.

This group declares the scopes `read:cloud` and `write:cloud-organization`, the same pair as [`org`](/docs/reference/cli/cloud/commands/org) and [`invite`](/docs/reference/cli/cloud/commands/invite), because the API has no separate scope for membership. A personal access token cannot use the mutating verbs: see [Authentication](/docs/reference/cli/cloud/authentication#what-a-personal-access-token-cannot-do).

## surreal cloud team list {#team-list}

List the members of an organisation.

<Synopsis>
surreal cloud team list [OPTIONS]
</Synopsis>

This command takes no positional argument. The organisation comes from `--org` and the [precedence chain](/docs/reference/cli/cloud/global-flags#the-precedence-chain).

Accepts the [list presentation flags](/docs/reference/cli/cloud/output-and-exit-codes#list-presentation-flags) and nothing else. Column ids are `username`, `name` and `role`, with `user_id` and `profile_picture` under `--wide`.

```bash
surreal cloud team list
```

```text title="Output"
USERNAME             NAME            ROLE
ana@acme.example     Ana Silva       owner
bo@acme.example      Bo Nakamura     admin
cai@acme.example     Cai Oduya       member
```

```bash title="Owners and admins only"
surreal cloud team list --json | jq -r '.[] | select(.role != "member") | .username'
```

## surreal cloud team get {#team-get}

Show one member.

<Synopsis>
surreal cloud team get [OPTIONS] <MEMBER>
</Synopsis>

<OptionsTable
    title="Arguments"
    options={[
        {
            "name": "<MEMBER>",
            "required": true,
            "description": "The member, by username or user id."
        }
    ]}
/>

This command has no options of its own.

```bash
surreal cloud team get bo@acme.example
```

A reference that does not match any member exits `5`, and lists the near matches it found. The detail view shows the username, role, user id and organisation id.

## surreal cloud team invite {#team-invite}

Invite someone to an organisation.

<Synopsis>
surreal cloud team invite [OPTIONS] --role <ROLE> <EMAIL>
</Synopsis>

<OptionsTable
    title="Arguments"
    options={[
        {
            "name": "<EMAIL>",
            "required": true,
            "description": "The email address to invite."
        }
    ]}
/>

<OptionsTable
    title="Options"
    options={[
        {
            "name": "--role",
            "value": "<ROLE>",
            "required": true,
            "description": "The role to grant. Run `surreal cloud org roles` for the ones this organisation defines."
        }
    ]}
/>

```bash
surreal cloud team invite dee@acme.example --role member
```

The answer is the invitation, not a member - the person appears in [`team list`](#team-list) only once they accept. Track it in the meantime with [`invite list`](/docs/reference/cli/cloud/commands/invite#invite-list).

**Refusals**, exit `2`, before any request. The address validator is deliberately shallow - an `@` with something either side and no internal whitespace - because the API is the authority on deliverability:

```text
`dee.acme.example` is not an email address: it has no `@`.
```

The role vocabulary is per organisation, so only an empty value is refused locally:

```text
A role cannot be empty. Run `surreal cloud org roles` to see the ones this organization defines.
```

A role the API rejects as invalid is annotated with a pointer to [`org roles`](/docs/reference/cli/cloud/commands/org#org-roles) - but only for that class of error, never for a 403 or a rate limit, where the role is not the problem.

An invitation is not retried automatically, because a repeat would send a second email with a second working code.

## surreal cloud team update {#team-update}

Change a member's role.

<Synopsis>
surreal cloud team update [OPTIONS] --role <ROLE> <MEMBER>
</Synopsis>

<OptionsTable
    title="Arguments"
    options={[
        {
            "name": "<MEMBER>",
            "required": true,
            "description": "The member, by username or user id."
        }
    ]}
/>

<OptionsTable
    title="Options"
    options={[
        {
            "name": "--role",
            "value": "<ROLE>",
            "required": true,
            "description": "The new role. Run `surreal cloud org roles` for the ones this organisation defines."
        }
    ]}
/>

```bash
surreal cloud team update cai@acme.example --role admin
```

The command prints the updated member. The role is compared exactly as written: if the member already holds it, the command prints a note that nothing changed, sends no request and exits `0`.

## surreal cloud team remove {#team-remove}

End someone's membership of an organisation.

<Synopsis>
surreal cloud team remove [OPTIONS] <MEMBER>
</Synopsis>

<OptionsTable
    title="Arguments"
    options={[
        {
            "name": "<MEMBER>",
            "required": true,
            "description": "The member, by username or user id."
        }
    ]}
/>

<OptionsTable
    title="Options"
    options={[
        {
            "name": "--force",
            "description": "Remove without confirming."
        }
    ]}
/>

```bash title="With a confirmation"
surreal cloud team remove cai@acme.example
```

```bash title="From an offboarding script"
surreal cloud team remove cai@acme.example --force --json
```

This ends a membership. It does not delete the person's SurrealDB account, and it does not touch anything they created.

**Refusals.** The confirmation names the person and the organisation, and says that the account is not deleted. Declining prints `Nothing was changed.` and exits `0`. Removing yourself prints a warning first, because only another member can invite you back. In a non-interactive session without `--force` or `--yes`, it exits `2` having sent nothing.
