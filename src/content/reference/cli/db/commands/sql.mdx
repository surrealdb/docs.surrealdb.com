## Example usage

To start an interactive REPL, run the `surreal db sql` command with the required arguments. Once you see the `>` character you can type SurrealQL, followed by the `enter` key. The command has support for `↑` and `↓` arrows for selecting previous SQL statements, and stores the statement history in a `history.txt` file. To exit the REPL, use the `ctrl + c` or `ctrl + d` key combinations.

```bash
surreal db sql --endpoint http://localhost:8000 --namespace main --database main --auth-level root --username username --password password
```

For a one-shot query without staying in the REPL, pipe SurrealQL into `surreal db sql`. This is only for a small number of statements; for larger scripts use the [import command](/docs/reference/cli/db/commands/import).

<Tabs syncKey="shell">
<TabItem label="Bash">
```bash
echo 'INFO FOR DB;' | surreal db sql --endpoint http://localhost:8000 --username root --password secret --namespace main --database main --pretty --hide-welcome
```
</TabItem>
<TabItem label="PowerShell">
```powershell
'INFO FOR DB;' | surreal db sql --endpoint http://localhost:8000 --username root --password secret --namespace main --database main --pretty --hide-welcome
```
</TabItem>
</Tabs>

You can also pipe a file:

```bash
cat myfile.surql | surreal db sql --endpoint http://localhost:8000 --username root --password secret --namespace main --database main
```

### Default namespace and database

<Since v="v3.0.0" />

As the `surreal db start` command defaults to defining a namespace and database by the name `main` upon starting up, the `surreal db sql` command also connects to these two by default. As such, a command like `surreal db sql --user root --pass secret` or even just `surreal db sql` (for an instance with authentication disabled) is all that is needed to connect and begin using an instance via the CLI.

A [`USE`](/docs/reference/query-language/statements/use) statement changes the namespace and database for every statement after it in the same session, in the REPL and in piped input, so it does not need to be repeated on each line. The REPL prompt shows the current namespace and database, and the `USE` statement itself [returns them](/docs/reference/query-language/statements/use#value-returned-by-use-statement):

```text
main/main> USE NS shop DB sales;
[{ database: 'sales', namespace: 'shop' }]

shop/sales> CREATE person:one;
[[{ id: person:one }]]
```

## Using environment variables

> [!IMPORTANT]
> Most of the flags above have a corresponding [environment variable](/docs/reference/cli/db/environment-variables#command-environment-variables).
> For example, the `--database` flag can be configured with the `SURREAL_DATABASE` environment variable instead.

When using the `surreal db sql` command, you can also use environment variables to set the values for the command-line flags.

For more on the environment variables available for CLI commands or SurrealDB instances in general, see the [environment variables](/docs/reference/cli/db/environment-variables#command-environment-variables) page.

## `--auth-level` option

The `--auth-level` option sets the authentication level to use when connecting to the database. The option has three possible values: `root`, `namespace`, and `database`. The `root` value is the highest level of authentication, while the `namespace` and `database` values are used for authenticating as users defined on a specific namespace or database.

There are a few things to keep in mind when using the `--auth-level` option:

- The `root` value is used to access the database server as a root user, and if not specified is the default value.

```bash
surreal db sql --endpoint http://localhost:8000 --namespace main --database main --auth-level root --username username --password password
```

- The `namespace` value is used for accessing a specific namespace and all databases within that namespace. When this level is specified, a namespace must be provided via `--namespace`.

```bash
surreal db sql --endpoint http://localhost:8000 --namespace main --database main --auth-level namespace --username username --password password
```

- The `database` value is used for accessing a specific database within a namespace. When this level is specified, a namespace and a database must be provided via `--namespace` and `--database`.

```bash
surreal db sql --endpoint http://localhost:8000 --namespace main --database main --auth-level database --username username --password password
```

## `--token` option

The `--token` option sets the authentication token to use when connecting to the server. This option allows you to connect to SurrealDB using a JWT instead of user credentials. The token is used to authenticate the user and provide access to the database server which means it cannot be provided at the same time as `--username`, `--password` or `--auth-level`.

```bash
surreal db sql --endpoint http://localhost:8000 --namespace main --database main --token <token>
```

## Capabilities and remote connections

Both `surreal db sql` and [`surreal db start`](/docs/reference/cli/db/commands/start) accept the same capability flags (`--allow-funcs`, `--allow-eval-query`, `--allow-experimental`, and so on). **Where those flags take effect depends on how you connect.**

| Connection | Examples | Where capabilities are enforced |
| --- | --- | --- |
| **Remote server** | `ws://localhost:8000`, `http://…`, `grpc://…` with sign-in | On the **server** process started with `surreal db start` |
| **Embedded engine** | `memory`, `surrealkv://…` (no separate server) | On the **`surreal db sql` process** itself |

> [!NOTE]
> `grpc://` and `grpcs://` endpoints are accepted from SurrealDB 3.3.0. The server always mounts the gRPC transport, and the `surreal` binary now ships the client, so `surreal db sql --endpoint grpc://127.0.0.1:8000` connects without a custom build. On earlier versions the endpoint was rejected as an invalid connection string or an invalid URI.

When you use `surreal db sql` against a **running instance**, flags on the REPL command do **not** change what the server allows at execution time. Configure [`surreal db start`](/docs/reference/cli/db/commands/start) (or the server's environment variables) instead - including for [`eval::*`](/docs/reference/query-language/functions/database-functions/eval), arbitrary-query gates, and experimental features such as extensions (CLI flag: `surrealism`).

Capability flags on `surreal db sql` still matter in two cases:

- **Embedded storage** - there is no separate server; pass the flags on `surreal db sql` directly.
- **REPL syntax validation** - the client uses its capability set when checking whether a line parses before you submit it. That can affect experimental syntax in the prompt; it is **not** the security boundary for remote execution.

## Connecting to a Cloud instance

`surreal cloud instance sql <name>` wraps this command: it resolves the endpoint and credentials of a SurrealDB Cloud instance and then hands off to `surreal db sql`, passing through any flags given after `--`. Everything on this page applies to that session. See the [surreal cloud reference](/docs/reference/cli/cloud) for the control-plane side.

## Experimental capabilities

> [!NOTE]
> The experimental capability is completely hidden in the CLI help command, and `--allow-all` will not enable the experimental capabilities by default.

To use experimental capabilities, set the `SURREAL_CAPS_ALLOW_EXPERIMENTAL` [environment variable](/docs/reference/cli/db/environment-variables) to the experimental capability you want to allow.

For **embedded** `surreal db sql` (for example `surreal db sql memory`), set the variable or flag on the REPL command. For a **remote** server, set it on [`surreal db start`](/docs/reference/cli/db/commands/start#experimental-capabilities) instead - see [Capabilities and remote connections](#capabilities-and-remote-connections).

For example, to use [SurrealDB extensions](/docs/learn/extensions/plugins/overview) in an embedded session:

<Tabs syncKey="shell">

<TabItem label="Bash">
```bash
SURREAL_CAPS_ALLOW_EXPERIMENTAL=surrealism surreal db sql ...
```
</TabItem>

<TabItem label="PowerShell">
```powershell
$env:SURREAL_CAPS_ALLOW_EXPERIMENTAL = "surrealism"
surreal db sql ...
```
</TabItem>
</Tabs>

or, using the `--allow-experimental` flag:

```bash
surreal db sql -e [CONNECTION_STRING] --allow-experimental surrealism
```

Multiple experimental capabilities can be enabled by separating them with a comma.

<Tabs syncKey="shell">

<TabItem label="Bash">
```bash
SURREAL_CAPS_ALLOW_EXPERIMENTAL=surrealism,kvexport surreal db sql ...

-- OR

surreal db sql -e [CONNECTION_STRING] --allow-experimental surrealism,kvexport
```
</TabItem>

<TabItem label="PowerShell">
```powershell
$env:SURREAL_CAPS_ALLOW_EXPERIMENTAL = "surrealism,kvexport"
surreal db sql ...

-- OR

surreal db sql -e [CONNECTION_STRING] --allow-experimental surrealism,kvexport
```
</TabItem>
</Tabs>

The current experimental targets are `surrealism` and `kvexport`. [ISO GQL](/docs/learn/querying/gql/overview) is enabled by default from 3.3.0, and buckets and files are enabled by default from 4.0, so neither uses an experimental target. From 4.0, the tags `gql` and `files` are refused as invalid names, so the command does not start. 3.3 accepted `gql` and ignored it, and needed `files` to use buckets and files.

| Example feature/statement | Tag |
| --- | --- |
| [DEFINE EXTENSION](/docs/reference/query-language/statements/define/extension) | `surrealism` |

> [!NOTE]
> When connecting to a **remote** server (`ws://`, `http://`, …), experimental features are enforced on the server. Configure them with [`surreal db start`](/docs/reference/cli/db/commands/start#experimental-capabilities) (or the server's `SURREAL_CAPS_ALLOW_EXPERIMENTAL`). Flags on `surreal db sql` only affect [embedded connections](#capabilities-and-remote-connections) or REPL parse validation. From 3.3.0, [ISO GQL](/docs/learn/querying/gql/overview) does not need an experimental flag; `eval::gql` still needs [`--allow-eval-query`](/docs/learn/security/authorization/capabilities#eval-queries) on the server.
