This page is divided into two views: the details of the `surreal db start` command itself, and a builder that creates a command based on the options you choose.

The root user from `--username` and `--password`, and the default namespace and database, are created only when the datastore is new, and are stored in it. Starting the same datastore again with other values changes nothing: the existing root user keeps its password, and no new namespace or database is created. To change the password of an existing root user, use [`ALTER USER`](/docs/reference/query-language/statements/alter/user) or [`DEFINE USER OVERWRITE`](/docs/reference/query-language/statements/define/user).

`surreal db start` has more options than any other subcommand, and the table above covers the ones described on this page. The remaining groups - database tuning, datastore TLS, HTTP server, capabilities, and logging - are listed in full in the [command help](#command-help) below, and mapped to their variables on the [environment variables](/docs/reference/cli/db/environment-variables) page.

Three of the flags above are documented in more detail elsewhere: `--postgres-bind` exposes the [Postgres wire protocol](/docs/reference/rest-api/postgres-protocol), `--mysql-bind` exposes the [MySQL wire protocol](/docs/reference/rest-api/mysql-protocol), and the `--durable-*` flags are explained under [Durable HTTP RPC sessions](#durable-http-rpc-sessions). From SurrealDB 3.1, the `Forwarded` value for `--client-ip` reads the RFC 7239 `Forwarded` header.

The `--query-timeout` flag in the [command help](#command-help) sets the maximum duration that a batch of statements can run for, and is off by default. From 3.3.0 the same value is also a hard wall-clock limit on each HTTP `/sql`, `/gql` and `/graphql` request and on each RPC method call. An HTTP `/sql` or `/gql` request that exceeds it is answered with `504 Gateway Timeout`, and a `/graphql` request with a GraphQL error. The `begin`, `commit` and `cancel` RPC methods are exempt, but the calls made inside the transaction they control are still limited individually. See [`SURREAL_QUERY_TIMEOUT`](/docs/reference/cli/db/environment-variables#command-environment-variables).

## Getting started

This example will show how to host a SurrealDB server with the `surreal db start` command, and then access the Surreal DB server using the [`surreal db sql` command](/docs/reference/cli/db/commands/sql).

To start a SurrealDB server, run the `surreal db start` command, using the options below. This example stores the database in memory, with a username and password, hosted at `127.0.0.1:8000` (the default location).

```bash
surreal db start memory --user my_username --pass my_password
```

The server is actively running, and can be left alone until you want to stop hosting the SurrealDB server.

> [!NOTE]
> The message "Started web server on 127.0.0.1:8000", indicates where the server is being hosted and can be accessed by clients. The location `127.0.0.1:8000` is the default, and can be manually changed by specifying the `--bind` option of the `surreal db start` command.

To access the SurrealDB server that you have started hosting, open a new terminal which will act as the client, while the previous terminal is still running the `surreal db start` command described above. This is done using a separate [`surreal db sql`](/docs/reference/cli/db/commands/sql) command. Ensure that the hosting location indicated by the output of the `surreal db start` command is passed to the `--endpoint` argument, and that you specify the same `--username` and `--password` as in the `surreal db start` command.

A particular namespace and database can be specified at this point, as seen below.

```bash
surreal db sql --endpoint http://127.0.0.1:8000 --namespace my_namespace \
  --database my_database --username my_username --password my_password
```

## Positional argument

> [!WARNING]
> FoundationDB support was removed in SurrealDB 3.0.0, so `fdb://` paths are only accepted by 2.x. Migrate a FoundationDB deployment to one of the backends below before upgrading.

In the `surreal db start` command, the path argument is used to specify the location of the database. If no argument is given, the default of `memory` for storage [in memory](/docs/running/in-memory) is assumed.

Arguments for persistent backends are a combination of the backend name, a `:` or `://`, and an address or filename - for example `surrealkv://mydb` or `surrealkv:database`. The available backends are:

<Tabs syncKey="surrealkv-version">
<TabItem label="SurrealDB 4.0 and later">

- `memory` (or no argument) for in-memory storage
- `surrealkv` for SurrealKV, the on-disk backend
- `tikv` for TiKV

SurrealDB 4.0 removed the `rocksdb` and `indxdb` backends. The `rocksdb://` and `indxdb://` schemes are kept as deprecated spellings of `surrealkv://`: a path that names either is opened with SurrealKV, and the server logs a warning to use `surrealkv://` instead. Starting the server on a RocksDB data directory, with either scheme, converts it to SurrealKV. See [Moving a RocksDB database to SurrealKV](/docs/manage/self-hosted/deployment-models#moving-a-rocksdb-database-to-surrealkv).

</TabItem>
<TabItem label="Before SurrealDB 4.0">

- `memory` (or no argument) for in-memory storage
- `surrealkv` for SurrealKV
- `rocksdb` for RocksDB, the recommended on-disk backend
- `indxdb` for IndexedDB
- `tikv` for TiKV

### Absolute vs. relative paths

The datastorage flavour (`surrealkv`, `tikv`, etc.) followed by `:` or `://` will be recognised as a relative path, which is resolved from the directory you run `surreal db start` in. Running `surreal db start surrealkv:mydb` from `/home/ann/projects` stores the data in `/home/ann/projects/mydb`, and running the same command from another directory creates a new, empty database there. Use an absolute path for a server that is started from different places, such as by a service manager. Any other number of slashes such as `surrealkv:/path` or `surrealkv:///path` will be interpreted as an absolute path. As a short absolute path of this nature will often require elevated permissions, the output for this command may end in this sort of error.

```text
There was a problem with the datastore: IO error: Read-only file system (os error 30)
```

If you see this error without having intended to start the server on an absolute path, it is likely that the path passed in unintentionally contains either one slash or more than two slashes.

> [!NOTE]
> Be sure not to point two storage backends at the same location. As storage is entirely delegated to the backend, the CLI is not aware of the structure of the data itself. While each backend uses its own file names and directory structure to store data, it is possible that data overwrite or other issues may occur. The one deliberate exception is a RocksDB directory from before 4.0, which SurrealKV converts when it opens it.

> [!IMPORTANT]
> **TiKV** (`tikv://…`) is supported for local multi-node experimentation with the Community edition. Production multi-node HA uses distributed storage on [SurrealDB Cloud Scale](https://surrealdb.com/pricing/scale) or [SurrealDB Enterprise](https://surrealdb.com/enterprise). See [Run a multi-node cluster](/docs/running/multi-node) and [Deployment](/docs/manage/self-hosted/deployment-models). To provision and scale those instances from a script rather than a browser, see [`surreal cloud`](/docs/reference/cli/cloud).

## Datastore configuration

<Tabs syncKey="surrealkv-version">

<TabItem label="SurrealDB 4.0 and later">

Configuring a datastore is done by passing in a string that begins with the datastore name, a path if persistent storage is needed, and optional parameters. Some examples:

```bash
surreal db start --user root --pass secret "surrealkv://path/to/db?versioned=true&sync=every&retention=30d"
surreal db start --user root --pass secret "mem://tmp/data?aol=sync&snapshot=60s&sync=5s"
```

Each database store supports different parameters.

### Supported parameters for Memory (SurrealMX)

The memory backend does not support versioned queries. From 3.3.0 a server started on it with `versioned=true` or a non-zero `retention`, whether through the parameters or the matching `SURREAL_DATASTORE_VERSIONED` and `SURREAL_DATASTORE_RETENTION` environment variables, fails to start. `versioned=false` and a zero retention are accepted. To use the [`VERSION` clause](/docs/reference/query-language/statements/select#the-version-clause), start the server on SurrealKV instead.

- `aol` (`never`, `sync`, or `async`), for writing changes to an append-only log file
- `snapshot` (a duration string, e.g. `60s`), for periodically writing a snapshot of the database to the file system
- `sync` (`never`, `every`, or a duration string like `5s`), for specifying when to flush the append-only log file to the file system
  - `never` - (default) leave flushing to the OS (least durable)
  - `every` - sync on every commit (most durable)
  - `interval` - periodic background flushing at the given interval

Persistence for the memory backend is used for the following:

- Append-Only Log (AOL) - Synchronous/asynchronous modes for durability
- Snapshots - Periodic full database state capture
- Data Recovery - Automatic recovery from snapshots + AOL on startup
- AOL Truncation - Automatic cleanup after snapshots

### Supported parameters for SurrealKV
- `versioned` (`true` or `false`)
- `retention` (a duration string, e.g. `30d`, `24h`, `30m`)
- `sync` (`never`, `every`, or a duration string like `5s`), for specifying when to flush the database to the file system
  - `every` - (default) sync each transaction to disk before it is confirmed (most durable)
  - `never` - leave flushing to the OS (least durable)
  - `interval` - periodic background flushing at the given interval

With `sync=every`, a commit becomes visible to other transactions only once it is durable on disk.

### Storage engine settings

Any setting of the storage engine can also go in the path, named without its `SURREAL_<ENGINE>_` prefix. For SurrealKV, `block_cache_capacity` sets [`SURREAL_SURREALKV_BLOCK_CACHE_CAPACITY`](/docs/reference/cli/db/environment-variables#surrealkv-environment-variables) and `max_memtable_size` sets `SURREAL_SURREALKV_MAX_MEMTABLE_SIZE`. This caps the block cache at 256 MiB and each memtable at 64 MiB:

```bash
surreal db start --user root --pass secret "surrealkv://path/to/db?block_cache_capacity=268435456&max_memtable_size=67108864"
```

A setting in the path takes precedence over the same setting made by an environment variable. At startup the server logs the values SurrealKV uses, as in `Setting block cache capacity: 268435456`, so the log shows which one applied.

## Authentication

When starting a SurrealDB instance, authentication is enabled by default, and your user credentials will be required to connect. If you are starting a new instance, the user credentials you use to run the `start` command will [define a new root user](/docs/reference/query-language/statements/define/user#roles) with the [`OWNER`](/docs/reference/query-language/statements/define/user#roles) role.

```bash
surreal db start --user root --password secret
```

## Unauthenticated mode

> [!NOTE]
> We recommend enabling authentication when running SurrealDB in production or in publicly exposed ways. Failure to do so may result in unauthorised access.

Using the `--unauthenticated` flag, you can also start a SurrealDB instance in unauthenticated mode. By doing so, authentication will be disabled. In this mode, any guest user is considered to have the same permissions as a root user with the [`OWNER`](/docs/reference/query-language/statements/define/user#roles) role.

To start a SurrealDB instance in unauthenticated mode, run the following command:

```bash
surreal db start --unauthenticated
```

## Using environment variables

> [!IMPORTANT]
> Most of the flags above have a corresponding [environment variable](/docs/reference/cli/db/environment-variables#command-environment-variables).
> For example, the `--temporary-directory` flag can be configured with the `SURREAL_TEMPORARY_DIRECTORY` environment variable instead.

When using the `surreal db start` command, you can also use environment variables to set the values for the command-line flags. This is useful when you want to set the values for the command-line flags without having to pass them directly on the command line.

For more on the environment variables available for CLI commands or SurrealDB instances in general, see the [environment variables](/docs/reference/cli/db/environment-variables#command-environment-variables) page.

## Stopping the server

To stop the server, press `Ctrl+C` in its terminal, or send it `SIGTERM` (as `docker stop`, `kill` and `systemctl stop` do). Either signal starts a graceful shutdown: the server stops accepting connections, the storage engine writes out what it holds in memory, and the process exits with status `0`.

```text
WARN surrealdb::net: SIGINT received. Waiting for a graceful shutdown. A second signal will force an immediate shutdown.
INFO surrealdb::net: Web server stopped. Bye!
```

A second signal during the shutdown stops the process at once, without waiting. On a persistent backend such as SurrealKV, data from committed transactions is kept either way, subject to the backend's [`sync` setting](#datastore-configuration). On the in-memory backend, all data is lost when the process stops unless [persistence](#supported-parameters-for-memory-surrealmx) is configured.

## Enabling capabilities

> [!NOTE]
> If using SurrealDB Cloud, capabilities can be set from [SurrealDB Studio](/docs/manage/instances/configure#capabilities) or with [`surreal cloud`](/docs/reference/cli/cloud).

Capabilities arguments such as `allow-scripting` or `deny-net` can also be passed into the `surreal db start` command. These arguments, the order in which they are evaluated, and other notes on security are presented in detail in a [separate page on capabilities](/docs/learn/security/authorization/capabilities). From SurrealDB 4.0, the server logs the capabilities it starts with, and logs a warning at startup for `--allow-all`, guest access, scripting and network access to every target, as described in [Capabilities in the startup log](/docs/learn/security/authorization/capabilities#capabilities-in-the-startup-log).

A production-oriented example of the `surreal db start` command that begins with the `--deny-all` flag and only thereafter sets which capabilities will be allowed:

```bash
surreal db start --deny-all --allow-funcs "array, string, crypto::argon2, http::get" --allow-net api.example.com
```

## Strict mode

Versions before SurrealDB 3.0 contained a flag to start the entire server in strict mode. When running in strict mode, no `NAMESPACE`, `DATABASE`, or `TABLE` definitions were enacted automatically when data is inserted. Any queries would return an error if the selected namespace, database, or table were not specifically defined in advance.

```bash
surreal db start --strict --log debug memory
```

Since SurrealDB 3.0, strict mode is now enacted on the database level via a [`DEFINE DATABASE`](/docs/reference/query-language/statements/define/database) statement.

```surql
DEFINE DATABASE my_anything_goes_db;
DEFINE DATABASE my_strict_db STRICT;
```

## Experimental capabilities

> [!NOTE]
> The experimental capability is completely hidden in the CLI help command, and `--allow-all` will not enable the experimental capabilities by default.

For example, to use [Surrealism](/docs/learn/extensions/plugins/overview) extensions, set the `SURREAL_CAPS_ALLOW_EXPERIMENTAL` environment variable to `surrealism` - or pass it in via the `--allow-experimental` flag.

`--allow-experimental` accepts several values, so a storage path written after it is read as one more capability name, and the server refuses to start with `invalid experimental target name`. Join the value to the flag with `=`, or put the path before the flag:

```bash
surreal db start --allow-experimental=surrealism,files surrealkv:mydatabase.db
surreal db start surrealkv:mydatabase.db --allow-experimental surrealism,files
```

> [!NOTE]
> Experimental capabilities are enforced on the **server** for remote clients. If you use [`surreal db sql`](/docs/reference/cli/db/commands/sql) against `ws://` or `http://`, configure flags here - not only on the REPL. See [Capabilities and remote connections](/docs/reference/cli/db/commands/sql#capabilities-and-remote-connections).

> [!NOTE]
> From **3.3.0**, [ISO GQL](/docs/learn/querying/gql/overview) is enabled by default and no longer uses an experimental capability. From 4.0, `--allow-experimental gql` is refused with `invalid experimental target name` and the server does not start, so remove `gql` from the list. On 3.3.x the tag is accepted and has no effect, and on **3.2.x** it enables GQL.

| Example feature/statement | Tag |
| --- | --- |
| [DEFINE BUCKET](/docs/reference/query-language/statements/define/bucket) | `files` |
| [DEFINE EXTENSION](/docs/reference/query-language/statements/define/extension) | `surrealism` |
| The `POST /kvexport` HTTP route, which streams the stored keyspace to the root owner | `kvexport` |

## Identification headers

By default, SurrealDB includes headers in the HTTP response that identify the server name and version. You can suppress these headers by using the `--no-identification-headers` flag.

```bash
surreal db start --no-identification-headers
```

## Durable HTTP RPC sessions

<Since v="v3.2.2" />

<Tabs syncKey="surrealkv-version">
<TabItem label="SurrealDB 4.0 and later">

Every client-attached session on the HTTP [`/rpc`](/docs/reference/rest-api/rpc-protocol) endpoint is stored in the datastore. A session survives a restart, and any node that shares the same storage can serve it, so a load-balanced deployment does not need sticky routing. Requests from several nodes on the same session can run at the same time: each request writes its changes back only if the stored session has not changed meanwhile, and otherwise merges them onto the newer copy.

A session expires between one and one and a half times `--durable-session-ttl` (default `24h`) after its last request. An expired session is refused when it is loaded. A background task removes expired entries from the datastore (`--durable-session-gc-interval`, default `1h`; set `0` to disable the sweep).

```bash
surreal db start --durable-session-ttl 12h surrealkv://mydb
```

The `--durable-sessions` flag and `SURREAL_DURABLE_SESSIONS` are still accepted so that existing configurations keep starting, but have no effect, and the server logs a deprecation warning. Each node keeps at most [`SURREAL_HTTP_MAX_ATTACHED_SESSIONS`](/docs/reference/cli/db/environment-variables#http-server-config) sessions attached through it.

> [!WARNING]
> The stored session includes its authentication state and is stored **unencrypted** in the datastore.

</TabItem>
<TabItem label="Before SurrealDB 4.0">

Client-attached sessions on the HTTP [`/rpc`](/docs/reference/rest-api/rpc-protocol) endpoint normally live only in the process memory of the node that created them. After a restart, or when a later request is routed to a different node, the client receives a session-not-found error.

The `--durable-sessions` flag can be used to store those sessions in the datastore so they survive restarts and can be resumed on any node that shares the same storage. Each use refreshes a sliding idle TTL (`--durable-session-ttl`, default `24h`). A background task removes expired entries (`--durable-session-gc-interval`, default `60s`; set `0` to disable the sweep). Expired sessions are still dropped when loaded.

```bash
surreal db start --durable-sessions --durable-session-ttl 12h surrealkv://mydb
```

> [!WARNING]
> The durable copy includes the session's authentication state and is stored **unencrypted** in the datastore. Sticky routing is recommended so a given session is used on one node at a time. Concurrent use from multiple nodes is best-effort.

</TabItem>
</Tabs>

WebSocket connections keep in-memory sessions only. Durable sessions do not change WebSocket behaviour.

## Further examples

As `surreal db start` is the command with by far the largest number of options, a few more examples will help give an idea of what sort of configurations are available.

An instance with a single root user, able to connect to the internet but unable to use three functions:

```bash
surreal db start --user root --pass secret --allow-net --deny-funcs "crypto::md5, http::post, http::delete"
```

An instance with more verbose logging that uses SurrealKV as its storage engine:

```bash
surreal db start --log debug surrealkv:mydatabase.db
```

An instance with all capabilities denied except a few functions and a single endpoint:

```bash
surreal db start --deny-all --allow-funcs "array, string, crypto::argon2, http::get" --allow-net api.example.com
```

An instance with a different default address, less verbose logging level, and ability to use JavaScript functions:

```bash
surreal db start --bind 0.0.0.0:2218 --log warn --allow-scripting
```
