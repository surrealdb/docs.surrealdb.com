# Installation

`surrealctl` is a single self-contained executable with no runtime dependencies. It is published for macOS, Linux and Windows on both `arm64` and `amd64`, and the same binary serves interactive use and CI.

`surrealctl` is a separate executable from [`surreal`](/docs/running/installation). Installing one does not install the other, and the two can be upgraded independently.

> [!NOTE]
> Release assets are published under `https://download.surrealdb.com/surrealctl/`. If a package manager on your platform reports the package as unavailable, take the binary from that prefix directly using the [direct download](#direct-download) steps below.

## Install using the install script

The install script picks the right asset for your platform and CPU, verifies the download over TLS, and installs into `/usr/local/bin`, falling back to a directory you choose when that is not writable. It works on macOS and on Linux.

```bash
curl -sSf https://install.surrealdb.com/surrealctl | sh
```

### Installing a specific version

Pass a version argument (`-v` or `--version`) through to the script.

```bash
curl -sSf https://install.surrealdb.com/surrealctl | sh -s -- -v v0.1.0
```

### Updating

Re-run the script. It replaces the installed binary with the current release.

```bash
curl -sSf https://install.surrealdb.com/surrealctl | sh
```

## Install using Homebrew

[Homebrew](https://brew.sh/) works on both macOS and Linux.

```bash
brew install surrealdb/tap/surrealctl
```

```bash title="Updating"
brew upgrade surrealdb/tap/surrealctl
```

## Install on Windows

The Windows install script downloads the current release and installs it into `C:\Program Files\SurrealDB`, falling back to a directory you choose.

```powershell
iwr https://windows.surrealdb.com/surrealctl -useb | iex
```

If you already use a package manager, either of the following works.

```powershell title="Chocolatey"
choco install surrealctl
```

```powershell title="Scoop"
scoop install surrealctl
```

```powershell title="Updating"
choco upgrade surrealctl
scoop update surrealctl
```

## Direct download

Every release is published under `https://download.surrealdb.com/surrealctl/`, with the current version recorded in `latest.txt`. This is the path to use in a container image or an air-gapped build, where piping a script into a shell is not acceptable.

```bash title="Download the current release for macOS on Apple silicon"
VERSION=$(curl -sSf https://download.surrealdb.com/surrealctl/latest.txt)
curl -sSfL "https://download.surrealdb.com/surrealctl/${VERSION}/surrealctl-${VERSION}.darwin-arm64.tgz" \
    | tar -xz -C /usr/local/bin
```

Assets follow one naming pattern, `surrealctl-<version>.<platform>`:

| Platform | Asset suffix |
| --- | --- |
| macOS, Apple silicon | `darwin-arm64.tgz` |
| macOS, Intel | `darwin-amd64.tgz` |
| Linux, `arm64` | `linux-arm64.tgz` |
| Linux, `amd64` | `linux-amd64.tgz` |
| Windows, `amd64` | `windows-amd64.exe` |

## Build from source

`surrealctl` is written in Rust and builds with a stable toolchain from 1.95 onwards. Building it yourself is the right choice for an unsupported platform, or when you want a binary compiled against your own toolchain.

```bash title="From crates.io"
cargo install --locked surrealctl
```

```bash title="From a clone"
git clone https://github.com/surrealdb/surrealctl
cd surrealctl
cargo install --path .
```

`cargo install` places the binary in `~/.cargo/bin`, which must be on your `PATH`.

## Confirm the installation

`surrealctl version` reports the build without touching the network.

```bash
surrealctl version
```

```text title="Output"
surrealctl  0.1.0
Commit      9f3c1ab
Built       2026-08-11
Target      aarch64-apple-darwin
```

`surrealctl status` — also spelled `surrealctl doctor` — checks your credential, the API, the resolved organisation and the `surreal` binary, and reports each one as a row. It is the command to run first when something is not behaving.

```bash
surrealctl status
```

```text title="Output"
CHECK            OK   DETAIL
credential       yes  login session, access token valid for 42m
api              yes  reachable, version 3.2.4
version          yes  0.1.0 meets the 0.1.0 minimum
cloud session    yes  available
organization     yes  acme (67upif0m8sh1cn1p2c8t) from persisted context (`org use`)
surreal binary   yes  /opt/homebrew/bin/surreal
```

The `credential` row is the only one that always appears. A seventh `system message` row is added when the API is advertising a banner, and rows that could not be evaluated show an empty `OK` cell rather than `no`.

## Shell completion

`surrealctl completion <SHELL>` writes a completion script to stdout. Five shells are supported: `bash`, `elvish`, `fish`, `powershell` and `zsh`.

```bash title="zsh"
surrealctl completion zsh > "${fpath[1]}/_surrealctl"
```

```bash title="bash"
surrealctl completion bash > /etc/bash_completion.d/surrealctl
```

```bash title="fish"
surrealctl completion fish > ~/.config/fish/completions/surrealctl.fish
```

```powershell title="PowerShell"
surrealctl completion powershell | Out-String | Invoke-Expression
```

`completion` is the one command whose output is not a view: it emits a shell script, so `--json` does not wrap it. Piping it into `head` exits `0` rather than failing on the closed pipe.

## The `surreal` handoff

[`instance sql`](/docs/reference/cli/surrealctl/commands/instance#instance-sql), [`instance import`](/docs/reference/cli/surrealctl/commands/instance#instance-import) and [`instance export`](/docs/reference/cli/surrealctl/commands/instance#instance-export) do not speak SurrealQL. They resolve the instance, mint a database token, and become the `surreal` binary. On unix the process image is replaced, so the child inherits the terminal, the signal handlers, the exit code and the job-control state. On Windows the child is spawned and its status forwarded — the one place the two platforms differ.

The token is passed to the child in its environment, never in `argv`, because `argv` is readable through `ps` on most systems and lands in shell history. `surrealctl` sets `SURREAL_TOKEN`, `SURREAL_NAMESPACE` and `SURREAL_DATABASE` for the child; the endpoint goes on the command line, because `surreal` reads no environment variable for it.

### Where the binary is looked for

Four locations, in order. The first one that resolves wins.

1. `surreal_binary` in the active profile of `config.toml`
2. `SURREALCTL_SURREAL_BINARY`
3. `surreal` on your `PATH`
4. `<config dir>/bin/surreal` — the copy `surrealctl` manages

A path you configured explicitly and that does not resolve is a hard error, not a fallback: silently running a different binary than the one you named is how the wrong version gets blamed.

```bash title="Point at a specific build"
surrealctl config set surreal_binary /opt/surrealdb/3.2.4/surreal
```

### The automatic download

If `surreal` is nowhere to be found and someone is present to answer, `surrealctl` offers to fetch a copy.

```text
$ surrealctl instance sql api
`surrealctl instance sql` hands off to the `surreal` binary, and it is not installed.
? Download it from https://download.surrealdb.com now? (y/N)
```

Accepting installs into `<config dir>/bin/` — `~/.config/surrealctl/bin/` on a default unix setup — never `/usr/local/bin`, so it needs no `sudo`. That directory is the **last** place the binary is looked for, below `PATH`, so installing `surreal` properly later takes over with nothing to undo. When the directory is not on your `PATH`, `surrealctl` says so and leaves your shell profile alone.

The offer only appears when it can be answered. `--yes` does not reach it: that flag pre-answers confirmations, not an unattended download from a host the invocation never named. In a non-interactive session the command fails with the install instructions instead.

```text
Could not find the `surreal` binary.

`surrealctl instance sql` hands off to it rather than reimplementing SurrealQL.
Install it with:
  curl -sSf https://install.surrealdb.com | sh

Or point at an existing copy with SURREALCTL_SURREAL_BINARY, or `surrealctl config set surreal_binary <path>`.
```

`surrealctl status` reports which `surreal` is in use, and reports it without offering to download anything — a diagnostic should not fetch a binary.
