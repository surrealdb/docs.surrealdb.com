# Metrics reference

This page is the canonical reference for every metric emitted by SurrealDB. It covers how operators access them, the labels and naming rules that govern the surface, the full catalogue grouped by signal family, the public allowlist for anonymous scrapers, and the migration table from 3.0 names.

The instruments listed below were introduced as part of the 3.1 observability overhaul. The [Migration from 3.0](#migration-from-30) section at the bottom maps every legacy Prometheus name to its current replacement.

## Access paths

Metrics can be exposed in two complementary ways. Both pipelines can run simultaneously.

### Prometheus pull

| Property | Value |
| --- | --- |
| Trigger | `SURREAL_METRICS_ENABLED=true` (default) |
| Transport | `GET /metrics` on the main HTTP port, content-type `text/plain; version=0.0.4` |
| Authentication | Root credentials gate the full surface. Anonymous scrapers receive the [`PUBLIC_METRICS`](#public-metrics-allowlist) allowlist only. |
| Surface | Every instrument the running build registers. |

Disable the endpoint by setting `SURREAL_METRICS_ENABLED=false` - the route then returns `404`.

### OTLP push

| Property | Value |
| --- | --- |
| Trigger | `SURREAL_TELEMETRY_PROVIDER=otlp` |
| Transport | gRPC, default endpoint `http://localhost:4317`, push cadence from `OTEL_METRIC_EXPORT_INTERVAL` (milliseconds; default `60000`), cumulative temporality |
| Authentication | The collector's responsibility. The exporter speaks gRPC and native-TLS but does not enforce client authentication. |
| Surface | The same instruments as `/metrics`, plus the OTel logs surface (audit and slow-query records, when their OTel export is enabled) and `tracing` spans. |

Selectively disable parts of the OTLP pipeline:

- `SURREAL_TELEMETRY_DISABLE_METRICS=true` - suppress the OTLP metrics reader, leaving logs and traces unaffected.
- `SURREAL_TELEMETRY_DISABLE_TRACING=true` - suppress the OTLP trace exporter, leaving metrics and logs unaffected.

For the full environment variable reference, see [Configuration](/docs/manage/observability/configuration#core-knobs).

## Render rules

OpenTelemetry instrument names use a dotted form (`surrealdb.statement.duration`). The Prometheus text exporter converts each instrument deterministically:

- Counters get a `_total` suffix.
- Histograms and counters with unit `s` get a `_seconds` suffix.
- Histograms and counters with unit `By` get a `_bytes` suffix.
- Up-down counters render as plain gauges with no suffix.
- Attribute keys containing dots (`http.request.method`, `http.route`, `rpc.method`) are sanitised to underscore form at render time.

The cadence of the process snapshot can be tuned with `SURREAL_PROCESS_METRICS_REFRESH_INTERVAL` (seconds; default `5`, floored at 1).

The four `surrealdb_process_memory_*_bytes` gauges are not on the [public allowlist](#public-metrics-allowlist), because together they show how close an instance is to refusing queries, so only an authenticated scrape returns them. The same is true of the refusal counter and the engaged gauge. The allocated and threshold gauges are available from 3.2.5, the requested and reserved gauges from 3.3.0, and the refusal counter and the engaged gauge from 3.3.5. The allocated, requested and reserved gauges report `0` in a build compiled without allocation tracking. Read together, they answer three questions:

- `surrealdb_process_memory_allocated_bytes / surrealdb_process_memory_threshold_bytes` is how close the instance is to the threshold. Once tracked memory passes it, queries fail with a memory threshold error.
- `surrealdb_process_memory_bytes - surrealdb_process_memory_allocated_bytes` is resident memory the tracker cannot see, such as allocator overhead and thread stacks. This is the headroom to leave between `SURREAL_MEMORY_THRESHOLD` and a container memory limit.
- `surrealdb_process_memory_reserved_bytes - surrealdb_process_memory_requested_bytes` is internal fragmentation. Use the reserved gauge rather than the allocated one here, because the allocated gauge also counts the external reporters.

### Bucket - `surrealdb.bucket`

<Edition value="community" /> <Since v="v3.3.0" />

Bucket operations run below the session layer, so these families carry no `namespace`, `database` or `user` labels. ### Index compaction - `surrealdb.index`

<Edition value="community" /> <Since v="v4.0.0" />

Count, full-text, HNSW and DiskANN indexes keep each write as a pending update. A background compaction pass later merges the pending updates into the index. Until then, every query that uses the index must read the pending updates too, so a backlog makes queries slower. These metrics show whether compaction keeps up with writes.

Every metric is labelled by the kind of index, never by the index itself, so the number of series is fixed. None of them is on the [public allowlist](#public-metrics-allowlist), so only a scrape with root credentials returns them. To check one index, use [`INFO FOR INDEX`](/docs/reference/query-language/statements/info#index-information).

| Name | Type | Labels | Notes |
| --- | --- | --- | --- |
| `surrealdb_index_compaction_pass_total` | counter | `kind`, `trigger`, `outcome` | Compaction passes, one for each pass over one index. |
| `surrealdb_index_compaction_pass_duration_seconds` | histogram | `kind`, `trigger`, `outcome` | Duration of each pass. |
| `surrealdb_index_compaction_plans_total` | counter | `kind`, `mode` | Committed compaction steps that merged at least one pending update. |
| `surrealdb_index_compaction_plan_duration_seconds` | histogram | `kind`, `mode` | Duration of each of those steps. |
| `surrealdb_index_compaction_pending_keys_folded_total` | counter | `kind`, `mode` | Pending updates that those steps merged into the index. |
| `surrealdb_index_compaction_retries_total` | counter | `kind`, `reason` | Steps that had to start again. |
| `surrealdb_index_compaction_unqueued_total` | counter | `kind`, `trigger` | Passes that stopped with work left and could not queue a new request for it. |
| `surrealdb_index_hnsw_cache_discards_total` | counter | - | HNSW steps that failed to commit after they changed the in-memory graph. The node drops the graph and loads it again from storage on next use. |
| `surrealdb_index_pending_keys_read` | histogram | `kind` | Pending updates that one query read merged. A read that merged none records nothing, so `_count` counts reads that met a backlog, not all reads. A BM25 full-text search can record two values: one for its terms and one for its document statistics. Buckets: `1`, `4`, `16`, `64`, `256`, `512`, `1024`, `4096`, `16384`. |

The labels take these values:

- **`kind`:** `count`, `fulltext`, `hnsw` or `diskann`. A pass that stopped before it read the index definition reports `-`.
- **`trigger`:** `queue` for the background pass over queued requests, which runs at a fixed interval and also when a write that queued compaction commits. `after_commit` for a pass that a blocking `DEFINE INDEX` or `REBUILD INDEX` runs after it commits, while it waits for its index to be ready.
- **`mode`:** `folded` for count, full-text and DiskANN steps. `staged` for an HNSW step that only adds vectors, built beside the graph and published on commit. `in_place` for an HNSW step applied to the in-memory graph directly.
- **`reason`:** `txn_conflict` when the write transaction conflicted at commit, or `lost_race` when another compaction pass merged part of the same work first.

On the two pass metrics, `outcome` is the result of the pass. It does not use the `success`, `error` and `cancelled` values of the other families:

| `outcome` | Meaning |
| --- | --- |
| `empty` | Nothing was pending, or the index was removed. |
| `short` | The pass merged everything it found. |
| `budget` | The pass reached its limit of steps, or lost its compaction lease between steps, with work left, and queued the index again. |
| `lost_race` | Other compaction passes kept changing the same work, the pass ran out of retries, and it queued the index again. |
| `fenced` | An index build owns the vector index, so the pass left the request for later. |
| `not_visible` | The index definition is not yet visible on this node while a build owns it, so the pass left the request for later. |
| `error` | The pass failed. If it failed after it ran out of retries on write conflicts, it also queued the index again. |
| `cancelled` | The pass stopped because it was cancelled, for example at shutdown. |

## Public metrics allowlist

Anonymous scrapers on `/metrics` see only the metrics on the public allowlist. Adding a metric to this list requires a security review. The six allowlisted metrics are:

- `surrealdb_build_info`
- `surrealdb_process_uptime_seconds`
- `surrealdb_process_memory_bytes`
- `surrealdb_process_cpu_percent`
- `target_info`
- `otel_scope_info`

Root credentials unlock the full surface for an authenticated scrape.

### Recommended cloud whitelist

For cloud and multi-tenant deployments the recommendation is a three-tier whitelist:

- **Tier 1 - Always public.** The allowlisted six above.
- **Tier 2 - Customer-visible (per-tenant, via proxy filter).** A subset of labelled families exposed to customers showing their own usage. Every metric in this tier carries `namespace` and `database` labels and the cloud proxy MUST filter on those before responding to a customer request - there is no server-side mechanism today that restricts a labelled family to a single tenant. Strip the `user` label before exposing. Suggested subset: `surrealdb_statement_*`, `surrealdb_transaction_total`, `surrealdb_transaction_duration_seconds`, `surrealdb_transaction_conflicts_total`, `surrealdb_query_*`, `surrealdb_http_request_total`, `surrealdb_network_received_bytes_total`, `surrealdb_network_sent_bytes_total`, `surrealdb_live_query_active`, `surrealdb_slow_query_total`.
- **Tier 3 - Operator-only.** Everything else: all `surrealdb_ds_*`, all pipeline self-metrics, `surrealdb_rpc_*` (full method dimension), `surrealdb_auth_*` (failure rates can be probed by an attacker), `surrealdb_graphql_*`, `surrealdb_mcp_*`, `surrealdb_storage_*`, `surrealdb_bucket_*`, the index compaction metrics (`surrealdb_index_*`), `surrealdb_license_*`, the tracked-memory gauges (`surrealdb_process_memory_allocated_bytes`, `_requested_bytes`, `_reserved_bytes` and `_threshold_bytes`), `surrealdb_http_active_requests` (real-time concurrency snapshot), and the KV-layer `surrealdb_transaction_*` counters. Reach these over an internal sidecar or private network with root credentials.

## Cardinality and sensitivity

| Flag | Where it applies | Mitigation |
| --- | --- | --- |
| **Tenant-identifying** | `namespace`, `database`, `user` on every labelled family | Strip or filter at the proxy before exposing to a customer. Anonymous scrapers cannot see any family carrying these labels because the families are absent from the public allowlist. |
| **High-cardinality** | `peer` (cluster family, bounded by cluster size), `http_route`, `rpc_method` | Fine internally. External exposure should be conditional on the route or method set already being public. |
| **Workload inference** | The allowlisted process gauges (uptime, memory, CPU) | Already on the allowlist, but in a single-tenant-per-pod deployment they correlate with tenant workload. Acceptable trade-off in most architectures. |
| **PII risk** | Audit and slow-query *records* carry SQL when `*_INCLUDE_SQL=true`. The pipeline self-metrics are safe; the records themselves go to the file sink and (opt-in) OTLP logs, not to `/metrics`. | Run the [three-pass redactor](/docs/manage/observability/audit-logging#redaction); alert on `*_append_errors`. |
| **Default-deny** | Multi-tenant deployments | Set `SURREAL_METRICS_ENABLED=false` on customer-facing pods; serve scrapes from an internal sidecar bound to a non-tenant-visible interface. |

## Alert hints

A starter set for production:

- `rate(surrealdb_statement_total{outcome="error"}[5m])` rising sharply against a baseline - application or operator error spike.
- `rate(surrealdb_transaction_conflicts_total[5m])` rising - OCC pressure or retry storms.
- `rate(surrealdb_ds_consensus_fast_quorum_timeouts_total[5m]) > 0` - consensus is falling through to the slow path.
- `surrealdb_ds_replica_state != 0` for more than a few seconds - a replica is in view-change or recovery.
- `surrealdb_ds_cluster_peers_unresolved > 0` for more than a startup window - DNS or connectivity gap.
- `rate(surrealdb_audit_dropped[5m]) > 0` or `rate(surrealdb_audit_append_errors[5m]) > 0` - audit records being lost.
- `surrealdb_audit_queue_depth` sustained above ~50% of `SURREAL_AUDIT_QUEUE_CAPACITY` - sink is falling behind.
- `surrealdb_process_memory_allocated_bytes / surrealdb_process_memory_threshold_bytes > 0.9 and surrealdb_process_memory_threshold_bytes > 0` sustained - tracked memory is close to the point where queries fail.
- `increase(surrealdb_process_memory_refusals_total[5m]) > 0`, or `surrealdb_process_memory_guard_engaged_seconds > 30` - the memory threshold is refusing requests.
- `increase(surrealdb_index_compaction_unqueued_total[5m]) > 0` - a compaction pass could not queue the work it left.
- `rate(surrealdb_index_compaction_pass_total{outcome="budget"}[15m])` sustained, or `rate(surrealdb_index_pending_keys_read_sum[5m])` rising - compaction is not keeping up with writes, and queries read a growing backlog.
- `surrealdb_license_state{state="valid"} == 0` - an Enterprise node's licence is not currently verified as valid, so its next start may be refused. A `surrealdb_license_shutdown_at_seconds` series means an exit is scheduled.

Dashboards that filtered by scope should switch to the metric name (which now carries the same information, since scopes mirror the family prefix) or to the `service.edition` resource attribute, which is the authoritative edition signal.
