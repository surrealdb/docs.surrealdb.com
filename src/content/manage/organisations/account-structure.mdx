# Account structure

SurrealDB Cloud has five layers, from your company down to the data. This page shows how they fit together, who manages each one, and which layer to use when you need to keep things apart, such as production and development, two teams, or two invoices.

## The layers

Each layer sits inside the one above it. The enterprise is optional, and the data lives at the bottom, in databases.

```text
Enterprise               your company: single sign-on, verified domains, one member list (optional)
└── Organisation         members, roles, one invoice, one support plan
    ├── Instance         a running SurrealDB server, with its own size, region and version
    │   └── Namespace    a group of databases
    │       └── Database tables, records, indexes and functions
    └── Agent Memory context
```

| Layer | What it holds | Managed in | Details |
| --- | --- | --- | --- |
| Enterprise | Single sign-on, verified email domains, a company-wide member list and custom administration roles | The enterprise portal in Studio | [Enterprises](/docs/manage/enterprise) |
| Organisation | Instances, Agent Memory contexts, members, billing and a support plan | The organisation in Studio | [Organisations](/docs/manage/organisations) |
| Instance | Namespaces and databases, on one server with its own CPU, memory, storage, version, settings and backups | Studio, the CLI, and SurrealQL on the instance | [Instances](/docs/manage/instances) |
| Namespace | Databases, and the users defined at namespace level | SurrealQL on the instance | [`DEFINE NAMESPACE`](/docs/reference/query-language/statements/define/namespace) |
| Database | Tables, records, indexes, functions and the users defined at database level | SurrealQL on the instance | [`DEFINE DATABASE`](/docs/reference/query-language/statements/define/database) |

An [Agent Memory](/docs/agent-memory) context belongs to an organisation in the same way as an instance, and appears on the same invoice.

## Two layers of permissions

Two separate sets of permissions apply, and a role in one grants nothing in the other.

- **Administration** decides who can run the account in Studio: deploy and delete instances, invite members, and view or change billing. Organisation roles and enterprise roles belong here.
- **Data access** decides who can read and change data inside an instance. It is defined in each instance with [`DEFINE USER`](/docs/reference/query-language/statements/define/user) and [`DEFINE ACCESS`](/docs/reference/query-language/statements/define/access), and applications sign in through it.

| Role | Layer | What it can do |
| --- | --- | --- |
| Enterprise owner | Administration | Everything in the enterprise. One member holds it at a time, and it can be transferred. |
| Enterprise custom role | Administration | The permissions you choose over members, roles, domains, single sign-on and settings. It does not currently grant anything inside organisations. See [Enterprise roles](/docs/manage/enterprise/roles). |
| Organisation Owner | Administration | Everything in the organisation, including billing and changing other members' roles. |
| Organisation Admin | Administration | Deploy, configure, pause and delete instances, invite and remove members, and view invoices. |
| Organisation Member | Administration | View the instances and the team. |
| Database user with the Owner role | Data access | Read and change everything at its level and below, including creating other users. |
| Database user with the Editor role | Data access | Read and change everything at its level and below, except users and access tokens. |
| Database user with the Viewer role | Data access | Read everything at its level and below. |

[Members and roles](/docs/manage/organisations/members-and-roles) has the full table of what each organisation role can do.

A user defined in an instance applies at one of three levels. A root user covers the whole instance, a namespace user covers every database in its namespace, and a database user covers one database. A user can only create users at its own level or below, so a namespace Owner can create namespace and database users, and a database Owner can only create database users.

## Where to keep things apart

Each layer separates something different. Use the lowest layer that separates what you need, because each layer above it adds something to manage, such as another server to size or another invoice to pay.

| To separate | Use separate | Because |
| --- | --- | --- |
| The data of two applications, or of two environments that can share a server | Databases | A query runs against one namespace and one database, and cannot read another database's data. |
| Groups of databases, for example per team or per customer, each with its own administrators | Namespaces | A namespace user covers every database in its namespace and nothing outside it. |
| Server resources, size, region, version or backups | Instances | Everything on one instance shares its CPU, memory, storage, version and settings. |
| Root users | Instances | Each instance has its own root users. |
| Members, roles, invoices, support plans or the payment route | Organisations | Each organisation has its own member list, one invoice, its own support plan, and its own payment details or marketplace subscription. |
| Company-wide sign-in through your identity provider | An enterprise | Single sign-on and verified domains are set up once on the enterprise. |

Some common reasons to add a second instance are:

- **Different sizes:** a small instance for development and a larger one for production, each paid for at its own size.
- **Analytics:** heavy reporting queries use CPU and memory. On their own instance, a large report does not slow down the application.
- **Region or data residency:** an instance runs in one region, so data that must stay in the EU, or close to its users, goes on an instance in that region.
- **Stricter separation:** production with its own root users, its own version and its own backups.

A common setup puts production in one organisation and development and testing in another. The production organisation then has a short member list and its own invoice, while one non-production instance holds a database for each of `dev`, `test` and `uat`.

```text
Organisation: Production
└── Instance: app
    └── Namespace: main
        └── Database: prod
Organisation: Non-production
└── Instance: app-nonprod
    └── Namespace: main
        ├── Database: dev
        ├── Database: test
        └── Database: uat
```

Splitting environments into databases on one instance costs the least, but they share the server, so a load test in `test` competes with `dev` for CPU and memory. Splitting them into instances in one organisation keeps one member list and one invoice. Splitting them into organisations also separates who can deploy and delete instances.

## Single sign-on and organisation membership

Single sign-on is set up on the [enterprise](/docs/manage/enterprise/single-sign-on), and it controls how people sign in to Studio, which is the administration layer. Applications that connect to an instance sign in through the data access layer instead, with database users or with tokens from an access method.

A person who signs in through single sign-on for the first time gets a new SurrealDB account in the enterprise's member list, with no organisation memberships. Add them to each organisation they need, with the role they need, as described in [Members and roles](/docs/manage/organisations/members-and-roles). This account is separate from any account the person already has with the same email address, so memberships of the earlier account do not carry over. Enterprise roles do not currently grant anything inside organisations, so each person is added to each organisation directly.

## Billing

Billing belongs to the organisation. Each organisation receives one monthly invoice that covers all of its instances and Agent Memory contexts, so two organisations means two invoices. See [Billing](/docs/manage/organisations/billing).

A [support plan](/docs/manage/organisations/support) also applies to a whole organisation. With more than one organisation, check that each one has the plan it needs.

Buying through a marketplace works per organisation as well. Claiming an [AWS Marketplace](/docs/manage/organisations/aws-marketplace) or [Azure Marketplace](/docs/manage/organisations/azure-marketplace) subscription creates a new organisation, billed through that cloud account. Existing instances can be moved into it through support.
