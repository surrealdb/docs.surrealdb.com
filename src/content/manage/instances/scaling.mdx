# Scaling

Scaling an instance means changing the resources behind it so that query load, connection counts, and dataset growth stay within what the instance can serve. What you can change depends on the plan: **Start** instances scale vertically on one node, while **Scale** clusters scale vertically and horizontally on [SurrealDS](https://surrealdb.com/platform/surrealds).

This page covers when to scale and what to expect. The console steps are in [Configure an instance](/docs/manage/instances/configure#compute-and-storage).

## What scales on each plan

| | **Start** | **Scale** |
| --- | --- | --- |
| Compute up | Larger instance type on one node | Larger node size, or more nodes |
| Compute down | Smaller instance type | Smaller node size, or fewer nodes |
| Storage | Increase only | Increase only |
| Fault tolerance while resizing | Brief reconnect while the node restarts | Cluster stays available; capacity dips as each node restarts |

Storage can be increased but never decreased on either plan, and disk size can be increased once every six hours. Over-provisioning storage is therefore a one-way decision: start close to what the dataset needs and grow it as the dataset does.

## When to scale

The signals worth acting on are:

- **CPU pegged** near the instance-type limit under normal traffic, not just at peaks.
- **Memory pressure** — working set no longer fits, so the engine reads from disk more often.
- **Storage growth** trending towards the provisioned limit. Act well before the limit; a full disk stops writes.
- **Connection saturation** — clients queuing or being refused.
- **Latency objectives breached** on queries that used to meet them.

Read those from the [instance dashboard, metrics, and logs](/docs/manage/instances/monitoring). Rule out query-level causes first: a missing index or a full-table scan is cheaper to fix than a larger instance, and resizing hides it rather than removing it.

Schedule resizes outside peak traffic where you can. Some changes cause a brief reconnect, so clients need retry logic regardless.

## Scaling a Start instance

A Start instance has one node, so growth means a larger instance type — more vCPU, memory, and I/O — and a larger disk. Move to **Scale** instead when a single node is no longer the right shape: when the workload must survive the loss of a node, when query throughput needs to spread across nodes, or when you have reached the largest available Start instance type.

Moving from Start to Scale is not an in-place upgrade. Deploy a Scale instance and [restore a backup](/docs/manage/instances/backups) or [import an export](/docs/manage/instances/import-and-export) into it.

## Scaling a Scale cluster

A Scale cluster grows in two directions. **Vertically**, each node moves to a larger size. **Horizontally**, nodes are added — a three-node cluster becomes four, then five, and so on. SurrealDS handles replication, consensus, and distributed transactions across whatever the node count becomes.

> [!NOTE] An even node count does not improve fault tolerance. A cluster of N nodes survives the same number of failures as one of N−1, and the fast commit path needs every node to agree, so one slow node forces the slower path. Odd sizes — three, five, seven — give the best ratio of resilience to cost.

After scaling out, confirm **replication lag** stays within what the application tolerates, and check **per-node balance**: an unbalanced cluster means added nodes are not taking their share of the load.

See [Architecture](/docs/manage/instances/architecture) for the topologies, and [High availability](/docs/manage/instances/high-availability) for what each survives.

## Confirming the resize worked

Compare the same metrics before and after. A resize that shifts the bottleneck rather than removing it is common: CPU headroom appears and disk I/O becomes the new limit.

If utilisation stays low after a large resize, step back down. Instance type is billed on what is provisioned, not on what is used, so an oversized instance is a standing cost with no benefit.

`surrealctl instance metrics` and `surrealctl instance update` let you read the signals and apply the change from a terminal. See [surrealctl instances](/docs/manage/surrealctl/instances).
