# Versions and upgrades

Each instance runs a specific SurrealDB release. You pick it when you [create the instance](/docs/manage/instances/create) and change it from **Instance settings → Version** in [SurrealDB Studio](https://app.surrealdb.com). The platform replaces the running image, so there are no binaries to swap and no rolling restart to orchestrate yourself.

## Changing the version

The Version tab lists the releases available to the instance and links their release notes. Only upgrades are offered: the flow will not move an instance to an older release, because on-disk data written by a newer version is not readable by an older one.

On paid instance types the platform takes a snapshot before the change, which appears in the instance's [backup list](/docs/manage/instances/backups). That snapshot is the way back if the new version behaves differently than expected — restoring it produces a new instance on a compatible version.

> [!NOTE] Pre-release builds, such as nightly or beta tags, are only offered when they have been enabled for your organisation. Keep production on stable releases unless you are deliberately testing a preview.

## What happens during the upgrade

| Plan | Behaviour |
| --- | --- |
| **Start** | The single node restarts on the new image. Expect a short window where connections fail and clients reconnect. |
| **Scale** | The new image rolls through nodes one at a time while SurrealDS keeps storage consistent. The cluster stays reachable; query capacity dips while each node restarts. |

Timing depends on instance size, dataset size, and cluster layout. Watch [metrics and logs](/docs/manage/instances/monitoring) during and after the change and confirm query latency and error rates return to their previous level.

## Planning an upgrade

1. **Read the [release notes](https://surrealdb.com/releases)** for the target version and everything between it and your current one. Look for breaking changes, changed defaults, and removed options.
2. **Test against a non-production instance** on the target version, with your own application and SDK versions. SDK and server versions are released independently, so check both.
3. **Confirm you have a recent snapshot**, or take a [logical export](/docs/manage/instances/import-and-export) if you want a copy that lives outside the platform.
4. **Apply the change** and run your smoke tests — health checks, the queries your critical paths depend on, and anything that touches features named in the release notes.

For a major-version change that migrates data on disk, work through [Migrating from older SurrealDB versions](/docs/build/migrating/from-old-surrealdb-versions/overview) against a staging instance before touching production.

`surrealctl instance update` sets the version from a terminal, and `surrealctl instance status` reports what an instance is running — useful for checking a fleet at once. See [surrealctl instances](/docs/manage/surrealctl/instances).

## Compared with self-hosting

Self-hosted operators replace the `surreal` binary, run `surreal fix` where a release requires it, and coordinate the restart order across nodes themselves. On a managed instance the control plane does that work. The underlying mechanics, and the release-specific migration notes, are in [Self-hosted upgrades and patching](/docs/manage/self-hosted/upgrades-and-patching).
