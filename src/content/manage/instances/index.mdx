# Instances

An instance is a SurrealDB deployment that SurrealDB runs for you. Provisioning, high availability, patching, backups, and version upgrades are handled by the platform. You choose a plan, a size, and a region, then connect your application.

Every instance belongs to an [organisation](/docs/manage/organisations), which is also where members, usage, and billing are managed. You operate instances from [SurrealDB Studio](https://app.surrealdb.com), or from the command line with [`surrealctl`](/docs/manage/surrealctl/instances). If you would rather run and operate the server yourself, see [Self-hosted](/docs/manage/self-hosted).

## Plans

Two plans are available, and the plan you choose at deploy time fixes the topology of the instance.

| Plan | Topology | How it grows | Storage | Suited to |
| --- | --- | --- | --- | --- |
| **Start** | Single node | Vertically — move to a larger instance type | Dedicated disk per instance | Development, staging, and workloads that fit on one node |
| **Scale** | Multi-node cluster, minimum three nodes | Vertically and horizontally — larger nodes, more nodes | [SurrealDS](https://surrealdb.com/platform/surrealds) distributed storage | Production that must survive the loss of a node |

Within the Start plan, instance types come in three families: **Free** for trying SurrealDB out, **Burstable** for low-traffic and intermittent workloads, and **General purpose** for steady production traffic. Scale uses General purpose nodes.

The plan also gates some options. Configurable [backup frequency](/docs/manage/instances/backups), for example, is available on Scale instances only. Current capacity ceilings and prices are on the [pricing page](https://surrealdb.com/pricing); the plan cards in the deploy flow show what applies to your organisation.

For the topologies behind each plan, see [Architecture](/docs/manage/instances/architecture).

## Where instances live

The **Instances** section of SurrealDB Studio lists every instance in the organisation you are currently viewing, with its SurrealDB version and region. Search and the **Version** and **Type** filters narrow the list once an organisation holds more than a handful.

![The Instances page of SurrealDB Studio for the Acme Corp organisation, listing three instance cards — api-production on SurrealDB 3.2.4, and api-staging and analytics-eu on SurrealDB 3.2.1 — all in AWS Europe (Ireland), with a search box, Version and Type filters, and a Deploy new instance button.](~/assets/img/surrealdb/manage/instances-list.webp)

Selecting an instance opens its own workspace: a [dashboard](/docs/manage/instances/monitoring) of resource use, the schema and query views, and **Settings**, where [configuration](/docs/manage/instances/configure), [capabilities](/docs/manage/instances/configure#capabilities), [versions](/docs/manage/instances/versions-and-upgrades), compute, and [backups](/docs/manage/instances/backups) live.

`surrealctl instance list` prints the same list in a terminal, and `--json` makes it scriptable. See [surrealctl instances](/docs/manage/surrealctl/instances).

## Lifecycle

An instance moves through four states you control:

| Action | Effect | Where |
| --- | --- | --- |
| **Deploy** | Provisions the instance on the chosen plan, type, and region | [Create an instance](/docs/manage/instances/create) |
| **Resize** | Changes instance type or storage capacity in place | [Scaling](/docs/manage/instances/scaling) |
| **Pause** | Stops compute and billing for usage; data and configuration are kept, and the instance is unreachable until resumed | [Configure an instance](/docs/manage/instances/configure#pause-an-instance) |
| **Delete** | Destroys the instance and everything stored in it, with no way to recover it | [Configure an instance](/docs/manage/instances/configure#delete-an-instance) |

Instance names cannot be changed after deployment, so pick something a colleague will still recognise in six months — `api-production` rather than `db1`.
