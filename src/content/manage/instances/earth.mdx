# SurrealDB Earth

> [!IMPORTANT]
> SurrealDB Earth is in beta. Features, limits and pricing can change before general availability.

SurrealDB Earth is serverless SurrealDB that runs on the Cloudflare network.

You get a full SurrealDB database with SurrealQL, transactions and live queries. You do not choose an instance type or a node count: Earth adds compute when traffic grows, up to the number of [cells](#deploy-an-earth-instance) you set, and scales to zero when the instance is idle.

Earth is a separate product from the [Start and Scale plans](/docs/manage/instances). Some SurrealDB features are not available on Earth yet. See [Features not available yet](#features-not-available-yet) before you move a workload to it.

## When to use Earth

| Use Earth when | Use Start or Scale when |
| --- | --- |
| Traffic is irregular, or the database is idle for long periods | Traffic is steady and you want fixed capacity |
| Clients connect from many locations | Clients run in one cloud region, next to the database |
| You want no capacity planning | You want to choose the instance type and the number of nodes |
| The workload does not need the features listed below | The workload needs change feeds, Surrealism, JavaScript functions or DiskANN vector indexes |

## How Earth works

An Earth instance has three parts:

- **Compute:** SurrealDB runs on the Cloudflare network, close to the clients that connect to it. Each client session is served by one compute unit. When the sessions on the current units fill them, Earth starts more units for the instance.
- **Commit order:** each instance has one commit log. Every transaction commits in one strict order, so a transaction sees a consistent snapshot of the data and conflicting writes fail at commit, as they do on any SurrealDB server.
- **Storage:** the data of an instance is kept in Cloudflare object storage in one location. Earth writes a commit to durable storage before it acknowledges the commit.

These parts give the behaviour that follows:

- **Single-location storage, queries from many locations.** The data lives in one place, and queries arrive through the Cloudflare location nearest to each client.
- **Scale to zero.** After the last request, an idle instance stops using compute. The next request wakes it. The first request after an idle period can take longer than later requests.
- **Fully transactional.** Explicit transactions (`BEGIN` and `COMMIT`) and single statements both commit in the instance's one commit order.
- **Highly available.** No single compute unit holds data that only it can serve. If a unit fails, a new unit serves its sessions and reads the data from storage.

## Deploy an Earth instance

Deploy an Earth instance from the deploy page in [SurrealDB Studio](https://studio.surrealdb.com), in the same way as [any other instance](/docs/manage/instances/create). Earth is offered to organisations that have it enabled, and its settings differ from those of a dedicated instance:

| Setting | What it sets |
| --- | --- |
| **Data residency** | Where the data may be stored: **Worldwide**, **European Union**, or **United States**, which keeps the data in FedRAMP-compliant data centres. It cannot be changed after the instance is created. |
| **Preferred location** | Where Earth places storage and compute. **Automatic** places them near where requests to the instance come from. Each residency also offers fixed locations: Western and Eastern North America, Western and Eastern Europe, Asia-Pacific and Oceania for Worldwide, the two European locations for the European Union, and the two North American locations for the United States. |
| **Cells** | The most compute units the instance can run across at once. More cells let the instance handle more concurrent work. Studio offers up to 100 cells, and a larger count is available on request. Cells are set when the instance is deployed. |
| **Network policy** | Optional. Which client addresses can connect. See [Limit the addresses that can connect](#limit-the-addresses-that-can-connect). |
| **Capabilities** | What the instance permits at runtime, such as guest access and the functions it can use. See [Capabilities](/docs/learn/security/authorization/capabilities). They can be changed later. |

## Plans and usage

Every Earth instance in an organisation runs on the organisation's Earth plan.

- **Earth Free** includes a monthly allowance of request units, active hours and storage. When the allowance is spent, the organisation's Earth instances pause until the next month, and Studio shows a paused instance as disabled. The data is kept.
- **Earth Pro** is a monthly subscription for the organisation. Instances keep running after the allowance is spent, and the usage beyond it is billed.

Upgrade to Earth Pro from the deploy page, or from the **SurrealDB Earth** section of the organisation's billing page, where an owner can also cancel it. A cancelled subscription stays active until the end of the month. See [Pricing](https://surrealdb.com/pricing) for the allowances and prices.

The allowance belongs to the organisation, so all of its Earth instances use the same allowance. The plans also differ in these limits:

| Limit | Earth Free | Earth Pro |
| --- | --- | --- |
| Earth instances in the organisation | 100 | No limit |
| Clients connected to one instance at once | 100 | 10,000 |
| Cells per instance | Up to 100 | Up to 100 |

When an instance holds as many connections as its plan allows, it refuses a new connection.

### What is measured

Earth measures three things for each instance: request units, active hours and storage. The dashboard of an instance shows its request units and active hours for the current billing period. Network egress is not billed on either plan.

**Request units** measure the work that requests do. A request is one HTTP request, or one WebSocket message that carries a query or another RPC method. A query of several statements is one request, and its request units add up the reads and writes of all its statements.

- **Reads:** one unit for each started 16 KiB of a record or index entry that a request fetches by its key, including a check that finds nothing. A scan, such as a `SELECT` over a table or a range of an index, costs one unit for each started 16 KiB that it returns. Reads of table and field definitions cost nothing.
- **Writes:** three units for each started 4 KiB of each record, index entry or graph edge that a committed transaction writes. A delete counts as one write. A transaction that fails or is cancelled writes nothing, so its writes cost nothing.
- **Minimum:** a request that writes nothing costs at least one unit.
- **HTTP:** a request over HTTP costs two units more than the same request over WebSocket.

So a small record read by its ID costs about one unit, and the same record created costs about three units, plus three for each index entry that the write adds.

**Active hours** measure how long the compute units of an instance run. They are added up over all the units, so one unit that runs for an hour and ten units that run for six minutes each are both one active hour. A unit counts from when it starts to serve the instance until it is stopped, a short time after its last request, so a few requests spread over an hour can keep a unit running for most of it. Active hours are not CPU time. An idle instance that has scaled to zero uses no active hours.

**Storage** is the size of the instance's data, averaged over the month.

### Control usage

Earth Pro has no setting for a spending limit or for billing alerts yet. These settings limit what an instance can use:

- **Cells** are the most compute units that an instance runs at once, so they also limit its active hours: an instance with 10 cells uses at most 10 active hours in an hour. Fewer cells mean lower peak cost, and less work that the instance can do at the same time.
- **Capabilities** set the functions that queries can call and whether guests can connect. Deny a function that costs a lot to run, such as `crypto::argon2::generate()`, when the application does not need it. See [Capabilities](/docs/learn/security/authorization/capabilities).
- **Permissions** on tables and fields limit what a record user can read and write. See [Table permissions](/docs/reference/query-language/statements/define/table#defining-permissions).
- **A network policy** limits the addresses that can connect. See [Limit the addresses that can connect](#limit-the-addresses-that-can-connect).

To keep an organisation's Earth usage within a fixed amount, stay on Earth Free, which pauses the instances at its allowance instead of billing more.

## Connect to an Earth instance

You connect to an Earth instance in the same way as to any other instance: with [SurrealDB Studio](/docs/manage/instances/connect/via-studio), [an SDK](/docs/manage/instances/connect/via-sdk), [the CLI](/docs/manage/instances/connect/via-cli) or [HTTP](/docs/manage/instances/connect/via-http). Use the public endpoint that the instance's dashboard in Studio shows, in the form `wss://<instance-id>.surrealdb.earth/rpc`. The dashboard also shows the request units and active hours the instance has used in the current billing period.

![The dashboard of an Earth instance named elegant-comet in SurrealDB Studio, running SurrealDB 4.0.0 on Earth in the European Union. Four tiles show the region, Earth European Union, served from Cloudflare's network; 0 request units from 0 requests; 0 active hours this billing period; and version v4.0.0. Below them is the public endpoint, wss://06gq7rerilpj12gv0o92kbshsk.surrealdb.earth/rpc, with a copy button.](~/assets/img/surrealdb/manage/earth-dashboard.webp)

Use a WebSocket connection when a client sends many queries. Each HTTP request is routed and authenticated separately, so a long series of HTTP requests is slower than the same queries on one open WebSocket.

## Connect with PostgreSQL or MySQL clients

PostgreSQL and MySQL clients connect to an Earth instance over TCP. TLS is required, and a connection without TLS is closed.

A client names the instance in one of two ways: in the TLS server name (SNI), or in the user name as `<user>@<instance-id>`.

| Client | Host | Port | User name |
| --- | --- | --- | --- |
| PostgreSQL client that sends SNI | `<instance-id>.sql.surrealdb.earth` | `5432` | `<user>` |
| PostgreSQL client that does not send SNI | `sql.surrealdb.earth` | `5432` | `<user>@<instance-id>` |
| MySQL client | `sql.surrealdb.earth` | `3306` | `<user>@<instance-id>` |

MySQL clients, such as the `mysql` CLI and other clients built on libmysqlclient, do not send SNI, so a MySQL user name always includes `@<instance-id>`.

When a client does not send SNI and the user name has no `@<instance-id>`, Earth closes the connection without an error message. `psql` then reports `server closed the connection unexpectedly`. Add `@<instance-id>` to the user name, or connect to `<instance-id>.sql.surrealdb.earth` with a client that sends SNI.

Sign in with a user defined `ON DATABASE`. Users defined `ON ROOT` or `ON NAMESPACE` cannot run queries over PostgreSQL or MySQL, so [define a database user](/docs/reference/query-language/statements/define/user) first:

```surql title="Define a database user"
DEFINE USER app ON DATABASE PASSWORD 'change-me' ROLES EDITOR;
```

Name the namespace and database as `<namespace>/<database>`, with a slash:

```bash title="Connect with psql"
psql "host=<instance-id>.sql.surrealdb.earth port=5432 user=app dbname=main/main sslmode=require"
```

```bash title="Connect with psql, without SNI"
psql "host=sql.surrealdb.earth port=5432 user=app@<instance-id> dbname=main/main sslmode=require"
```

```bash title="Connect with the mysql CLI"
mysql -h sql.surrealdb.earth -P 3306 -u 'app@<instance-id>' -p --ssl-mode=REQUIRED main/main
```

## Move a database to Earth

Move a database from a self-hosted server, or from another instance, with [`surreal db export`](/docs/reference/cli/db/commands/export) and [`surreal db import`](/docs/reference/cli/db/commands/import). An export holds one database, so move a namespace one database at a time.

Upgrade the source to SurrealDB 4.0 first, and export after the upgrade. Earth runs 4.0, so the export is then written by the version that imports it. See [3.x to 4.0](/docs/build/migrating/from-old-surrealdb-versions/3x-to-4x) for the upgrade. Then export each database from the source:

```bash title="Export a database from the source"
surreal db export \
  --endpoint https://<source-host> \
  --user root --pass <password> \
  --ns app --db production \
  ./production.surql
```

Then import each file into the Earth instance, with the token from the instance's **Connect** menu in Studio:

```bash title="Import a database into Earth"
surreal db import \
  --endpoint https://<instance-id>.surrealdb.earth \
  --token <token> \
  --ns app --db production \
  ./production.surql
```

Use an `https://` endpoint for both commands. Export and import run over HTTP, and fail on a `wss://` endpoint.

Earth defines the namespace and the database on the first request that uses them, so you do not need to create them first. After the import, define these again on the Earth instance:

- **Definitions on the namespace**, such as users and access methods defined `ON NAMESPACE`. A database export does not hold them.
- **Access methods with a signing key.** An export writes a placeholder in place of the key, and the import refuses it. See [Exports and imports](/docs/build/migrating/from-old-surrealdb-versions/3x-to-4x#exports-and-imports).

An import commits each statement as it runs, so a failure partway through keeps the statements before it. See [Import and export](/docs/manage/instances/import-and-export) for how to retry a partial import.

## Limit the addresses that can connect

A network policy lists the client addresses that can connect to an Earth instance, as IP addresses and CIDR blocks such as `203.0.113.0/24`. Set it on the deploy page, or later in the **Network policy** subsection of the instance's **Capabilities** settings.

- **Allowed:** when the list has entries, only those addresses can connect. When it is empty, every address can connect.
- **Denied:** these addresses cannot connect, even when they are also in the allowed list.

The policy applies to HTTP and WebSocket connections. It does not apply to PostgreSQL and MySQL clients yet.

## Handle busy responses

When an instance is adding compute, Earth can answer a new request with HTTP status `503`. The request did not start, so it is safe to send again. Retry it after a short delay, and increase the delay for each retry.

Earth does not refuse work that belongs to a transaction it has already accepted. A transaction that has started continues to its commit or rollback.

## Features not available yet

The features below are not available on Earth. They are planned for a future release.

| Feature | What happens on Earth | Documentation |
| --- | --- | --- |
| **Change feeds** | `SHOW CHANGES` returns an error, and a table or database defined with `CHANGEFEED` records no changes | [Change feeds](/docs/learn/querying/real-time/changefeeds) |
| **Surrealism** | WebAssembly extensions cannot be loaded or called | [Extensions](/docs/learn/extensions) |
| **JavaScript functions** | Embedded scripting functions, written as `function() { ... }`, are turned off. The scripting capability cannot be turned on | [Scripting](/docs/reference/query-language/scripting/overview) |
| **Outbound network access** | The network access capability is not offered, so functions such as `http::get()` cannot reach other hosts | [Capabilities](/docs/learn/security/authorization/capabilities) |
| **DiskANN vector indexes** | A `DEFINE INDEX ... DISKANN` statement returns an error. Define the vector index with `HNSW` instead, which Earth supports | [Vector indexes](/docs/learn/data-models/vector-search/vector-indexes) |

If your workload needs one of these features now, deploy it on the [Start or Scale plan](/docs/manage/instances/create).

> [!NOTE]
> Check the [changelog](https://surrealdb.com/changelog) for features as they become available on Earth.

## Things to know

- **Define a table before a long transaction writes to it.** A transaction that creates a table by its first write, and stays open for a long time, can fail at commit with a transaction conflict. Run `DEFINE TABLE` first, outside the transaction, and the same transaction commits.
- **Capabilities still apply.** You can allow guest access, and allow or deny functions and other [capabilities](/docs/learn/security/authorization/capabilities), for an Earth instance. The scripting capability always stays off.
- **An Earth instance can be renamed.** Change its name in the **General** tab of its settings. The instance id and the endpoints stay the same.
- **The first request after an idle period is slower.** An instance that has scaled to zero starts again on its next request.
