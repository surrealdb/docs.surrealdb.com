# Architecture

Managed instances build on [SurrealDB's layered architecture](/docs/architecture), which separates storage from compute. That separation is what allows an instance to grow, replicate, and recover without you operating, sharding, or resharding the database yourself.

The plan you choose when you [create an instance](/docs/manage/instances/create) selects one of two topologies.

## Start: single node

The **Start** plan provides one compute node backed by a dedicated disk. Compute and storage are sized together and resized together, and the node holds the only copy of the working data.

<img src="~/assets/img/image/cloud/light/start-single-node-light.png" darkSrc="~/assets/img/image/cloud/start-single-node.png" alt="Diagram of the single-node topology: one SurrealDB compute node paired with its own dedicated disk-based storage volume." />

This suits development, staging, and production workloads that fit comfortably on one node and can tolerate a short recovery window. It scales vertically: as load grows, you move to a larger instance type. See [Scaling](/docs/manage/instances/scaling).

Because there is a single node, there is no in-instance failover. [Backups](/docs/manage/instances/backups) are the recovery mechanism — see [High availability](/docs/manage/instances/high-availability) for what that means in practice.

## Scale: multi-node on SurrealDS

The **Scale** plan runs a cluster on [SurrealDS](https://surrealdb.com/platform/surrealds), SurrealDB's distributed storage engine, starting at three nodes. Each node runs in a different availability zone within the region, backed by its own disk.

<img src="~/assets/img/image/cloud/light/enterprise-multi-node-light.png" darkSrc="~/assets/img/image/cloud/enterprise-multi-node.png" alt="Diagram of the multi-node topology: three SurrealDB compute nodes, each in a separate availability zone with its own storage volume, coordinating through the SurrealDS distributed storage layer." />

Data is replicated continuously between nodes, and every node serves reads, writes, and queries. SurrealDS handles replication, quorum consensus, and distributed transactions, so a query does not need to know which node holds which data.

The practical consequences are:

- **Node loss is survivable.** A quorum of the remaining nodes keeps serving. Three nodes is the minimum because it leaves a majority when one node is out for a failure, an upgrade, or maintenance.
- **Query capacity scales horizontally.** Adding nodes adds throughput, unlike vertical scaling which is bounded by the largest available instance type.
- **The equivalent self-hosted deployment is substantial.** Running the same topology yourself means operating Kubernetes, storage replication, patching, backups, and upgrade orchestration. Those are handled for you on Scale — compare [Self-hosted deployment models](/docs/manage/self-hosted/deployment-models).

> [!NOTE]
> Several Scale capabilities are still on the roadmap: object-storage backing, which keeps hot data on disk and cold data in object storage and in turn enables instant database branching; cross-region replication; automatic sharding; and read replicas. See [Pricing](https://surrealdb.com/pricing) and [Roadmap](https://surrealdb.com/roadmap) for current availability.
