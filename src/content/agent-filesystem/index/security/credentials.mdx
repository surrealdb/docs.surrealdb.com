# Protocol credentials

Agent Filesystem can serve its files over WebDAV and an S3-style HTTP API with the `surrealfs-rs serve webdav` and `surrealfs-rs serve s3` commands. The logins that these servers accept are stored as records in a `credential` table, apart from SurrealDB users and from [record users](/docs/agent-filesystem/security/record-access). This page describes the credential kinds, the commands that manage them, how the servers resolve a request to a credential, and what a valid login grants in this release.

> [!NOTE]
> Agent Filesystem is in beta. The API, schema and command-line interface may change in breaking ways between releases. This page describes version 0.2.0 of [SurrealFS](https://github.com/surrealdb/surrealfs), the open source project behind Agent Filesystem, and each limitation that applies is listed where it matters.

> [!WARNING]
> A WebDAV or S3 request that carries no `Authorization` header is served in full. A request with a valid credential receives the server's own access to the whole tree, and not the access of the credential's user. Keep both servers on the loopback address, and treat any client that can reach them as having full access to every file. See [Authentication in this release](#authentication-in-this-release).

For how to start the servers, see [Network servers](/docs/agent-filesystem/interfaces/network-servers).

## Credential records

A credential is one record in the `credential` table. The table is open only to `root` and to system credentials, so no record user can read or manage it.

| Field | Meaning |
| --- | --- |
| `kind` | One of `webdav`, `s3`, `ssh`, `slack`, `teams` or `bearer` |
| `identifier` | The login name, access key or token. The pair of `kind` and `identifier` is unique |
| `secret_hash` | The secret that the client must present, or its SHA-256 digest. The field is optional |
| `user_id` | The Agent Filesystem user that the credential belongs to. The field is a plain string, no server reads it, and the examples on these pages use the bare user name, such as `alice` |
| `enabled` | `true` until the credential is revoked |
| `meta` | Optional free-form metadata |

The WebDAV and S3 servers read three kinds: `webdav`, `s3` and `bearer`. The `webdav` and `s3` kinds hold a login name and a secret, and the `bearer` kind holds a token. The `ssh` kind holds a public-key fingerprint that the SFTP session code reads. No command starts an SFTP listener yet, because the `serve sftp` and `serve nfs` commands print a configuration line and start no listener. Nothing reads the `slack` and `teams` kinds, although the table accepts them.

## Manage credentials

The `surrealfs-rs credential` commands manage the records. They connect with a system credential, so the examples set the connection first. The [command-line quickstart](/docs/agent-filesystem/quickstarts/command-line) shows how to build the tool.

```bash
export SURREALDB_URL=ws://localhost:8000/rpc SURREALDB_NS=agents SURREALDB_DB=files
export SURREALDB_USER=root SURREALDB_PASS=secret
```

<Synopsis>
surrealfs-rs credential create <KIND> <IDENTIFIER> <SECRET> <USER_ID>
surrealfs-rs credential list [-u <USER_ID>]
surrealfs-rs credential revoke <KIND> <IDENTIFIER>
</Synopsis>

| Command | Effect |
| --- | --- |
| `credential create` | Creates a credential with `enabled` set to `true`. The kind and identifier together must be new |
| `credential list` | Prints the kind, identifier, user and `enabled` flag of every credential, including revoked ones. It never prints the secret |
| `credential revoke` | Sets `enabled` to `false`. The servers stop accepting the credential, and the record stays in the table |

```bash
surrealfs-rs credential create webdav alice-dav hunter123 alice
surrealfs-rs credential list
surrealfs-rs credential revoke webdav alice-dav
```

```text title="Output"
Created credential alice-dav (webdav) for alice
webdav   alice-dav                alice            enabled=true
Revoked credential alice-dav (webdav)
```

Five behaviours of the tool need care:

- **Existing credential:** `credential create` prints `Created credential` for a kind and identifier that already exist, and changes nothing, because the stored `created_at` field is read-only. The old secret and the old `enabled` flag stay as they were. To change a secret or to enable a revoked credential, update the record with a system credential, as shown after this list.
- **Kind:** `credential create` prints `Created credential` for a kind that the table does not accept, such as `bogus`, and stores nothing. Run `credential list` afterwards to confirm the record exists.
- **Unknown credential:** `credential revoke` prints `Revoked credential <identifier> (<kind>)` and exits with status 0 for a credential that does not exist. A mistyped identifier looks like a revocation while the real credential stays enabled. Run `credential list` afterwards and check for `enabled=false`.
- **User filter:** The `-u` option of `credential list` is applied as a filter on the kind, so `credential list -u alice` prints nothing. Run the command without `-u`.
- **Secret argument:** The command takes the secret as an argument, so it appears in the shell history and in the process list. A `bearer` credential ignores its secret, so pass an empty string for it.

A credential record has the identifier `credential:[kind, identifier]`, so SurrealQL can update it directly. Run the statement with a system credential, for example in `surreal sql --endpoint http://localhost:8000 --user root --pass secret --ns agents --db files` or in Surrealist:

```surql
UPDATE credential:['webdav', 'alice-dav'] SET secret_hash = crypto::sha256('hunter789'), enabled = true;
```

The function `crypto::sha256()` returns the hexadecimal digest that the servers compare against, so the record stores the digest and not the password. The next section describes both forms.

### How secrets are stored

The `credential create` command stores the secret exactly as given. A listing hides it, but the `secret_hash` field holds the plain text unless the operator supplies a digest. To store a SHA-256 digest, hash the secret first and pass the hexadecimal result:

```bash
HASH=$(printf '%s' 'hunter123' | openssl dgst -sha256 -r | cut -d' ' -f1)
surrealfs-rs credential create webdav bob-dav "$HASH" bob
```

The server accepts a password when it equals the stored value exactly, or when the SHA-256 digest of the password equals the stored value. Two consequences follow. A client that presents the stored digest itself is accepted as well. Anyone who can read the `credential` table can therefore log in with a digest, and the digest protects the original password and not the account. A record that has no `secret_hash` value accepts any password, and only a record written by other means can be without one, because the command always stores a value.

The comparison is not constant-time, uses no salt, and has no rate limit.

## Authentication in this release

A server checks credentials in the way the table below describes, and each server reads the `Authorization` header of the request:

| Header | Servers | Lookup | Secret check |
| --- | --- | --- | --- |
| `Authorization: Basic <base64 of user:password>` | WebDAV, S3 | A `webdav` credential with the user as identifier. When none matches or its secret differs, an `s3` credential with the same identifier | The password is compared with `secret_hash` as described above |
| `Authorization: Bearer <token>` | S3 only | A `bearer` credential with the token as identifier | None. Any enabled token is accepted |
| `Authorization: AWS4-HMAC-SHA256 Credential=<access key>/..., SignedHeaders=..., Signature=...`, as the AWS CLI and SDKs send it | S3 | None. The `Credential=` part follows the algorithm name without a comma, so the server finds no access key | The request returns `403` |
| `Authorization: AWS4-HMAC-SHA256, Credential=<access key>/...`, with a comma after the algorithm name | S3 | The `s3` credential for the access key | None. The signature is never verified |
| No `Authorization` header | WebDAV, S3 | None | None. The request is served |

Only enabled credentials are resolved. A wrong WebDAV password or an unknown user returns `401`, and an unaccepted S3 header returns `403`. A WebDAV request with a Bearer header returns `401`. [Network servers](/docs/agent-filesystem/interfaces/network-servers#credentials-and-access-control) shows the same decisions for both servers.

Four limits apply:

- **Requests without a header are served.** The servers check credentials only when the request carries an `Authorization` header. A WebDAV `GET`, `PUT` and `DELETE`, and an S3 `GET`, without the header are served.
- **The authenticated user is not used.** After a successful login the server discards the `user_id` of the credential. It handles the request with its own identity, which is the `--caller` of the server process, or the database username when `--caller` is not set. A file that `alice-dav` creates with a `PUT` belongs to that identity, and with the default identity `root` the server reads private homes without any check.
- **AWS signatures are not supported.** The S3 server never verifies a request signature. The headers that the AWS CLI and AWS SDKs send return `403`, so clients that sign requests cannot log in today. Unsigned requests, Basic requests and Bearer requests work.
- **There is no transport security.** The servers speak plain HTTP, so a Basic password and a Bearer token travel in clear text.

Both servers bind to `127.0.0.1` by default, on ports 8080 for WebDAV and 9000 for S3. Passing `-a 0.0.0.0:<port>` exposes the whole tree to the network, with the limits above. Put a proxy that terminates TLS and authenticates clients in front of a server before it is reachable from another machine.

### Check a login

The commands below create a new credential, start the WebDAV server, and send three requests with `curl` from a second shell. The server keeps running until you stop it. The check uses its own identifier, because `alice-dav` above is revoked or has a different password.

```bash
surrealfs-rs credential create webdav dav-check hunter123 alice
surrealfs-rs serve webdav
```

```bash
curl -s -o /dev/null -w "%{http_code}\n" -u dav-check:hunter123 http://127.0.0.1:8080/
curl -s -o /dev/null -w "%{http_code}\n" -u dav-check:wrong http://127.0.0.1:8080/
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/
```

```text title="Output"
200
401
200
```

The correct password returns `200` and the wrong one returns `401`. The request without a header returns `200` as well, which shows why a credential alone does not close the server.

## Credentials for the database

The clients that connect to SurrealDB use a separate set of credentials, which come from environment variables:

- **Level:** The Python surfaces read `SURREALDB_AUTH_LEVEL`, which is `root` by default and may be `namespace`, `database` or `record`. The level decides the shape of the sign-in. [Record access](/docs/agent-filesystem/security/record-access) uses `record`.
- **Defaults:** The Python surfaces and the Rust tool default to the user `root` with the password `root`. Set `SURREALDB_USER` and `SURREALDB_PASS` for every deployment.
- **Rust connection:** For a `ws://` or `wss://` URL, the Rust tool removes the prefix from the URL and opens a plain WebSocket. A `wss://` URL against a server that does not use TLS connects, so the credential travels unencrypted. Over a WebSocket the tool signs in only as a root user.
- **Configuration file:** The MCP server reads `$XDG_CONFIG_HOME/surrealfs/env`, which is `~/.config/surrealfs/env` when `XDG_CONFIG_HOME` is not set, or the file named by `SURREALFS_ENV_FILE`. It warns when other users can read the file. The file holds the password in plain text.

The [configuration page](/docs/agent-filesystem/operations/configuration) lists every variable and the differences between the Python and Rust names.
