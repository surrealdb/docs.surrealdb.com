# Licence, version and status

This page states the licence declarations, the version, the status and the install sources of Agent Filesystem, so that you can check them before you depend on it. Agent Filesystem is the name of the product. SurrealFS is the name of the open source project that contains it. The name SurrealFS appears in the repository, [surrealdb/surrealfs](https://github.com/surrealdb/surrealfs), and in the names of the Python package, the commands and the environment variables.

The facts on this page describe version 0.2.0 at commit `76d2444` of the `next` branch of that repository. The version number does not identify a build, as [Version](#version) explains, so the commit is the exact reference.

## At a glance

| Item | Value |
| --- | --- |
| Version | 0.2.0. The number does not identify a build, as [Version](#version) explains. |
| Build described | Commit `76d2444` of the `next` branch |
| Status | Beta |
| Licence | Declared as Apache-2.0 by the Rust crates and the TypeScript package, and as MIT by the Python package and the Claude plugin. The repository has no licence file. See [Licence](#licence). |
| Source | [github.com/surrealdb/surrealfs](https://github.com/surrealdb/surrealfs), branch `next` |
| Published packages | None on PyPI, npm, crates.io or Docker Hub. Every install reads the Git repository. See [Where to get it](#where-to-get-it). |
| SurrealDB server | 3.x (checked against 3.2.3) |
| Python | 3.11 or later |
| Rust | No minimum declared. The locked dependencies need 1.95 or later. |

## Licence

Four groups of components declare a licence in a manifest. The table lists what version 0.2.0 declares, and where:

| Component | Where it is declared | Declared licence |
| --- | --- | --- |
| Rust crates: `surrealfs-core`, `surrealfs-cli`, `surrealfs-server`, `surrealfs-fuse`, `surrealfs-shim` and `surrealfs-sim` | `license` in `[workspace.package]` of `Cargo.toml`, which every crate inherits | `Apache-2.0` |
| TypeScript package `@surrealdb/fs` | `license` in `packages/sdk-ts/package.json` | `Apache-2.0` |
| Python package `surrealfs`, whose source tree includes the MCP server and the Hermes plugins | A classifier in `pyproject.toml`. The package has no `license` field. | `License :: OSI Approved :: MIT License` |
| Claude plugin | `license` in `surrealfs/integrations/claude/.claude-plugin/plugin.json` | `MIT` |

The other manifests in the repository declare no licence. They include `apps/macos-menu/Package.swift`, `surrealfs/browser/ui/package.json`, `wrangler.toml`, `.claude-plugin/marketplace.json` and the two Hermes `plugin.yaml` files.

> [!IMPORTANT]
> The declarations disagree, and the repository contains no licence text. It has no `LICENSE`, `NOTICE` or `COPYING` file, and GitHub reports no licence for it. The manifest fields in the table are the only licence statements in the repository, so this page does not name one licence for Agent Filesystem as a whole. If your use depends on the licence, for example when you redistribute a component or include it in a product, ask SurrealDB which licence applies to that component.

You can read the declaration of an installed Python package yourself. The classifier appears in the output of `pip show`:

```bash
pip show --verbose surrealfs | grep "License ::"
```

```text title="Output"
  License :: OSI Approved :: MIT License
```

The licence of the SurrealDB server, and the licences of the libraries that Agent Filesystem depends on, are separate from the declarations above, and this page does not cover them.

## Version

The Python package, the Rust crates, the TypeScript package, the Claude plugin and the MCP server all report version 0.2.0. One manifest differs: the `plugin.yaml` of the Hermes memory provider declares version 0.3.0. The commands below print the version of the components that you installed. The Rust command is installed as `surrealfs-rs`, and it prints its name as `surrealfs`.

For the Python package:

```bash
python -c "import surrealfs; print(surrealfs.__version__)"
```

```text title="Output"
0.2.0
```

For the Python command:

```bash
surrealfs --version
```

```text title="Output"
surrealfs 0.2.0
```

For the Rust command:

```bash
surrealfs-rs --version
```

```text title="Output"
surrealfs 0.2.0
```

### The version number does not identify a build

The repository has no release tags and no GitHub releases, and the version number has stayed at 0.2.0 across commits. The `main` branch also reports 0.2.0, but it holds an earlier state of the code. Its Python tool registry has 15 tools, and it has no Rust crates and no TypeScript package. The Python tool registry of the `next` branch has 31 tools, and the branch has both the Rust crates and the TypeScript package. These pages describe commit `76d2444` of the `next` branch. The branch moves, so a later commit can differ from what these pages describe.

To find out which commit an installed copy of the Python package was built from, run `pip freeze`. The commit hash follows the `@`:

```bash
pip freeze | grep surrealfs
```

```text title="Sample output"
surrealfs @ git+https://github.com/surrealdb/surrealfs.git@<commit>
```

For the Rust command, `cargo install --list` shows the first eight characters of the commit after the `#`:

```bash
cargo install --list
```

```text title="Sample output"
surrealfs-cli v0.2.0 (https://github.com/surrealdb/surrealfs?branch=next#<short-commit>):
    git-remote-surrealfs
    surrealfs-rs
```

To install the same build again, or to keep an install from changing when the branch moves, name the commit in place of the branch:

```bash
pip install "surrealfs @ git+https://github.com/surrealdb/surrealfs.git@<commit>"
cargo install --locked --git https://github.com/surrealdb/surrealfs --rev <commit> surrealfs-cli
```

## Where to get it

The Python package is not on PyPI, the TypeScript package is not on npm, none of the Rust crates is on crates.io, and Docker Hub has no `surrealdb/surrealfs` image repository. Every install therefore reads the Git repository. The `pip` and `cargo` commands below name the `next` branch, and the Claude plugin and the Hermes provider directory read the default branch, as their rows say.

A URL without a branch name uses the default branch, `main`, which reports the same version number and holds an earlier state of the code. With `pip`, such a URL installs that earlier code. With `cargo install`, it fails with `could not find Cargo.toml`, because `main` has no Rust crates.

| Component | Install | Notes |
| --- | --- | --- |
| Python library and the `surrealfs` command | `pip install "surrealfs @ git+https://github.com/surrealdb/surrealfs.git@next"` | Needs Python 3.11 or later and Git. The [Python quickstart](/docs/agent-filesystem/quickstarts/python#2-install-the-package) lists the optional extras. |
| MCP server | `pip install "surrealfs[mcp] @ git+https://github.com/surrealdb/surrealfs.git@next"` | The `mcp` extra adds the packages that the server needs, and the bare command above does not install them. See [MCP server](/docs/agent-filesystem/interfaces/mcp-server). |
| Rust command `surrealfs-rs` | `cargo install --locked --git https://github.com/surrealdb/surrealfs --branch next surrealfs-cli` | Needs a Rust toolchain, as [Requirements](#requirements) describes. The command installs two executables, `surrealfs-rs` and `git-remote-surrealfs`. The [command-line reference](/docs/agent-filesystem/interfaces/command-line#install) describes the first, and [Git import](/docs/agent-filesystem/interfaces/git) describes the second. |
| Gateway program `surrealfs-server` | `cargo install --locked --git https://github.com/surrealdb/surrealfs --branch next surrealfs-server` | Needs a Rust toolchain. See [Gateway server](/docs/agent-filesystem/interfaces/gateway-server) and [REST API](/docs/agent-filesystem/interfaces/rest-api). |
| TypeScript package `@surrealdb/fs` | Not published | The source is in `packages/sdk-ts` of the repository. See [TypeScript SDK](/docs/agent-filesystem/interfaces/typescript-sdk). |
| Claude plugin | Added from the repository as a plugin marketplace | By default the plugin builds the `main` branch, which has 15 tools. Set `SURREALFS_SOURCE` to a `next` source to run the build that these pages describe. See [Claude plugin](/docs/agent-filesystem/interfaces/claude-plugin). |
| Hermes tool plugin | Part of the Python package, which Hermes finds through the `hermes_agent.plugins` entry point | See [Hermes plugins](/docs/agent-filesystem/interfaces/hermes). |
| Hermes memory provider | `hermes plugins install surrealdb/surrealfs/surrealfs/integrations/hermes_memory`, followed by a separate install of the Python package | Hermes finds the provider by directory, and not through an entry point. See [Hermes plugins](/docs/agent-filesystem/interfaces/hermes#install-and-set-up), which names the branch for the package install. |

The name `surrealfs` is not registered on PyPI, so `pip install surrealfs` fails:

```bash
pip install surrealfs
```

```text title="Error output"
ERROR: Could not find a version that satisfies the requirement surrealfs (from versions: none)
ERROR: No matching distribution found for surrealfs
```

## Requirements

| Requirement | Applies to | Details |
| --- | --- | --- |
| SurrealDB 3.x server | Every component | The schema uses `COMPUTED` fields and the `FULLTEXT ANALYZER` index syntax, which SurrealDB 2.x does not accept. These pages were checked against SurrealDB 3.2.3, and other 3.x releases were not tested. |
| Python 3.11 or later | Python package | The package declares `requires-python = ">=3.11"`. Tested with Python 3.11, 3.12, 3.13, 3.14 and 3.15: a short script that writes, edits, reads and searches a file ran on each. |
| `surrealdb==3.0.0b8` | Python package | The package requires exactly this beta release of the Python SDK, so an environment that needs another SDK version reports a conflict. The other required dependency is `pydantic>=2.12`. |
| Git | Installs from the repository | `pip` and `cargo` both clone the repository. |
| Rust 1.95 or later | `surrealfs-rs` and `surrealfs-server` | The repository declares no minimum Rust version, but the locked dependencies need Rust 1.95 or later. A build with Rust 1.94 fails in two of them, `yrs` and `surrealdb-common`. Rust 1.95 passes `cargo check`, and Rust 1.99.0 installs both programs. |

## Status

Agent Filesystem is in beta. The project states that the API, the schema and the command-line interfaces can change in breaking ways between releases, and it does not yet recommend the use of Agent Filesystem in production. Four consequences follow from the way the repository is built and released.

**A build is identified by its commit.** The release has no tags and no changelog, so [Version](#the-version-number-does-not-identify-a-build) shows how to find the commit of an install and how to pin it. The list of commits between two builds is the record of what changed. On GitHub, open `https://github.com/surrealdb/surrealfs/compare/<old>...<new>` with the two commit hashes.

**The schema has no migration step.** The schema is the file `file.surql` and the optional file `record_auth.surql`, and applying it runs the whole file each time. The Python package reads the two files, and the Rust programs embed them when they are built. The TypeScript package carries a generated copy that is older than the two files. The database stores no schema version, and the repository has no migration tool.

**Some programs apply the schema when they start or connect.** The table shows which program applies which file when it connects to SurrealDB directly:

| Program | When it applies the schema | Files applied |
| --- | --- | --- |
| The Python `surrealfs` commands `status`, `lock`, `history`, `restore` and `grep`, and the Hermes plugins | The first time a process connects with a system credential | `file.surql` |
| The Python MCP server | When it starts, with any credential. A failure prints a message and the server continues. | `file.surql` |
| `surrealfs-server` | Every time it starts. A failure prints a warning and the program continues. | Both files |
| `surrealfs schema apply` and `python -m surrealfs.schema` | When you run the command | `file.surql`, and `record_auth.surql` with `--record-auth` |
| `surrealfs init` and `surrealfs-rs init` | When you run the command | Both files |

A system credential is a SurrealDB root, namespace or database user. The Rust command `surrealfs-rs` applies the schema only in `init`, and not when it connects. With `SURREALFS_SERVER_URL` set, the Python commands and the Hermes plugins connect to a gateway instead of SurrealDB, and they apply no schema when they connect. Starting a newer build against an existing database can therefore apply the schema of that build without a prompt. Run against an empty database, `surrealfs status` defines 32 tables and creates the `/home` folder. It defines no `user` table and no access method, because those belong to `record_auth.surql`.

**A re-application replaces most definitions but not all.** Applying `file.surql` overwrites the definitions of tables, fields, functions, events and most indexes, so a local change to one of them is lost the next time a program applies the schema. The analysers, the full-text indexes, and the vector indexes on the `file` and `file_section` tables use `IF NOT EXISTS`. An existing one keeps its definition, including a definition that someone changed since. The vector index on the `file_chunk` table is overwritten like the rest. Applying `record_auth.surql` overwrites the `user` table and the four access methods. Each application also sets the owner of `/home` back to `root` and its mode to `0o777`. A release that changes one of the preserved definitions therefore does not change an existing database by itself.

Export the database before you connect a newer build to it. [Back up a database](/docs/agent-filesystem/operations/backup-and-restore#back-up-a-database) shows the command.

The three implementations differ in what they cover. The Python library is the most complete, the Rust command and the TypeScript package implement subsets, and some features are not available in this release. [Limits and caveats](/docs/agent-filesystem/operations/limits-and-caveats) lists each feature with its status.
