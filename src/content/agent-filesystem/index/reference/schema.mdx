Agent Filesystem keeps its data in SurrealDB tables that the schema files define. This page lists every table, field, index, analyser and event in that schema, grouped by the part of the product that uses them. For each table it says which code writes it and what a record user may do with it.

The schema consists of `surrealfs/schema/file.surql`, which is always applied, and `surrealfs/schema/record_auth.surql`, which is optional. The [SurrealQL function reference](/docs/agent-filesystem/reference/surrealql-functions) describes the 76 functions that the first file also defines, and the [data model](/docs/agent-filesystem/concepts/data-model) page describes the `file` table in prose.

> [!NOTE]
> Agent Filesystem is in beta. This page describes version 0.2.0 of the SurrealFS repository, run on SurrealDB 3.2.3. Several tables are defined before any shipped code uses them, and each table entry says so under **Written by**.

| Kind | Count in `file.surql` |
| --- | --- |
| Tables | 32 |
| Indexes | 40 |
| Analysers | 6 |
| Events | 4 |
| Functions | 76 |

The optional `record_auth.surql` adds one table, `user`, and four access methods. The counts match the output of `INFO FOR DB` and `INFO FOR TABLE` on a database where the schema has been applied.

## Apply and inspect the schema

Apply the schema to a database on a SurrealDB 3.x server with the Python package:

```bash
python -m surrealfs.schema --url ws://localhost:8000/rpc --username root --password secret --namespace surrealfs --database demo
```

The command needs a running SurrealDB server and the `surrealfs` Python package, which is installed from the repository. The [function reference](/docs/agent-filesystem/reference/surrealql-functions#install-the-functions) shows both steps. Each option falls back to an environment variable, which is `SURREALDB_URL`, `SURREALDB_USER`, `SURREALDB_PASS`, `SURREALDB_NAMESPACE` or `SURREALDB_DATABASE`, and then to a default: `ws://localhost:8000/rpc`, the user `root` with the password `root`, the namespace `surrealfs` and the database `demo`. Add `--record-auth` to apply `record_auth.surql` as well, and `--print` to print the statements without connecting. The Rust command `surrealfs-rs init` applies both files. The statements use `OVERWRITE` or `IF NOT EXISTS`, so you can apply them repeatedly.

The schema needs a SurrealDB 3.x server, because it uses computed fields and full-text indexes. Applying it again replaces tables, fields, events and functions with the packaged definitions. It does not replace the six analysers or eight of the 40 indexes, because those use `IF NOT EXISTS`. The eight indexes are `idx_hnsw_file_embedding`, `idx_file_content`, `idx_text_de`, `idx_text_fr`, `idx_text_es`, `idx_text_cjk`, `idx_text_code` and `idx_section_hnsw`. To change one of them, remove it, for example with `REMOVE INDEX idx_file_content ON file;`, and define your version before you apply the schema again, because applying the schema defines a missing one from the packaged definition.

The vector length of 1536 is fixed in this release. Besides the HNSW indexes, the `embedding` fields of `file_section` and `file_chunk` have the type `array<float, 1536>`, and the schema defines those fields with `OVERWRITE`, so applying the schema again undoes a change to them. Use embeddings of 1536 numbers.

The examples on this page create their own data with `fn::sfs_*` calls, and some outputs, such as record counts, assume that nothing else exists. Run each section on a database that has only the schema applied, for example by applying the schema to a new database.

To inspect a database that has the schema, use the standard statements:

```surql
INFO FOR DB;
INFO FOR TABLE file;
```

> [!NOTE]
> The TypeScript package embeds an older copy of the schema in `packages/sdk-ts/src/schema_sql.ts`, with 1,405 lines against 2,425 in `file.surql`. It defines 15 of the 32 tables, 44 of the 76 functions, 3 of the 4 events and 1 of the 6 analysers. The missing tables are `blob`, `credential`, `entity`, `file_row`, `folder_digest`, `git_commit`, `group_member`, `mentions`, `quota`, `sfs_job`, `share`, `symbol`, `upload`, `usage`, `user_group`, `webhook` and `webhook_delivery`. The missing event is `evt_file_jobs`. Apply the schema from the Python package or the Rust command line instead.

## How to read the table entries

Each table entry has a **Written by** line and a **Record access** line. The first names the code that fills the table, and the second states in words what a record user may do. Three situations recur under **Written by**:

- A table that a function or event fills during normal use, such as `file_version`.
- A table that only one client fills on request, such as `symbol`, which `surrealfs-rs symbols --index` fills.
- A table that no shipped code fills, such as `folder_digest`. You can write to it yourself, but nothing in the product does.

Every table has a `PERMISSIONS` clause. The clauses apply only to record users, which are users that sign in through the `account` access method described under [Record authentication](#record-authentication). A root, namespace or database user bypasses them. See [Record access](/docs/agent-filesystem/security/record-access) for the model.

## The file table

Every file and every folder is one record in this table. A record's place in the tree is its `parent` link, and its path is computed from the chain of parents. A folder is a record whose `file`, `content` and `symlink` fields are all empty. The [data model](/docs/agent-filesystem/concepts/data-model) page explains the record in prose.

**Written by:** every write path: the Python, Rust and TypeScript clients and the functions in the [SurrealQL function reference](/docs/agent-filesystem/reference/surrealql-functions).

**Record access:** the permission rules for record users are listed under [Permissions for record users](#permissions-for-record-users).

### Fields

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `owner` | `string` | `'root'` | The user that owns the record. A record user cannot change it and no function changes it, so there is no `chown`. A system credential can change it with a direct `UPDATE`. |
| `group` | `option<string>` | `NONE` | An optional group name. Set by `fn::sfs_chgrp`. The Python client does not consult it. |
| `mode` | `int` | `438` | The Unix permission bits as a decimal integer. 438 is octal 666, and 493 is octal 755. |
| `filename` | `string` | required | One path segment. The schema does not validate the name, but the functions split paths on `/`. Names are case-sensitive. |
| `parent` | `option<record<file>>` | `NONE` | The containing folder, or `NONE` for a top-level record. |
| `parent_key` | `string` | set by a field rule | A stored copy of `parent` as a string, with `'root'` for a top-level record. A unique index skips records that have a `NONE` field, so this copy lets `child_unique` cover the top level. It is recomputed on every write. |
| `generation` | `int` | set by a field rule | Starts at 1 and rises by 1 when a write changes the content hash. `chmod`, `mv`, `chgrp` and `meta` updates do not change it. The field rule recomputes it, so a statement cannot set it directly. Under record authentication it does not rise: the counter keeps the value that it had. |
| `path` | `string` | computed | The parent's path, then `/`, then `filename`. It is never stored, so renaming a folder changes the path of every descendant with one update. It cannot be indexed. |
| `is_folder` | `bool` | computed | `true` when `file`, `content` and `symlink` are all `NONE`. An empty text file keeps `content = ''` so that it stays a file. A file committed through the chunked upload has all three empty and reports `true`. |
| `gate` | `option<string>` | computed | Who can traverse down to this record: `NONE` when every ancestor folder lets everyone enter, otherwise the users or groups that can pass all the closed ancestors. See `fn::sfs_gate`. |
| `file` | `option<bytes>` | `NONE` | The bytes of a binary file. |
| `content` | `option<string>` | `NONE` | The text of a text file. The full-text index covers this field. |
| `symlink` | `option<file>` | `NONE` | Typed with the SurrealDB `file` pointer type, not as a link to another record. No shipped code creates or follows a symlink, so treat the field as unused. |
| `content_type` | `string` | required | A media type. The field has no default, so a `CREATE` without it fails. Folders use `inode/directory`. |
| `meta` | `option<object>` | `NONE` | Free-form metadata. The Python client stores the frontmatter of a Markdown file here. Other features use the keys `legal_hold`, `summary`, `simhash`, `encrypted`, `encryption_algo`, `nonce` and `key_id`. |
| `crdt` | `bool` | `false` | `true` for a collaborative document. `enable_crdt` sets it, and nothing turns it off. |
| `hash` | `string` | `''` | The MD5 of the text, or of the unpadded base64 text of the bytes. The `evt_file_hash` event sets it after the content changes. The record that the Python client returns from a write can carry the earlier hash, because the event runs after the statement. The hash is a change marker, not a security measure. A record user cannot write it. A system credential can, and the stored value then stays until the content changes again. |
| `size` | `option<int>` | `NONE` | Set only when a chunked upload is committed. Functions that report a size otherwise count the characters of `content` or the bytes of `file`. |
| `language` | `option<string>` | `NONE` | Chooses which of the `text_*` fields receives the text. No shipped code writes it, so the language fields stay empty until you set it. |
| `encoding` | `option<string>` | `'utf-8'` | Never written by shipped code, so it stays `utf-8`. |
| `is_generated` | `bool` | `false` | Never written by shipped code. |
| `digest` | `option<string>` | `NONE` | Never written by shipped code. |
| `created_at` | `datetime` | `time::now()`, read-only | Set when the record is created. |
| `updated_at` | `datetime` | `time::now()` on every write | Set on every write, including a rewrite with identical content and the hash event's own update. |
| `deleted_at` | `option<datetime>` | `NONE` | Unused. A delete removes the record. |
| `embedding` | `option<array<float>>` | `NONE` | The vector of the whole text. The index `idx_hnsw_file_embedding` requires exactly 1536 numbers. Only a system credential or the `indexer` access can write it. |
| `embedded_at` | `option<datetime>` | `NONE` | When the vector was written. Informational. |
| `embedded_hash` | `option<string>` | `NONE` | The MD5 of the text that the vector came from. The vector is stale when this differs from the MD5 of the current text. |
| `indexer_version` | `option<string>` | `NONE` | The name of the embedder that produced the vector, for example `openai:text-embedding-3-small`. |
| `text_de` | `option<string>` | set by a field rule | Receives `content` when `language` is `de`. Covered by `idx_text_de`. |
| `text_fr` | `option<string>` | set by a field rule | Receives `content` when `language` is `fr`. Covered by `idx_text_fr`. |
| `text_es` | `option<string>` | set by a field rule | Receives `content` when `language` is `es`. Covered by `idx_text_es`. |
| `text_cjk` | `option<string>` | set by a field rule | Receives `content` when `language` is `ja`, `zh` or `ko`. Covered by `idx_text_cjk`. |
| `text_code` | `option<string>` | set by a field rule | Receives `content` when `language` is one of the code languages listed below. Covered by `idx_text_code`. |

### Indexes

| Index | Fields | Kind | Purpose |
| --- | --- | --- | --- |
| `child_unique` | `parent_key, filename` | `UNIQUE` | Makes a name unique in a folder, and serves every lookup of the children of a folder. The order of the fields matters: the reverse order forces a table scan. |
| `idx_file_content` | `content` | `FULLTEXT ANALYZER fts_simple BM25(1.2,0.75)` | Full-text index for `fn::sfs_search_text`. |
| `idx_hnsw_file_embedding` | `embedding` | `HNSW DIMENSION 1536 DIST COSINE TYPE F32 EFC 150 M 12 M0 24` | Vector index for `fn::sfs_search_semantic`. |
| `idx_text_cjk` | `text_cjk` | `FULLTEXT ANALYZER sfs_cjk BM25(1.2,0.75)` | Per-language index for `text_cjk`. No function queries it. |
| `idx_text_code` | `text_code` | `FULLTEXT ANALYZER sfs_code BM25(1.2,0.75)` | Per-language index for `text_code`. No function queries it. |
| `idx_text_de` | `text_de` | `FULLTEXT ANALYZER sfs_de BM25(1.2,0.75)` | Per-language index for `text_de`. No function queries it. |
| `idx_text_es` | `text_es` | `FULLTEXT ANALYZER sfs_es BM25(1.2,0.75)` | Per-language index for `text_es`. No function queries it. |
| `idx_text_fr` | `text_fr` | `FULLTEXT ANALYZER sfs_fr BM25(1.2,0.75)` | Per-language index for `text_fr`. No function queries it. |

The Kind column shows each index in the form that `INFO FOR TABLE` reports, without the `LM` value that the output also carries. `EFC 150`, `M 12` and `M0 24` are the defaults of an HNSW index, and `BM25(1.2,0.75)` is the default of `BM25`. Only `idx_hnsw_file_embedding` writes the HNSW values out in `file.surql`. The other HNSW indexes, on `file_chunk` and `file_section`, and the `idx_text_*` indexes leave them out and receive the same values.

### Language fields

The `text_*` fields receive a copy of `content` for the languages in the table below. Each has its own full-text index and analyser. No shipped code sets `language`, so the fields are empty until you set it, and no function queries these indexes. Query them with the `@@` operator.

| Field | Receives `content` when `language` is | Analyser | Index |
| --- | --- | --- | --- |
| `text_de` | `de` | `sfs_de` | `idx_text_de` |
| `text_fr` | `fr` | `sfs_fr` | `idx_text_fr` |
| `text_es` | `es` | `sfs_es` | `idx_text_es` |
| `text_cjk` | `ja`, `zh` or `ko` | `sfs_cjk` | `idx_text_cjk` |
| `text_code` | `code`, `python`, `rust`, `typescript`, `javascript`, `go`, `c`, `cpp`, `html`, `css`, `json`, `yaml`, `toml`, `sql`, `surrealql` or `shell` | `sfs_code` | `idx_text_code` |

```surql
fn::sfs_write('/handbuch/konfiguration.txt', 'Die Konfigurationen der Systeme sind wichtig.', NONE, NONE, 'alice').path;
//- '/handbuch/konfiguration.txt'

fn::sfs_write('/handbuch/notes.txt', 'Configuration notes for the systems.', NONE, NONE, 'alice').path;
//- '/handbuch/notes.txt'

-- The default full-text search stems with English rules, so the German plural is not matched
fn::sfs_search_text('Konfiguration', 5, 'any', 'alice').map(|$h| $h.path);
//- []

-- Set the language of the file. Nothing in the repository does this automatically
UPDATE fn::sfs_resolve('/handbuch/konfiguration.txt') SET language = 'de' RETURN NONE;
SELECT VALUE path FROM file WHERE text_de @@ 'Konfiguration';
//- ['/handbuch/konfiguration.txt']

SELECT VALUE path FROM file WHERE text_de != NONE;
//- ['/handbuch/konfiguration.txt']
```

### Computed fields

`path`, `is_folder` and `gate` are computed when a record is read, and the database never stores them. A rename or a move of a folder is one update to `filename` or `parent`, and the paths of all descendants follow.

```surql
fn::sfs_write('/projects/launch/plan.md', 'Launch plan', NONE, NONE, 'alice').path;
//- '/projects/launch/plan.md'

-- Renaming a folder is one update. The path of everything below it follows
fn::sfs_mv('/projects/launch', '/projects/q4-launch', 'alice').path;
//- '/projects/q4-launch'

SELECT VALUE path FROM file WHERE filename = 'plan.md';
//- ['/projects/q4-launch/plan.md']

SELECT path, is_folder FROM file WHERE filename IN ['q4-launch', 'plan.md'] ORDER BY path;
//- [{ is_folder: true, path: '/projects/q4-launch' }, { is_folder: false, path: '/projects/q4-launch/plan.md' }]
```

### Generation and hash

The `hash` field is the MD5 of the text, or of the base64 text of the bytes without padding. The `evt_file_hash` event sets it after the content changes. The `generation` field starts at 1 and increases by 1 when the new content hashes differently from the stored `hash`, so identical content, `chmod`, `mv`, `chgrp` and `meta` updates leave it alone. A record user cannot write either field. A system credential can write `hash`, which then keeps that value until the content changes again, but the field rule recomputes `generation`, so a statement cannot set it directly.

```surql
fn::sfs_write('/notes/a.md', 'one', NONE, NONE, 'alice').generation;
//- 1

-- Identical content does not change the generation
fn::sfs_write('/notes/a.md', 'one', NONE, NONE, 'alice').generation;
//- 1

fn::sfs_write('/notes/a.md', 'two', NONE, NONE, 'alice').generation;
//- 2

-- A mode change does not change the generation
fn::sfs_chmod('/notes/a.md', 384);
//- true

fn::sfs_stat('/notes/a.md').{ generation, hash, mode };
//- { generation: 2, hash: 'b8a9f715dbb64fd5c56e7783c6820a61', mode: 384 }

crypto::md5('two');
//- 'b8a9f715dbb64fd5c56e7783c6820a61'
```

> [!WARNING]
> Under record authentication the database does not keep the value that it computes for `generation`, because the field has `PERMISSIONS FOR update WHERE false`. The counter keeps the value that it had, which is 1 for a file that a record user created, so `$if_generation` cannot detect a conflicting write.

### Folder nesting depth

The `gate` field refers to its parent's `gate`, so every level of folder depth adds work to each read and write of a record. Down to about four levels the time hardly changes. Beyond that, each extra level makes a write take roughly three times as long, and a read takes somewhat less than that. Keep trees shallow. The [data model](/docs/agent-filesystem/concepts/data-model#folder-depth) page has measurements.

### Events

All four events are defined on the `file` table, and they run for every client and every credential.

| Event | Fires when | What it does |
| --- | --- | --- |
| `evt_file_move` | A record is updated and `parent` or `filename` changed. | For a session with `$auth` set, which means a record user, throws `sfs:denied: rename needs w+x on both folders` unless the user can add and remove entries in both the old and the new folder. It does nothing for a system credential. |
| `evt_file_hash` | The event is not a delete, and `content` or `file` changed. | Updates `hash` to the MD5 of the text, the MD5 of the base64 text of the bytes, or `''`. |
| `evt_file_jobs` | The same condition as `evt_file_hash`. | When the hash is not empty, creates or resets three `sfs_job` records for the file, with the kinds `detect`, `chunk` and `symbols`, the status `pending` and 0 attempts. |
| `evt_file_version` | A record is deleted, or updated with a change to `generation`, `content`, `file`, `parent`, `filename` or `mode`. | Creates a `file_version` record with the state before the change. See [`file_version`](#file_version). |

### Permissions for record users

These clauses apply to a record user. The record's owner is `owner`, the digit that applies is chosen as described for [`fn::sfs_bits_grp`](/docs/agent-filesystem/reference/surrealql-functions#permission-predicates), and a closed folder above a record hides it through `gate`.

| Operation | A record user may |
| --- | --- |
| Read | Read a record when the gate lets the user through and the applicable digit, with the group digit for a member of the record's `group`, has the read bit. The `indexer` access can read every record. |
| Create | Create a record that has the user's own name as `owner`, in a folder where the user has write and entry permission, and not in a way that breaks the `/home` rules. A record directly under `/` has no folder, so the folder test passes for every record user. |
| Update | Change a record when the gate lets the user through and the user has either the write bit on the record or write and entry permission on its folder. The `indexer` access can always update. The field rules below then limit which fields change. |
| Delete | Delete a record from a folder where the user has write and entry permission, when the record has no children, has no legal hold of its own and does not break the `/home` rules. For a record directly under `/` the folder test passes for every record user. |

| Field | Who may update it |
| --- | --- |
| `owner`, `generation`, `hash` | Nobody. |
| `group` | The owner, or `root`. |
| `mode` | The owner. |
| `file`, `content`, `symlink`, `content_type`, `meta`, `crdt`, `size` | A user with the write bit on the record, without group rules. |
| `language`, `encoding`, `is_generated`, `digest` | A user with the write bit on the record, or the `indexer` access. |
| `embedding`, `embedded_at`, `embedded_hash`, `indexer_version` | The `indexer` access. |

A member of a record's group can read the record and create and rename entries in the folder, but cannot change its content, because the field rules ignore groups.

> [!WARNING]
> A record directly under `/` has no parent folder, and [`fn::sfs_can_enter`](/docs/agent-filesystem/reference/surrealql-functions#permission-predicates) returns `true` when the folder is `NONE`. The folder test therefore passes for every record user at the top level. Any record user can create a top-level record, can rename or move any top-level record that the user can read, and can delete any such record that has no children, whoever owns it. A move can also leave the owner unable to reach the file, because the `gate` of a file follows its folder. Only records below a folder that withholds write and entry permission from other users are protected by the folder rules, so files that need that protection belong inside a home folder such as `/home/alice`.

> [!WARNING]
> The delete rule reads only the `meta.legal_hold` flag of the record itself. A hold on a folder makes `fn::sfs_rm` refuse to delete the files inside it, but a direct `DELETE` of one of those files by a record user succeeds. A user with the write bit on a record, including a user who does not own it, can set or clear its hold with `fn::sfs_set_legal_hold`, because the `meta` field accepts that user's update.

A refused field update is reverted without an error, and a refused delete deletes nothing, so the statement succeeds and the record stays as it was. A client has to read the record back to confirm a change.

### The `/home` seed

The last statements of `file.surql` create the folder `/home`, with the record id `file:home`, the owner `root`, the mode 511 and the content type `inode/directory`. An update first takes back a `/home` that someone else created, and an `INSERT IGNORE` creates it when it is missing, so applying the schema twice is safe. The rules for `/home` say that only `root` owns it and that a record directly under it must be named after its creator.

## Search analysers

An analyser turns text into the terms that a full-text index stores. The schema defines six. They use `IF NOT EXISTS`, so applying the schema again does not change an analyser that exists.

| Analyser | Tokenizers | Filters | Used by |
| --- | --- | --- | --- |
| `fts_simple` | `blank`, `class`, `camel`, `punct` | `snowball(english)` | `idx_file_content`, and the query side of `fn::sfs_search_text` |
| `sfs_de` | `blank`, `class` | `lowercase`, `snowball(german)` | `idx_text_de` |
| `sfs_fr` | `blank`, `class` | `lowercase`, `snowball(french)` | `idx_text_fr` |
| `sfs_es` | `blank`, `class` | `lowercase`, `snowball(spanish)` | `idx_text_es` |
| `sfs_cjk` | `blank` | `ngram(1,2)` | `idx_text_cjk` |
| `sfs_code` | `class`, `camel` | `lowercase` | `idx_text_code` |

The `fts_simple` analyser keeps punctuation as terms, does not remove stop words and stems every language with the English rules. See [Search](/docs/agent-filesystem/concepts/search).

## Content storage

Four tables support the chunked upload that `surrealfs-rs upload` uses, and a fifth, `quota`, is defined for limits that no code enforces. A file committed through the upload has no `content` and no `file` bytes, so it reports `is_folder: true`. See [Content storage](/docs/agent-filesystem/concepts/content-storage) and the warning in the [chunked uploads](/docs/agent-filesystem/reference/surrealql-functions#chunked-uploads) section of the function reference.

### `file_chunk`

`file_chunk` holds the manifest of a file that was stored through the chunked upload, with one record for each chunk.

**Written by:** `fn::sfs_upload_commit`, which fills `file`, `offset`, `length` and `blob`. No code writes the other fields.

**Record access:** a record user can read a chunk record when the file is readable. Only the `indexer` access or a system credential can write it.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `file` | `record<file>` | required | The file that the chunk belongs to. |
| `chunk_index` | `option<int>` | `NONE` | Never written. |
| `byte_offset` | `option<int>` | `NONE` | Never written. |
| `byte_length` | `option<int>` | `NONE` | Never written. |
| `text` | `option<string>` | `NONE` | Never written. |
| `embedding` | `option<array<float, 1536>>` | `NONE` | Never written. The index `idx_hnsw_chunk_embedding` covers it. |
| `hash` | `option<string>` | `NONE` | Never written. |
| `offset` | `option<int>` | `NONE` | The byte offset of the chunk in the file. |
| `length` | `option<int>` | `NONE` | The length of the chunk in bytes. |
| `blob` | `option<record<blob>>` | `NONE` | The `blob` record that holds the chunk. |

| Index | Fields | Kind | Purpose |
| --- | --- | --- | --- |
| `idx_chunk_file_order` | `file, chunk_index` | standard | Lists the chunks of a file in order. No code fills `chunk_index`. |
| `idx_chunk_offset` | `file, offset` | standard | Finds the chunks that cover a byte range. |
| `idx_hnsw_chunk_embedding` | `embedding` | `HNSW DIMENSION 1536 DIST COSINE TYPE F32 EFC 150 M 12 M0 24` | Covers a field that no code writes. |

### `blob`

Each `blob` record is one stored chunk. The record id is the chunk id that the client chose. The Rust client uses `b3:` followed by a BLAKE3 hash. The bytes are stored inside the record. There is no external object store.

**Written by:** `fn::sfs_upload_chunk` creates the record, and `fn::sfs_upload_commit` increases `refs`. Nothing decreases `refs`.

**Record access:** every record user can read, create, update and delete these records, so a record user can read the bytes of another user's chunks.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `size` | `int` | required | The size of the chunk before compression. |
| `stored` | `int` | required | The size of the stored bytes. |
| `codec` | `string` | required | `none` or `zstd`, as the client reports it. The schema does not validate it. |
| `tier` | `string` | required | Always `inline`. |

## Versions

### `file_version`

`file_version` holds a snapshot of the state that a file had before a change. The `evt_file_version` event writes it when the text, bytes, mode, name or parent changes, and when the file is deleted. After a write, the snapshot holds the earlier text. A `chmod` or a rename changes no text, so its snapshot holds the live text together with the earlier mode, owner and gate, and the current generation and text then appear in this table too. History is keyed by path.

**Written by:** the `evt_file_version` event only.

**Record access:** a record user can read a snapshot when the owner, mode and gate stored in the snapshot allow it, so a later `chmod` does not make earlier snapshots private. The snapshot that a `chmod` creates carries the earlier mode and the live text. A user who could read a file before it was made private can therefore still read its current text through [`fn::sfs_history`](/docs/agent-filesystem/reference/surrealql-functions#fnsfs_history) and [`fn::sfs_version_content`](/docs/agent-filesystem/reference/surrealql-functions#fnsfs_version_content). Nobody can write the table directly.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `file` | `record<file>` | required | The file that the snapshot belongs to. |
| `generation` | `int` | required | The generation that the file had before the change. A `chmod` or `rename` snapshot has the current generation, and a `chmod` snapshot and the next `write` snapshot can share a generation. |
| `path` | `option<string>` | `NONE` | The path at the time of the event. For a rename, the new path. |
| `content` | `option<string>` | `NONE` | The text before the change. |
| `file_bytes` | `option<bytes>` | `NONE` | The bytes before the change. |
| `content_type` | `string` | required | The content type before the change. |
| `hash` | `string` | required | The hash before the change. |
| `author` | `string` | required | `fn::sfs_me()` when there is one, otherwise the owner of the file. Under a system credential the author is therefore the owner, not the writer. |
| `owner` | `string` | required | The owner before the change. |
| `mode` | `int` | required | The mode before the change. |
| `gate` | `option<string>` | `NONE` | The gate of the parent at the time of the event. |
| `op` | `string` | required | `delete` for a delete. Otherwise `chmod` when the mode changed, `rename` when the name or parent changed, and `write` in every other case. |
| `size` | `int` | required | The characters of the text, or the bytes, or 0 for a folder. |
| `created_at` | `datetime` | required | When the snapshot was taken. |

| Index | Fields | Kind | Purpose |
| --- | --- | --- | --- |
| `idx_version_file_gen` | `file, generation` | standard | Finds the snapshots of a file by generation. |
| `idx_version_path` | `path` | standard | Serves `fn::sfs_history`. |

### `file_section`

**Written by:** the Python client's `reindex_embeddings`, which runs as `root` and needs an embedder that you supply. Neither the Python client nor the `surrealfs-rs` command writes sections when a file is written, and deleting a file leaves its sections behind.

A `share` record holds a token for a path. In this release nothing turns a token into file access.

**Written by:** `fn::sfs_create_share` and `fn::sfs_revoke_share`.

**Record access:** every record user can read the table, including the tokens. A user can create, update and delete the shares that they created.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `path` | `string` | required | The shared path. |
| `mode` | `string` | `'ro'` | `ro` or `append` according to the schema comment. Not validated, and nothing interprets it. |
| `token` | `string` | required | 32 random alphanumeric characters. |
| `created_by` | `string` | required | The identity that created the share. |
| `expires_at` | `option<datetime>` | `NONE` | `NONE` for a share that does not expire. |
| `revoked` | `bool` | `false` | `true` after `fn::sfs_revoke_share`. |
| `created_at` | `datetime` | `time::now()` | When the share was created. |

| Index | Fields | Kind | Purpose |
| --- | --- | --- | --- |
| `idx_share_token` | `token` | `UNIQUE` | Makes a token unique, and serves `fn::sfs_resolve_share`. |

### `credential`

A `credential` record holds a credential for the protocol servers: WebDAV, S3, SSH, Slack, Teams or bearer tokens. See [Credentials](/docs/agent-filesystem/security/credentials).

**Written by:** the Rust client, with `surrealfs-rs credential create`.

**Record access:** no record user can read or write the table. The rule tests for an access method named `admin`, which the schema does not define.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `kind` | `string` | required | One of `webdav`, `s3`, `ssh`, `slack`, `teams` and `bearer`. |
| `identifier` | `string` | required | The user name, access key, key fingerprint or token, depending on the kind. |
| `secret_hash` | `option<string>` | `NONE` | Despite the name, the Rust command line stores the value that it is given without hashing it. The protocol servers accept a plaintext match or an unsalted SHA-256 digest, and a missing value matches any secret. |
| `user_id` | `string` | required | The identity that the credential stands for. |
| `enabled` | `bool` | `true` | `false` after a revoke. A disabled credential does not resolve. |
| `created_at` | `datetime` | `time::now()`, read-only | When the credential was created. |
| `meta` | `option<object>` | `NONE` | Free-form data. |

| Index | Fields | Kind | Purpose |
| --- | --- | --- | --- |
| `idx_credential_lookup` | `kind, identifier` | `UNIQUE` | Allows one credential for each kind and identifier, and serves `fn::sfs_resolve_credential`. |

## Record authentication

`record_auth.surql` is optional. Without it the permission clauses above do nothing for the clients that Agent Filesystem ships, because they sign in with a system credential. With it, a user can sign in as a record user, and the database enforces the rules itself. Provision users with `python -m surrealfs.users add name --password hunter123`, which also creates the user's private home folder. The command takes its connection settings only from the `SURREALDB_*` environment variables, and the [function reference](/docs/agent-filesystem/reference/surrealql-functions#calling-the-functions-as-a-record-user) shows the full sequence. See [Record access](/docs/agent-filesystem/security/record-access).

### `user`

The record id is the user name, for example `user:alice`, so `fn::sfs_me()` reads the name from `$auth` without fetching a record, and the name is unique by construction.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `password` | `string` | required | An Argon2 hash, which `surrealfs.users` creates with `crypto::argon2::generate`. |
| `created_at` | `datetime` | `time::now()`, read-only | When the user was created. |

A record user can read only their own record, which includes the password hash. Nobody can create, change or delete a `user` record through a record session. There is no sign-up, so an administrator with a system credential creates every user.

### Access methods

| Access | Signs in | Duration |
| --- | --- | --- |
| `account` | A user that exists, whose name is not `root`, `indexer`, `projector` or `compactor`, and whose password matches. | Token 15 minutes, session 12 hours |
| `indexer` | The user named `indexer` only. | The same |
| `projector` | The user named `projector` only. | The same |
| `compactor` | The user named `compactor` only. | The same |

The `account` access is the one that the Python clients use. The `indexer` access has extra rights: it can read every `file` record, it can update records that the field rules allow without passing the gate, and it is the only access that can write the embedding fields and most of the derived tables. The `projector` access appears only in the rule for `sfs_job`, and nothing else uses the `compactor` access. The shipped Python surfaces cannot sign in through the three special accesses.

## Tables that clients create without a definition

Some clients write to tables that the schema does not define, so SurrealDB creates them as schemaless tables without permissions. A record user cannot read or write them.

| Table | Created by |
| --- | --- |
| `agent_mailbox` | The Rust client's table-based mailbox. |
| `file_mailbox` | The TypeScript SDK's table-based mailbox. |

The two names differ, so a Rust sender and a TypeScript worker do not see each other's messages. The Python and TypeScript file-based mailboxes use ordinary files under `/agents` instead. See [Mailboxes](/docs/agent-filesystem/concepts/mailboxes).

## What happens when a file is deleted

A delete removes the `file` record and the link records that touch it. Other tables that point at the file by a record link are not cleaned up.

| Table | After a delete |
| --- | --- |
| `file_version` | A snapshot with the operation `delete` is added. |
| `references`, `supersedes`, `derives_from`, `implements`, `links_to`, `mentions` | The links that touch the file are deleted. |
| `file_section`, `symbol`, `file_row`, `sfs_job`, `entity` | The records remain. Those that point at the file now point at a record that does not exist, and a section or a symbol in that state can make a search or a lookup fail. |
| `file_lock` | The record remains until it is replaced or deleted. |
| `file_chunk`, `blob`, `usage` | The records remain, and `refs` is not decreased. |
| `file_crdt_update`, `file_crdt_snapshot` | The records remain. |

```surql
fn::sfs_write('/notes/a.md', 'one', NONE, NONE, 'alice').path;
//- '/notes/a.md'

SELECT count() AS jobs FROM sfs_job GROUP ALL;
//- [{ jobs: 3 }]

fn::sfs_rm('/notes/a.md', false, 'alice');
//- true

-- The jobs of the deleted file remain
SELECT count() AS jobs FROM sfs_job GROUP ALL;
//- [{ jobs: 3 }]

-- A snapshot with the operation delete records the removal
SELECT op, path FROM file_version;
//- [{ op: 'delete', path: '/notes/a.md' }]
```

Deleting a folder with [`fn::sfs_rm`](/docs/agent-filesystem/reference/surrealql-functions#fnsfs_rm) removes the folder and its direct children only. Records deeper in the tree stay in the `file` table, and they are no longer reachable by path.
