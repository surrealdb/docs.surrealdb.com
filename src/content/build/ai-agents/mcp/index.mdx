# SurrealDB MCP Server

The SurrealDB MCP server is a hosted [Model Context Protocol](https://modelcontextprotocol.io) endpoint at **`https://mcp.surrealdb.com`**. Point an MCP client at that URL, sign in with your Surreal ID, and your assistant can work with your SurrealDB Cloud account directly: list and deploy instances, check metrics and logs, run SurrealQL against a running instance, and manage [Spectron](/docs/spectron) contexts.

You do not install or run anything locally. The server authenticates each user separately and calls the Cloud API with that user's own permissions.

> [!NOTE]
> This page covers the hosted server for **SurrealDB Cloud**. To give an assistant tools against a database you run yourself, see [Embedded MCP](/docs/build/ai-agents/mcp/embedded).

## What you can do

- **Deploy and operate instances** — create an organisation, check whether it can deploy, estimate cost, deploy, then pause, resume, resize, or upgrade the instance.
- **Query your data** — run SurrealQL against any ready instance on SurrealDB 3.1 or later, without pasting a connection string or a token into your editor.
- **Investigate problems** — read instance status, metrics, and logs in the same conversation where you are writing the query that caused them.
- **Manage access** — invite members, change roles, and revoke invitations.
- **Track spend** — read usage, invoices, and coupons, and complete billing setup before a paid deploy.
- **Work with Spectron** — create contexts, manage principals and keys, and call memory tools such as `remember` and `recall`.

## Endpoint

| | |
| --- | --- |
| **URL** | `https://mcp.surrealdb.com` |
| **Transport** | Streamable HTTP |
| **Authentication** | OAuth 2.1 with your Surreal ID, or a personal access token as a Bearer token |
| **Session header** | `mcp-session-id`, returned on `initialize` and sent on every later request |

The same server is also mounted on the API host at `https://api.surrealdb.com/api/mcp`. Both expose identical tools; prefer `mcp.surrealdb.com`.

## Connect a client

Most clients need only the URL. When the client supports OAuth, it discovers the authorisation endpoints itself and opens a browser for you to sign in.

Run `/mcp` in Claude Code to start the sign-in flow, then check the server is listed as connected.

```json
  }
```

Open **Settings → MCP**, then click **Connect** next to `surrealdb` to sign in.

```json
  }

```

To confirm the connection, ask the assistant to call `list_organizations`. It should return your organisations, each with an `id`, the value every organisation-scoped tool needs.

## Authentication

Every tool except `mcp_auth` needs a token, and the token decides what the tool can reach. The server verifies the token, then calls the Cloud API as you, so an assistant can never see an organisation you are not a member of.

### Sign in with your Surreal ID

Clients with OAuth support need no credentials in their config. On the first protected call the server answers `401` with a `WWW-Authenticate` header pointing at its metadata, and the client walks the standard discovery flow:

| Endpoint | Purpose |
| --- | --- |
| `/.well-known/oauth-protected-resource` | Protected resource metadata ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)) |
| `/.well-known/oauth-authorization-server` | Authorisation server metadata ([RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)) |
| `/oauth/register` | Dynamic client registration |
| `/oauth/authorize` | Authorisation request; opens Surreal ID sign-in in the browser |
| `/oauth/token` | Token exchange and refresh |

The server requires PKCE with `S256`, and it requires the `resource` parameter (`https://mcp.surrealdb.com`) on both the authorisation request and the token exchange, as described in [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707). Supported grants are `authorization_code` and `refresh_token`. Your email address must be verified on your Surreal ID before sign-in succeeds.

A signed-in session is not narrowed: it can call every tool the server publishes, limited only by your role in each organisation.

### Personal access tokens

For clients without OAuth, for scripts, and for anything running unattended, create a personal access token in the [account portal](https://account.surrealdb.com) and send it as a Bearer token:

```bash
curl -i https://mcp.surrealdb.com \
  -H "Authorization: Bearer sdbp_your_token" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1.0.0"}}}'
```

Every session starts with `initialize`. The response carries an `mcp-session-id` header; send that header with later calls such as `tools/list` so they land on the same session.

Tokens start with `sdbp_`. Unlike a browser sign-in, a token carries only the scopes you selected when you created it, and a tool whose scope is missing fails with `Insufficient scopes`:

| Scope | Grants |
| --- | --- |
| `read:cloud` | Read organisations, instances, Spectron contexts, usage, billing details, metrics, and logs |
| `write:cloud-instances` | Deploy, pause, resume, resize, upgrade, and delete instances; estimate cost |
| `query:cloud-instances` | Run tools against an instance database, and mint instance database tokens |
| `write:cloud-organization` | Create and rename organisations; manage members, roles, and invitations |
| `write:cloud-billing` | Update billing contacts and manage Spectron context packages |
| `write:cloud-spectron` | Create, update, and delete Spectron contexts, principals, keys, and scopes |
| `query:spectron-contexts` | Call memory, chat, and document tools against a Spectron context |

Scopes are checked per tool rather than per group, so pair a write scope with `read:cloud`. An assistant that can deploy an instance but cannot list your organisations has no way to find the `organization_id` it needs.

> [!IMPORTANT]
> A personal access token is a long-lived credential for your whole Cloud account. Grant the narrowest set of scopes the task needs, keep it out of committed config files, and revoke it in the account portal when the assistant no longer needs it.

### The `mcp_auth` tool

`mcp_auth` is the one tool callable without a token. It returns the OAuth endpoints and tells the agent to hand the sign-in back to you. Assistants call it when they hit an authentication error; nothing else works until the session is authenticated.

## Available tools

The server publishes 90 tools. Call `tools/list` for the current schemas. Each tool declares annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`) so a client can auto-approve reads and prompt before writes.

Each group below lists its tools and the scopes that cover them. A personal access token needs only the scope matching what it actually calls.

**Authentication** (no scope)
`mcp_auth`

**Profile and organisations** (`read:cloud`, `write:cloud-organization`)
`get_cloud_profile`, `list_organizations`, `get_organization`, `create_organization`, `update_organization`

**Catalogue** (`read:cloud`)
`list_regions`, `list_instance_types`, `list_instance_versions`, `list_billing_countries`, `list_context_regions`

**Instances** (`read:cloud`, `write:cloud-instances`)
`list_organization_instances`, `get_instance`, `estimate_instance_cost`, `deploy_instance`, `pause_instance`, `resume_instance`, `update_instance_type`, `update_instance_version`, `update_instance_compute_units`, `update_instance_storage`, `update_instance_access_type`, `update_instance_capabilities`, `get_instance_backup_policy`, `update_instance_backup_policy`, `delete_cloud_instance`

**Monitoring and usage** (`read:cloud`)
`get_instance_status`, `get_instance_metrics`, `get_instance_logs`, `get_instance_usage`, `get_organization_usage`

**Billing and payment** (`read:cloud`, `write:cloud-billing`)

**Spectron contexts** (`read:cloud`, `write:cloud-spectron`)
`list_organization_spectron_contexts`, `get_spectron_context`, `create_spectron_context`, `update_spectron_context`, `delete_spectron_context`, `get_spectron_context_config`, `get_spectron_context_usage`, `list_spectron_context_providers`, `list_spectron_context_verbs`

Organisation-scoped tools take `organization_id`, which is the `id` field from `list_organizations` rather than the display name. Instance tools take `instance_id` from `list_organization_instances`.

### Resources and prompts

Three catalogue endpoints are also exposed as MCP resources, for clients that prefer resources over tool calls: `surrealcloud://catalog/regions`, `surrealcloud://catalog/instance-types`, and `surrealcloud://catalog/instance-versions`.

One prompt, `deploy_instance_wizard`, scaffolds a guided deployment: it resolves organisation, region, instance type, and version, estimates the cost, and waits for your confirmation before the billable call. It takes optional `purpose`, `organization`, and `region` arguments.

## Querying instance data

`call_instance_tool` forwards a tool call to a Cloud instance's own MCP server, so the assistant can read and write data through the same connection it uses to manage the instance. It needs `query:cloud-instances`.

The instance must be **ready** and running **SurrealDB 3.1 or later**; anything else returns an error saying which condition failed. A typical sequence:

1. `list_organizations` → take `id`
2. `list_organization_instances({ organization_id })` → take `instance_id`
3. `get_instance({ instance_id })` → confirm `state` is `ready` and the version is 3.1 or later
4. `call_instance_tool(instance_id, "use", { namespace, database })`
5. `call_instance_tool(instance_id, "query", { query: "SELECT * FROM person LIMIT 10" })`

Namespace and database selection persists for the life of the pooled connection to that instance, so step 4 is not repeated on every call. The pool holds up to three instances per user and drops a connection after about four minutes idle, so re-issue `use` if a later call reports no context. For a namespace or database whose name starts with a digit or contains special characters, skip `use` and send an escaped statement instead:

```surql
USE NS `8889` DB `56+24546`;
```

Individual tool calls time out after 65 seconds.

### Published tools

An instance's MCP server publishes the tools below; pass the name as `tool` and its arguments as `arguments`. `list_instance_tools` returns the live schemas, including anything not listed here.

| Tool | Purpose |
| --- | --- |
| `use` | Select namespace and database |
| `query` | Run SurrealQL |
| `select`, `create`, `insert`, `upsert`, `update`, `delete`, `relate` | Data manipulation helpers |
| `run` | Call a database function with typed arguments |
| `list` | List namespaces, databases, tables, indexes, users, … |
| `info` | Schema or engine information for a scope |

These are the same tools a self-hosted server exposes. See [Embedded MCP](/docs/build/ai-agents/mcp/embedded) for their behaviour, limits, and permission model.

Spectron contexts work the same way through `call_spectron_tool`, which proxies `remember`, `recall`, `context`, `reflect`, `forget`, `upload`, and `inspect`. See the [Spectron MCP tools reference](/docs/spectron/integrations/mcp-server/tools-reference).

## Deploying an instance

Deployment is billable and depends on organisation state, so the server exposes a readiness check rather than letting an agent guess. Call `get_organization_deployment_readiness` before `deploy_instance`; it returns `can_deploy_free`, `can_deploy_paid`, quota counts, billing status, and a `blockers` array where each entry carries its own remediation.

New organisations on the Start plan often have no free instance quota, which makes billing setup the first blocker to clear:

1. `get_organization_billing_requirements` — required fields and valid country codes
2. `update_organization_billing` — set the contact and address, or `copy_organization_billing_from` another organisation you belong to
3. `get_organization_payment_setup_url` — returns a Stripe-hosted checkout URL for you to open in a browser
4. Poll `get_organization_deployment_readiness` until `billing.payment_complete` is `true`; the payment status arrives by webhook, so it is not instant
5. `deploy_instance`

`Name`, `Email`, `AddressLine1`, `City`, and `Country` are required on the billing contact, and `Country` must be an ISO 3166-1 alpha-2 code from `list_billing_countries`. No tool accepts card details as arguments. Payment always goes through the hosted checkout page.

The deploy configuration nests compute selection under `specs`:

```json
{
  "name": "production",
  "org": "<organization_id>",
  "region": "<region slug from list_regions>",
  "specs": {
    "slug": "<slug from list_instance_types>",
    "version": "<version from list_instance_versions>",
    "compute_units": 1
  }
}
```

Omit `compute_units` for the `free` slug. `access_type` accepts `public`, `private`, or `dual`. Use `estimate_instance_cost` with the same configuration to see the cost before committing.

## Sessions and limits

The server keeps one MCP session per `mcp-session-id`, bound to the user who created it. A session id presented by anyone else is rejected as `Session not found`.

| Limit | Value |
| --- | --- |
| Session idle timeout | 30 minutes |
| Concurrent sessions per user | 3 (the least recently used is closed) |
| Pooled instance connections per user | 3 |
| Instance tool call timeout | 65 seconds |
| OAuth requests per minute | 10 to `/oauth/register`, 20 to `/oauth/authorize` and `/oauth/token` |

## Guardrails

The server adds friction to the operations that are hardest to undo:

- **Instance deletion** requires `confirm_instance_name` to match the instance's current display name exactly. The server re-reads the live name and refuses on any mismatch, which stops an agent deleting the wrong instance from a stale id.
- **Payment details** are only ever entered by you, in Stripe's hosted checkout. No tool accepts a card number, CVV, or payment token.
- **Terms acceptance** requires `confirm_use_terms: true`, and the agent is instructed to show you the documents from `get_cloud_terms_and_conditions` first.
- **Secrets are shown once.** `mint_spectron_scoped_key`, `mint_spectron_access_token`, and `rotate_spectron_context_api_key` return a key that is never returned again. Provider API keys are never returned at all.

Tool annotations are hints, not enforcement. Treat a destructive call as destructive even when a client offers to auto-approve it.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `401` with a `WWW-Authenticate` header | No token, or an expired one. Sign in again in the client, or check the personal access token has not been revoked. |
| `Invalid resource` on `/oauth/authorize` | The client did not send `resource=https://mcp.surrealdb.com`. Update the client, or authenticate with a personal access token instead. |
| `Insufficient scopes` | The personal access token lacks the scope that tool requires. Create a new token with the scope added; scopes cannot be changed after creation. |
| `Unauthorized: email not verified` | Verify the email address on your Surreal ID, then sign in again. |
| `Session not found` | The session expired after 30 minutes idle, or was evicted. Reconnect so the client sends a fresh `initialize`. |
| `Instance is not ready (state: …)` | Wait until `get_instance` reports `state: ready`. |
| `instance MCP requires 3.1.0 or later` | The instance runs an older SurrealDB. Upgrade it with `update_instance_version`. |
| Agent cannot find an organisation | It is passing a display name. Organisation-scoped tools need the `id` from `list_organizations`. |
