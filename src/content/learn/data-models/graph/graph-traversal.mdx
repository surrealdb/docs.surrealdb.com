# Graph traversal

Graph queries in SurrealDB use SurrealQL’s `->` arrow syntax to walk relationships between records.

## Basic forward and reverse traversals

```surql
SELECT ->wrote->post.* AS userPosts
  FROM users:alice;
```

- `FROM users:alice` starts at that node.
- `->wrote->posts.*` follows the `wrote` edge to posts and returns full post records as `userPosts`.

Traverse in the reverse direction (for example, from a post to its authors):

```surql
SELECT <-wrote<-author AS authors
  FROM post:helloworld;
```

`<-wrote<-author` means “follow any `wrote` edge **into** this post from an `author`”.

### A single related record as a value

A traversal always returns an array, even when a record has only one edge of that kind. When there is only ever one, take the first element, either of the traversal or of the field read through it:

```surql
CREATE user:1;
CREATE card:1 SET name = 'visa';
RELATE user:1->has_card->card:1;

SELECT
	->has_card->card.name AS all_names,
	(->has_card->card.name)[0] AS name,
	->has_card->card[0].name AS also_name
FROM user:1;
```

```surql title="Output"
[
	{
		all_names: ['visa'],
		also_name: 'visa',
		name: 'visa'
	}
]
```

To be sure there is only one, add a [`UNIQUE` index](/docs/reference/query-language/statements/define/indexes#unique-index) on the edge's `in` field, so that a user cannot have a second `has_card` edge.

## Chaining paths

From comments, find authors and then all of their comments:

```surql
SELECT <-wrote<-user->wrote->comment FROM comment;
```

## Filtering a traversal

An arrow itself is already a filter on the edge table. For example, `->wrote->comment` follows only `wrote` edges and leaves every other kind alone. Two further filters sit alongside it - one on the edge's own fields, and one on how many edge tables to follow at once.

These examples use a user with two outgoing edges, one of which carries fields:

```surql
CREATE user:mcuserson SET name = "User McUserson";
CREATE comment:one SET text = "I learned something new!";
CREATE cat:pumpkin SET name = "Pumpkin";

RELATE user:mcuserson->wrote->comment:one SET
	location = "Arizona",
	os = "Windows 11",
	mood = "happy";

RELATE user:mcuserson->likes->cat:pumpkin;
```

A condition in parentheses applies to the edge, and only the edges that pass it are followed:

```surql
SELECT VALUE ->(wrote WHERE location = "Arizona")->comment FROM ONLY user:mcuserson;
```

```surql title="Output"
[comment:one]
```

The fields named in the condition are the edge's own, so a condition nothing matches ends the walk there:

```surql
SELECT VALUE ->(wrote WHERE location = "Oregon")->comment FROM ONLY user:mcuserson;
```

```surql title="Output"
[]
```

Square brackets look and act similar but are a different mechanism. `[WHERE ...]` is the generic [array filter](/docs/reference/query-language/language-primitives/data-types/arrays#filtering-and-mapping-with-array-functions), so `->wrote[WHERE location = "Arizona"]->comment` walks every `wrote` edge and then filters the array that comes back. Inside the parentheses the condition is part of the path instead, and becomes the edge scan's own predicate, so edges that fail it are never followed. Both return the same records, and [`EXPLAIN`](/docs/reference/query-language/statements/explain) shows the difference: the parenthesised form carries a `predicate` on the scan, the bracketed one carries none. On a record with a few edges the difference does not matter, while on one with thousands, only the first stays fast.

Naming several edge tables walks all of them at once, and `?` stands for any table:

```surql
SELECT VALUE ->(wrote, likes)->? FROM ONLY user:mcuserson;
```

```surql title="Output"
[comment:one, cat:pumpkin]
```

`->?->?` therefore follows every edge leaving a record, whatever its type. Where the edges on a record are not known in advance, reading the table name off each one gives the kinds of relationship it actually has:

```surql
SELECT VALUE array::distinct(->?.map(|$e| $e.id.tb())) FROM ONLY user:mcuserson;
```

```surql title="Output"
['likes', 'wrote']
```

An edge is a record like any other, so the same question can be asked from the edge table instead, with `in` and `out` naming the two ends:

```surql
SELECT out, mood FROM wrote WHERE location = "Arizona";
```

```surql title="Output"
[
	{
		mood: 'happy',
		out: comment:one
	}
]
```

Both forms reach the same edges. The arrow suits a walk that carries on to the records at the far end, and the table form suits a question about the edges themselves.

### Records with no edges

A traversal that finds no edges returns an empty array, and an empty array is falsy, so `!` in front of a path selects the records that have no edge in that direction. In a tree where each record points to its parent with a `child_of` edge, the roots are the records with no outgoing `child_of`, and the leaves are the records with no incoming one:

```surql
CREATE thing:a, thing:b, thing:c, thing:d;
RELATE thing:b->child_of->thing:a;
RELATE thing:c->child_of->thing:a;
RELATE thing:d->child_of->thing:b;
RELATE thing:d->child_of->thing:c;

-- Roots: no parent
SELECT VALUE id FROM thing WHERE !->child_of;
//- [thing:a]

-- Leaves: no children
SELECT VALUE id FROM thing WHERE !<-child_of;
//- [thing:d]
```

Each record checks only its own edges, so the query does not need to collect the ids of every child first.

## Querying symmetric (“between equals”) relations

For edges like `friends_with`, it may be unclear whether a `person` is on the `in` or `out` side. The `<->` operator traverses **both** directions on that edge table:

```surql
SELECT *, <->friends_with<->person AS friends FROM person;
```

Each record lists the other people in the relation, regardless of which side they were on:

```surql
[
	{
		friends: [
			person:one,
			person:two
		],
		id: person:one
	},
	{
		friends: [
			person:one,
			person:two
		],
		id: person:two
	}
]
```

To drop the current record’s own id from the list, use [`array::complement()`](/docs/reference/query-language/functions/database-functions/array#arraycomplement):

```surql
SELECT 
	*, 
	array::complement(<->friends_with<->person, [id]) AS friends
FROM person;
```

```surql title="Output"
[
	{
		friends: [
			person:two
		],
		id: person:one
	},
	{
		friends: [
			person:one
		],
		id: person:two
	}
]
```

For more on this pattern, see the [`RELATE` statement](/docs/reference/query-language/statements/relate#bidirectional-relation-querying) and [Chapter 7 of Aeon's Surreal Renaissance](/learn/book/chapter-07#bidirectional-querying-when-a-relationship-is-equal).

## Traverse directly from a record id

Traversal can start at one or more record IDs **without** wrapping everything in `SELECT`:

```surql
CREATE ONLY user:mcuserson SET name = "User McUserson";
CREATE ONLY comment:one SET 
    text = "I learned something new!", 
    created_at = time::now();
CREATE ONLY cat:pumpkin SET name = "Pumpkin";

RELATE user:mcuserson->wrote->comment:one SET
	location = "Arizona",
	os = "Windows 11",
	mood = "happy";

RELATE user:mcuserson->likes->cat:pumpkin;
```

```surql
-- Equivalent to:
-- SELECT VALUE <-wrote<-user FROM ONLY comment:one;
comment:one<-wrote<-user;

-- Equivalent to:
-- SELECT VALUE ->likes->cat FROM ONLY user:mcuserson;
user:mcuserson->likes->cat;
```

```surql title="Output"
-------- Query --------

[user:mcuserson]

-------- Query --------

[cat:pumpkin]
```

To include fields when starting from an id, use destructuring:

```surql
-- Equivalent to:
-- SELECT name, ->likes->cat AS cats FROM ONLY user:mcuserson;
user:mcuserson.{ name, cats: ->likes->cat };
```

## Automatic flattening in graph queries

When two lookups follow each other, or a filter follows a lookup, results can **flatten** in a way that mirrors the graph shape. This example builds a small org chart and walks up and down `works_for`:

```surql
CREATE 
	-- One president
	person:president, 
	-- Two managers
	person:manager1, person:manager2,
	-- Four employees
	person:employee1, person:employee2, person:employee3, person:employee4;

-- Employees work two to a manager, managers work two to a president
RELATE [person:manager1, person:manager2]->works_for->person:president;
RELATE [person:employee1, person:employee2]->works_for->person:manager1;
RELATE [person:employee3, person:employee4]->works_for->person:manager2;

[person:employee1, person:employee2, person:employee3, person:employee4]
    ->works_for->person
    ->works_for->person
    <-works_for<-person
    <-works_for<-person;
```

The result is four arrays, each reflecting the up-and-down path through the president.

You can approximate the same with nested `SELECT` / `map`, but nesting grows quickly:

```surql
[person:employee1, person:employee2, person:employee3, person:employee4]
	-- Each $p is a single record: an array<record>
    .map(|$p| SELECT VALUE out FROM works_for WHERE in = $p.id)
	-- Each $p is an array, so now you have to map each item inside that
    .map(|$p| $p.map(|$p| SELECT VALUE out FROM works_for
      WHERE in = $p.id))
    -- Now an array<array<array<record>>>
    .map(|$p| $p.map(|$p| $p.map(|$p| SELECT VALUE in FROM works_for
      WHERE out = $p.id)))
    -- Now an array<array<array<array<record>>>>
    .map(|$p| $p.map(|$p| $p.map(|$p| $p.map(|$p| SELECT VALUE in
      FROM works_for WHERE out = $p.id))));
```

Graph syntax keeps structure aligned with the traversal. Calling `flatten()` at each step produces a **flat** list of every record seen along the way instead:

```surql
[person:employee1, person:employee2, person:employee3, person:employee4]
    .map(|$p| SELECT VALUE out FROM works_for WHERE in = $p.id).flatten()
    .map(|$p| SELECT VALUE out FROM works_for WHERE in = $p.id).flatten()
    .map(|$p| SELECT VALUE in FROM works_for WHERE out = $p.id).flatten()
    .map(|$p| SELECT VALUE in FROM works_for WHERE out = $p.id).flatten();
```

Treat graph flattening as preserving the **shape** of the walk, not necessarily a single post-hoc array.

### Grouping children under each parent

A path that continues past a level gives the records at the end of the path, and the level in between is not part of the output. In the store below, `->has->category->has->item` gives every item in the store in one array, without the categories they belong to:

```surql
CREATE store:local SET name = 'Local store';
CREATE category:food SET name = 'Food';
CREATE category:drinks SET name = 'Drinks';
CREATE item:burger SET name = 'Burger';
CREATE item:roll SET name = 'Roll';
CREATE item:water SET name = 'Water';

RELATE store:local->has->[category:food, category:drinks];
RELATE category:food->has->[item:burger, item:roll];
RELATE category:drinks->has->item:water;

SELECT name, ->has->category->has->item.name AS items FROM store:local;
```

```surql title="Output"
[
	{
		items: ['Roll', 'Burger', 'Water'],
		name: 'Local store'
	}
]
```

To keep the items under their category, stop the path at `category` and continue from each category with a [destructuring](/docs/reference/query-language/language-primitives/idioms#destructuring) `.{ }`. The paths inside the braces start from the category:

```surql
SELECT name, ->has->category.{ name, items: ->has->item.name } AS categories FROM store:local;
```

```surql title="Output"
[
	{
		categories: [
			{ items: ['Roll', 'Burger'], name: 'Food' },
			{ items: ['Water'], name: 'Drinks' }
		],
		name: 'Local store'
	}
]
```

A nested `SELECT` over the path gives the same result, and also allows a `WHERE`, `ORDER BY` or `LIMIT` for each level:

```surql
SELECT name, (SELECT name, ->has->item.name AS items FROM ->has->category) AS categories FROM store:local;
```

The same approach works for record links, for example `categories.{ name, items: items.name }` for a store whose `categories` field holds record links to categories that each hold an `items` field.

### Ranking records by shared connections

A path through a shared record returns a record once for every route that reaches it, so the repeats count the connections. Going from a post to its tags and back to the posts with those tags, a post that shares two tags appears twice. Grouping the result and counting gives the related posts in order of how much they share:

```surql
CREATE post:a SET title = 'A';
CREATE post:b SET title = 'B';
CREATE post:c SET title = 'C';
CREATE post:d SET title = 'D';
CREATE tag:rust, tag:db, tag:web;
RELATE post:a->tagged->[tag:rust, tag:db];
RELATE post:b->tagged->[tag:rust, tag:db, tag:web];
RELATE post:c->tagged->tag:web;
RELATE post:d->tagged->tag:db;

LET $post = post:a;
SELECT title, count() AS shared
FROM ($post->tagged->tag<-tagged<-post).filter(|$p| $p != $post)
GROUP BY title
ORDER BY shared DESC;
```

```surql title="Output"
[
	{ shared: 2, title: 'B' },
	{ shared: 1, title: 'D' }
]
```

The `.filter()` removes the starting post, which the path also reaches through each of its own tags. A `SELECT` over an array of record IDs reads the records, so `title` is available to group by.

## Graph paths in schema fields

Paths are not limited to `SELECT`; they can appear in [`DEFINE FIELD`](/docs/reference/query-language/statements/define/field):

```surql
DEFINE FIELD employers
  ON TABLE person VALUE SELECT VALUE <-employs<-company FROM ONLY $this;

CREATE person:1, person:2, company:1;
RELATE company:1->employs->person:1;
person:1.*;
```

A plain `VALUE` field is computed when the record is created or updated; if the `RELATE` runs later, the field can be stale until an `UPDATE`:

```surql
UPDATE person:1;
```

```surql title="Output"
[
	{
		employers: [
			company:1
		],
		id: person:1
	}
]
```

A [computed field](/docs/reference/query-language/statements/define/field#restrictions-on-computed-fields) is recomputed on read:

```surql
DEFINE FIELD employers ON TABLE person COMPUTED <-employs<-company;

CREATE person:1, person:2, company:1;
RELATE company:1->employs->person:1;
person:1.*;
```

```surql title="Output"
{
	employers: [
		company:1
	],
	id: person:1
}
```

## Using SurrealDB Studio Explorer to debug paths

SurrealDB Studio’s [Explorer view](/docs/explore/studio) lets you step through records and relations one hop at a time, useful for building intuition for queries like `SELECT ->wrote->comment FROM user`.

Example setup with two outgoing edges:

```surql
CREATE user:mcuserson SET name = "User McUserson";
CREATE comment:one SET 
    text = "I learned something new!", 
    created_at = time::now();
CREATE cat:pumpkin SET name = "Pumpkin";

RELATE user:mcuserson->wrote->comment:one SET
	location = "Arizona",
	os = "Windows 11",
	mood = "happy";

RELATE user:mcuserson->likes->cat:pumpkin;
```

Walkthrough:

* Open `user`, then `user:mcuserson`.
* Open the **Relations** tab (outgoing `->`).
* Follow `wrote` into its edge record, then `comment` to the comment record, matching `->wrote->comment`.

Working backward in the Explorer is a good way to assemble a path while learning the syntax.
