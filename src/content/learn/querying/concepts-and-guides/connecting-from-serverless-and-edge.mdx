Instead of long-lived processes with persistent connections, serverless and edge code runs in short-lived, stateless executions, often across multiple regions.

Some examples of environments in which this pattern is used are AWS Lambda, Vercel Functions / Edge Functions, Cloudflare Workers, and Deno Deploy. For Vercel specifically, see [SurrealDB on Vercel](/docs/build/integrations/vercel), which covers Next.js, the AI SDK, eve and Vercel Sandbox.

SurrealDB works well in these environments when it is used with the connection patterns on this page.

These patterns are for application code that connects to a SurrealDB server running somewhere else, such as a [SurrealDB Cloud](/docs/running/cloud) instance or a self-hosted server. The server itself is designed to run as a separate long-lived service. The [`surrealdb-server`](https://crates.io/crates/surrealdb-server) crate does make its HTTP and RPC router available to a Rust application, but that crate is SurrealDB's internal API and can change between patch releases.

Each function instance also cannot open its own embedded datastore on shared storage. A SurrealKV data directory can be open in only one process at a time, and the second process that opens the same path fails with an error such as `Database at mydb/LOCK is already locked by another process`. Mounting the directory from a network file system such as Amazon EFS does not let several function instances use it at once. To share data between function instances, run SurrealDB as a separate server or use SurrealDB Cloud, and connect to it with the patterns on this page. [Embedding SurrealDB in Rust](/docs/reference/rust/embedding) describes the lock in more detail.

## Serverless vs. traditional

The following chart summarises the differences between the two approaches.


| Traditional server | Serverless / edge |
|------------------|------------------|
| Long-lived process | Short-lived execution |
| Persistent connections | No guaranteed reuse |
| Connection pooling | Not available |
| Single region | Often multi-region |
| Warm memory | Frequent cold starts |


As many serverless and edge environments don't support TCP sockets, connecting over HTTP is generally used. As no persistent connection is required, this allows you to create a new client, connect, run queries and then exit.

```javascript
import { Surreal } from 'surrealdb';

const db = new Surreal();

await db.connect('https://your-instance');

await db.signin({
  username: 'your-user',
  password: 'your-pass',
});

await db.use({
  namespace: 'app',
  database: 'prod',
});

const result = await db.query('SELECT * FROM user');
```

## Cloudflare Workers

A Worker cannot use a connection that another request opened. Cloudflare ties an I/O object, such as a WebSocket, to the request that created it, so a client kept in a global variable and shared between requests stops answering. Create the client inside the request handler, and close it when the response is sent.

Read the endpoint and the credentials from `env` inside the handler as well. Cloudflare runs the module's global code when it deploys the Worker, before secrets are available.

```typescript title="Connect for each request"
import { Surreal } from 'surrealdb';

export default {
  async fetch(request, env, ctx) {
    const db = new Surreal();

    await db.connect(env.SURREAL_URL, {
      namespace: 'app',
      database: 'prod',
      authentication: {
        username: env.SURREAL_USER,
        password: env.SURREAL_PASS,
      },
    });

    try {
      const [users] = await db.query('SELECT * FROM user').collect();
      return Response.json(users);
    } finally {
      ctx.waitUntil(db.close());
    }
  },
};
```

## Transactions over HTTP

A transaction started with `beginTransaction()` keeps its state on the connection, so it needs a WebSocket connection. Over HTTP, the JavaScript SDK throws `UnsupportedFeatureError` for it.

To run several queries atomically over HTTP, pass them to `db.transaction()`, from JavaScript SDK 2.1. The SDK wraps them in `BEGIN` and `COMMIT` and sends them as one request, so either all of their changes are applied or none are:

```javascript title="An atomic transaction over HTTP"
const [from, to] = await db.transaction([
  'UPDATE ONLY account:alice SET balance -= 30',
  'UPDATE ONLY account:bob SET balance += 30',
]);
```

A query that fails, or a `THROW`, cancels every change in the list. The queries cannot contain `BEGIN`, `COMMIT`, `CANCEL`, or a `RETURN` followed by further statements.

Use `beginTransaction()` over a WebSocket connection when the application needs the result of one query in the transaction to decide on the next one.

## Authentication patterns

Authentication by password uses [secure salted and hashed passwords](/learn/book/chapter-15#a-bit-of-cryptography) that rely on algorithms that are compute-heavy and purposely take a few hundred milliseconds per attempt.

```javascript
// Basic approach: authenticate per request
await db.signin({ username: '...', password: '...' });
```

If you can store pre-generated tokens securely in environment variables or platform secrets, then using a token directly may be preferred.

```javascript
await db.authenticate('your-token');
```

## Batching queries

The flexibility of SurrealQL allows you to batch and optimise queries, performing multiple operations inside a single request instead of multiple requests. Take this example to create and link two records that might be done over three operations, returning the first two results through an SDK to finally perform a `RELATE` operation at the end.

```surql
-- Request 1
CREATE person:one;

-- Request 2
CREATE person:two;

-- Request 3
RELATE person:one->likes->person:two;
```

This can be sent as a single request, and can even be written as a single query that both creates and relates the records in question.

```surql
RELATE
	(CREATE ONLY person:one RETURN VALUE id)
->likes->
	(CREATE ONLY person:two RETURN VALUE id);
```

## When not to use serverless patterns

Serverless and edge connections are not always the best choice.

Consider a long-lived backend service if you need:

* Live queries or subscriptions
* Real-time updates over WebSockets
* High-frequency queries from the same process
* Persistent connection state

In these cases, a traditional backend with a persistent SurrealDB connection will be more efficient.
