# Middleware for custom APIs

When you use [`DEFINE API`](/docs/reference/query-language/statements/define/api), the `THEN` block is the handler that decides the HTTP-shaped response. Middleware is everything you run before that handler, such as timeouts, logging, auth checks, or tweaks to the outgoing payload. SurrealDB runs built-in helpers from the [API functions](/docs/reference/query-language/functions/database-functions/api) package alongside your own `fn::` functions, in the order you list them.

Custom middleware functions are ordinary [user-defined functions](/docs/reference/query-language/statements/define/function). Each one receives:

* The current request object (conventionally `$req`).
* A `next` closure that continues the chain and eventually runs `THEN` when no middleware remains.

You can add extra parameters after those two. Their values are supplied when you attach the function to `DEFINE API` (for example passing in `time::now()` to return the time at which a request was processed).

The function must return an object - that is the response object passed to the next middleware or returned to the client. Names like `$req` and `$next` are only conventions; what matters is the order of arguments and that you actually call `$next($req)` when you want the pipeline to proceed.

## Starting from a handler with no middleware

```surql
DEFINE API "/custom_response"
    FOR get
        THEN {
            {
                status: 200,
                body: {
                    num: 1
                }
            };
        };
```

Calling `api::invoke("/custom_response")` returns the body you would expect:

```surql title="Sample output"
{
	body: {
		num: 1
	},
	headers: {
		"x-surreal-request-id": '90ecf16c-d3d5-4a06-825f-c54c5af5afbf'
	},
	request_id: '90ecf16c-d3d5-4a06-825f-c54c5af5afbf',
	status: 200
}
```

## Adding a function that adjusts the response

This middleware calls `$next($req)` to obtain the handler's result, then bumps `body.num` by one before returning:

```surql
DEFINE FUNCTION fn::increment_num($req: object, $next: function) -> object {
    LET $res = $next($req);
    $res + { body: { num: $res.body.num + 1 } }
};

DEFINE API "/custom_response"
    FOR get
        MIDDLEWARE
            fn::increment_num()
        THEN {
            {
                status: 200,
                body: {
                    num: 1
                }
            };
        };
```

Now `api::invoke("/custom_response")` yields `num: 2`, showing that the outer middleware has reshaped what the caller sees.

```surql title="Sample output"
{
	body: {
		num: 2
	},
	headers: {
		"x-surreal-request-id": 'a4fa9a57-f1ac-4eb1-8433-cce37a19a5e0'
	},
	request_id: 'a4fa9a57-f1ac-4eb1-8433-cce37a19a5e0',
	status: 200
}
```

## Stacking two pieces of middleware

Order matters when adding middleware, so be sure to list outer effects first if they should wrap everything that follows. Here a timer middleware adds a timestamp as an `x-called-at` header, and increment still adjusts the body:

```surql
DEFINE FUNCTION fn::start_timer($req: object, $next: function, $called_at: datetime) -> object {
    LET $res = $next($req);
    $res + { headers: { "x-called-at": <string>$called_at } }
};

DEFINE FUNCTION fn::increment_num($req: object, $next: function) -> object {
    LET $res = $next($req);
    $res + { body: { num: $res.body.num + 1 } }
};

DEFINE API "/custom_response"
    FOR get
        MIDDLEWARE
            fn::start_timer(time::now()),
            fn::increment_num()
        THEN {
            {
                status: 200,
                body: {
                    num: 1
                }
            };
        };

api::invoke("/custom_response");
```

```surql title="Sample output"
{
	body: {
		num: 2
	},
	headers: {
		"x-called-at": '2026-10-14T04:51:23.959554Z',
		"x-surreal-request-id": 'ba447d57-24e6-4cf4-9e8b-68076b040980'
	},
	request_id: 'ba447d57-24e6-4cf4-9e8b-68076b040980',
	status: 200
}
```
