# Dedicated Agent Memory clusters

A dedicated Agent Memory cluster is Agent Memory on compute that only your organisation uses. It is a SurrealDB database plus the memory engine, in an AWS region chosen when the cluster is created, and it runs on your own model keys. This page covers what a dedicated cluster changes compared with shared contexts, how an owner or admin manages one in [Studio](https://studio.surrealdb.com), and how its language models are configured.

> [!NOTE]
> Dedicated Agent Memory clusters are part of the Enterprise offering, and SurrealDB sets each one up for your organisation. To find out whether a dedicated cluster suits your workload, [contact us](https://surrealdb.com/contact/sales).

## Compared with shared contexts

| | Shared contexts | Dedicated cluster |
| --- | --- | --- |
| Created by | You, in Studio | SurrealDB staff |
| Compute | A shared pool | Your organisation's own nodes |
| Region | The shared pool's | Any AWS region, fixed at creation |
| Model keys | SurrealDB's | Your own keys, or your own model gateway |
| Billed | By Agent Memory plan | By use, for compute and storage |

Contexts on a dedicated cluster work like contexts anywhere else. The [REST API](/docs/agent-memory/reference/rest-api), the SDKs and the MCP server are the same, and each context has its own database. SurrealDB enables dedicated clusters for the organisation, and creates the cluster in the region you choose.

## Manage a cluster in Studio

A dedicated cluster appears in Studio under **Agent Memory**, as its own row beneath the shared contexts. The row lists the cluster's contexts and has a tile to deploy a new one into it. A cluster that is still being set up shows **Creating** instead of its contexts.

**View cluster** opens the cluster page, which has these tabs:

| Tab | What it shows |
| --- | --- |
| Contexts | The cluster's contexts. **Deploy new context** deploys straight into this cluster. |
| Usage | Compute hours, storage and tokens for the current billing period, then tokens for each context. |
| Settings | The cluster's name, region, model keys and model endpoint, and deletion. |

Every member of the organisation can see the cluster and its contexts. Only owners and admins can add or replace model keys, set a model endpoint, deploy a context or delete the cluster. Members see the settings read-only.

## Model keys and your own gateway

Chat and embeddings are configured separately. Chat runs on one provider that you choose, which can be your own OpenAI-compatible gateway. Embeddings always run on Gemini.

| Setting | What you provide | Limits |
| --- | --- | --- |
| Chat provider | An Anthropic, OpenAI, Google, OpenRouter or Cerebras key, and optionally a model | OpenAI and Google accept only the models Agent Memory knows. OpenRouter and Cerebras need a model ID. |
| Model endpoint | A base URL (HTTPS), an API key sent as the bearer token, and the model ID your gateway serves | Chat only. Tokens served through the endpoint do not count against Agent Memory limits. |
| Embeddings | A Gemini API key | Always `gemini-embedding-2` with 3072 dimensions. No other embedding model can be used. |
| OCR, speech, CLIP, document parsing and reranking | Optional HTTP endpoints | Set through the API only, not in Studio. |

Keys are stored encrypted and never shown again. **Replace** swaps a key, and the memory engine restarts on the new one. **Add endpoint** in the cluster's Settings points chat at your gateway. The [configuration reference](/docs/agent-memory/reference/configuration) lists which model each stage uses.

Because embeddings run on Gemini, the text that Agent Memory embeds goes to Google, even when chat runs entirely on your own gateway.

## Private gateways

The base URL of a model endpoint must not be, or resolve to, a loopback, link-local, reserved or cluster address. A private address is refused unless SurrealDB has allowed its network for your organisation. To have a network allowed, send SurrealDB its IP ranges.

Allowing a network only lets the address pass this check. The cluster also needs a network route to the gateway, such as PrivateLink or VPC peering, and dedicated clusters have neither. A gateway that is reachable only on a private network therefore cannot be used, and a gateway with a public HTTPS address can.

## Create a cluster without keys

SurrealDB staff can create a cluster before you have chosen model keys. The database comes up, the memory engine waits for keys, and the cluster stays in **Creating**. Studio shows the cluster as waiting for model keys.

An owner or admin then opens the cluster's **Settings** and selects **Add model keys**. They choose the chat provider, or **Custom endpoint** for their own gateway, and enter its key, the model where one is needed, and the Gemini key for embeddings. Studio saves them together, the memory engine starts, and the cluster becomes **Ready**. Creating a cluster this way means SurrealDB never handles your keys.

## Limits

- Customers cannot create a dedicated cluster in Studio. SurrealDB staff create every cluster.
- A cluster can be deleted only when it holds no contexts.
- Embeddings run only on Gemini `gemini-embedding-2`.
- Dedicated clusters have no PrivateLink or VPC peering.
